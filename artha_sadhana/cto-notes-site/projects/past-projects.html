Project 1 — IDFC PFM: Transaction Categorization + Spend Insights (sections 1–7)
1. 1. IDFC — PFM Transaction Categorization + Spend Insights

What is the problem?

Suppose a customer makes:

₹2,500 paid to Swiggy

The banking system initially only knows:

Merchant = Swiggy
Amount   = ₹2,500
Date     = 10-Sep

PFM = Personal Financial Management wants to convert that into:

Category = Food
Subcategory = Food Delivery

Then it can generate:

Monthly Food Spend = ₹8,500
Monthly Shopping  = ₹12,000
Monthly Travel    = ₹5,000

The ML model performs the categorization.

3. How this works

Step 1 — Transaction arrives

Example:

Customer → ₹1,200 → Amazon

The transaction event goes into Kafka.

Why Kafka?

Because you don't want the transaction processing system to wait for ML processing.

Step 2 — Feature generation

The system creates features such as:

merchant       = Amazon
amount         = 1200
transaction_type = UPI
time           = 20:30
historical_merchant_category = Shopping
customer_history = Shopping

These features are sent to the model.

Step 3 — ML prediction

Model returns:

Category = Shopping
Confidence = 96%

You can imagine the API as:

POST /categorize

{
   "merchant": "Amazon",
   "amount": 1200,
   "payment_type": "UPI"
}

Response:

{
  "category": "Shopping",
  "confidence": 0.96
}

Step 4 — Store result

Transaction
     |
     +--> Category
     +--> Subcategory
     +--> Confidence

Stored in PFM data store.

Step 5 — Spend insights

Now the analytics layer can calculate:

Food       ₹8,500
Shopping   ₹12,000
Travel     ₹5,000
Bills      ₹15,000

The application can show:

"Your shopping expenditure increased 25% this month."

5. What is drift?

This is extremely important for an interview.

Suppose the model was trained in 2024.

At that time:

UPI merchants
Amazon
Flipkart
Swiggy
Zomato

But in 2026 new merchants appear.

The distribution changes.

Old data

Amazon      20%
Flipkart    15%
Swiggy      10%

New data

QuickCommerce merchants
Digital subscriptions
New UPI merchants

The model starts becoming less accurate.

That's model/data drift.

7. What you can say in an interview

Don't say:

Instead:

"I was involved in introducing the early MLOps practices around the PFM transaction-categorization models. 11. Why rules instead of ML?

This is an important interview question.

Because rules provide:

Explainability

You can say:

"Transaction was flagged because it came from a new device and unusual geography."

ML might simply say:

Fraud probability = 0.92

Rules are therefore useful for:

  • regulatory requirements
  • explainability
  • immediate policy changes
  • deterministic controls
  • known fraud patterns

Usually real systems use rules + ML, not only one.

Likely Interviewer Questions & Answers (sections 21)
21. What interviewers may ask you

Given your resume wording, I would expect these questions.

IDFC

Q1. What exactly was the model predicting?

Answer:

"The primary use case was transaction categorization — mapping raw transaction information to categories such as food, shopping, travel, utilities etc., which then supported PFM spend analytics."

Q2. How did you detect drift?

"We looked at changes in the production data and model-performance indicators. Feature distribution changes could indicate data drift, while degradation in metrics such as accuracy or precision/recall could indicate model performance degradation."

Q3. What happened after drift?

"The pipeline could trigger retraining using more recent data, evaluate the candidate model against the existing production model, and only promote it if it met predefined quality thresholds."

PayPal Fraud

Q4. Why use rules?

"Rules are deterministic, explainable and can be changed quickly when a known fraud pattern emerges. They complement ML models rather than necessarily replacing them."

Q5. What happens if the fraud engine goes down?

A strong architectural answer:

"The payment path needs a defined fail-open versus fail-closed strategy based on risk. For high-risk operations we may prefer fail-closed or step-up authentication, while lower-risk scenarios could use graceful degradation. The decision also depends on latency and business risk."

That's a very good architecture interview answer.

PayPal Risk MLOps

Q6. What do you monitor?

Think in 4 buckets:

1. Infrastructure
   CPU / Memory / Latency

2. Data
   Missing values / Schema / Drift

3. Model
   Accuracy / Precision / Recall

4. Business
   Fraud loss / False positives /
   Review rate / Approval rate

This distinction is important.
