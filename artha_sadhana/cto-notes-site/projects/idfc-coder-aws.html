3. Step 1 — Developer sends prompt

Suppose developer enters:

"Create a REST API in Go
for fetching mutual fund holdings.
Use Redis caching and MongoDB."

The IDFC Coder plugin/client sends something conceptually like:

{
  "user_id": "12345",
  "repository": "wealth-api",
  "language": "go",
  "prompt": "Create a REST API...",
  "files": [
    "holding.go",
    "repository.go",
    "handler.go"
  ],
  "context": {
    "branch": "feature/mf-holdings"
  }
}

Don't send the entire repository blindly.

Instead:

Repository
     │
     ▼
Context Engine
     │
     ├── relevant files
     ├── symbols
     ├── imports
     ├── recent changes
     └── developer prompt
             │
             ▼
       Context Window

This is an important architectural point.

6. Step 4 — ALB
ALB (Application Load Balancer) = Traffic manager for your application. Distributes traffic across multiple servers so one server doesn't get overloaded. Checks server health and avoids sending traffic to unhealthy servers. Can route requests based on URL/path, e.g. /payment → Payment Service, /order → Order Service.

10. The GPU architecture

Now you get into the part from your uploaded architect notes.

For the 33B model:

33B parameters

FP16
33B × 2 bytes
≈ 66 GB

INT8
33B × 1 byte
≈ 33 GB

INT4
33B × 0.5 byte
≈ 16.5 GB

Your notes emphasize that 16.5 GB is not the actual production requirement because you also need KV cache, activations, runtime and headroom.

Your source gives an illustrative production calculation:

Weights             ~17 GB
KV cache             ~2 GB
Activations          ~1 GB
Runtime              ~2 GB
Headroom             ~1 GB
                     -------
Total                ~23 GB

12. How I would actually calculate 6 GPUs

Start here:

10,000 registered users
          │
          ▼
2,000 daily active
          │
          ▼
500 peak concurrent
          │
          ▼
100 requests/sec peak
          │
          ▼
LLM benchmark
          │
          ▼
X requests/sec/GPU
          │
          ▼
Required GPU count

Suppose load testing gives:

1 L4 + vLLM

= 20 concurrent generations
while meeting our latency SLA

Then:

500 concurrent users
        │
        ▼
20 concurrent/GPU
        │
        ▼
500 / 20
        │
        ▼
25 GPUs

Then add HA/headroom:

25 × 1.2
≈ 30 GPUs

So the answer could become:

Production
    │
    ├── 30 GPU nodes
    ├── 30 LLM replicas
    ├── 3 AZs
    └── autoscaling

This is only an example.

If benchmarking instead shows:

1 GPU = 80 concurrent requests

then:

500 / 80
≈ 7 GPUs

with redundancy:

~10 GPUs

That's why an architect should never say:

"10K users means 10 GPUs."

Scaling & Failure Handling
18. Autoscaling

This is a very important interview question.

CPU autoscaling alone is wrong for an LLM workload.

You care about:

Queue depth
GPU utilization
Tokens/sec
Request latency
Time-to-first-token
Active generations
KV-cache utilization

Architecture:

                    Metrics
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    Queue depth     GPU usage       TTFT
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                  Autoscaler
                       │
                       ▼
                 GPU Node Count
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
         Scale Out            Scale In

Example:

Queue depth < 20
       │
       ▼
     6 GPUs

Queue depth > 100
       │
       ▼
     10 GPUs

Queue depth > 250
       │
       ▼
     16 GPUs
19. What happens if one GPU dies?

This is a classic CTO/architect question.

                 Inference Router
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      GPU-01         GPU-02         GPU-03
        │              │              │
       OK              X              OK

Health check detects:

GPU-02 unhealthy
       │
       ▼
Remove from routing
       │
       ▼
Requests → GPU-01 / GPU-03
       │
       ▼
Auto-replace GPU-02

The key is:

Never make one GPU a single point of failure.
