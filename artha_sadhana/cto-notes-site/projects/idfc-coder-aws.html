IDFC Coder — Architecture Interview Notes

Yes. For your IDFC Coder story, I would build the architecture explanation around one simple flow:

Developer enters prompt → authentication → API layer → prompt/security processing → request queue → GPU inference cluster → LLM/vLLM → response streaming → developer IDE/UI

Your uploaded architect notes already establish the important GPU decision chain: workload → VRAM → GPU → concurrency → GPU count → infrastructure cost → TCO.

One important distinction: I can give you a production-grade AWS reference architecture and sizing model, but I can't represent the exact internal IDFC Coder production topology as fact unless you have internal architecture evidence. For an interview, present the numbers below as design assumptions / sizing decisions unless you actually operated those resources.

GPU Capacity & Inference Engine (sections 10–14)
10. The GPU architecture

Now you get into the part from your uploaded architect notes.

For the 33B model:

33B parameters

FP16
33B × 2 bytes
≈ 66 GB

INT8
33B × 1 byte
≈ 33 GB

INT4
33B × 0.5 byte
≈ 16.5 GB

Your notes emphasize that 16.5 GB is not the actual production requirement because you also need KV cache, activations, runtime and headroom.

Your source gives an illustrative production calculation:

Weights             ~17 GB
KV cache             ~2 GB
Activations          ~1 GB
Runtime              ~2 GB
Headroom             ~1 GB
                     -------
Total                ~23 GB

Therefore:

T4
16 GB
  │
  X
  │
Cannot fit


L4
24 GB
  │
  ✓
  │
Can fit

This is exactly the architectural reasoning in your notes.

Start here:

10,000 registered users

Suppose load testing gives:

1 L4 + vLLM

= 20 concurrent generations
while meeting our latency SLA

Then:

500 concurrent users
        │
        ▼
20 concurrent/GPU
        │
        ▼
500 / 20
        │
        ▼
25 GPUs

Then add HA/headroom:

25 × 1.2
≈ 30 GPUs

So the answer could become:

Production
    │

If benchmarking instead shows:

1 GPU = 80 concurrent requests

then:

500 / 80
≈ 7 GPUs

with redundancy:

~10 GPUs

That's why an architect should never say:

"10K users means 10 GPUs."

14. What happens inside vLLM

Suppose:

User A → Generate REST API
User B → Fix this Java code
User C → Write unit tests
User D → Explain this function

Instead of:

GPU
 │
 ├── A complete
 ├── B complete
 ├── C complete
 └── D complete

the inference engine can use batching/scheduling:

                 vLLM
                   │
          ┌────────┼─────────┐
          ▼        ▼         ▼
        Req A    Req B     Req C
          │        │         │
          └────────┼─────────┘
                   ▼
             GPU execution
                   │
                   ▼

This is why concurrency and batching become architectural variables after the model fits. Your notes explicitly distinguish fit from subsequent latency/throughput/concurrency optimization.

18. Autoscaling

This is a very important interview question.

CPU autoscaling alone is wrong for an LLM workload.

You care about:

Queue depth

Tokens/sec

                    Metrics

                 Inference Router
                       │

      GPU-01         GPU-02         GPU-03

GPU-02 unhealthy
       │
       ▼
