Account Aggregator — Explained Simply

Each section opens with a question first — think about it before you expand the explanation. Then the plain-English walkthrough, with diagrams.

1

The Big Idea

▶
Recall Before you read on — why would a loan app want to talk directly to your bank instead of just asking you for a PDF statement?
▸ click to reveal answer
Because a PDF can be edited, is slow to upload, and gives no guarantee of freshness or authenticity. Talking to the bank directly means the app gets verified, real-time, tamper-proof data — with your explicit consent, not a screenshot you could have altered.

Say you want a loan. Old way: screenshot your statement, upload the PDF, wait. New way: the loan app asks your bank for permission to look at your statement, and you just tap Approve on your phone. No file uploads.

This "ask → approve → fetch" system is India's Account Aggregator (AA) network, regulated by the RBI. This project is the code that sits inside the loan app and automates the entire flow.

2

The Four Players

▶
Recall Setu isn't the bank and isn't the app — so what's the one job it actually does in this chain?
▸ click to reveal answer
Setu is the middleman / AA gateway — it relays the consent request from the app to the network, tracks its status, and routes the approved data-fetch to the correct bank. It never stores your actual financial data itself; it just brokers the handshake.

Four parties are involved, each with one job:

You approve → App asks Setu → Setu is the middleman → Bank releases the data.

3

The Handshake, Step by Step

▶
Recall The app calls /getconsent/{id} even though it already knows it sent the consent request. Why bother checking again?
▸ click to reveal answer
Because sending the request doesn't mean you approved it — that approval happens asynchronously, on your own time, on a separate screen. The app has no way of knowing when (or if) you clicked "Approve," so it has to poll or check status before it's allowed to fetch anything.

Here's exactly what happens, step by step:

1
Ask for permission. App calls POST /postconsent — "Can I see 6 months of your statements?" Setu replies with a Consent ID and a link.
2
You approve. Open the link, enter your mobile number, verify with OTP, tap Approve. Consent status becomes ACTIVE.
3
App confirms. Calls GET /getconsent/{id} — "did they actually approve?" Setu says: ACTIVE.
4
Data is fetched. App calls POST /createsession to start the pull, then GET /getsession/{id} to download the statement as JSON.
4

The Code — Three Files, Three Jobs

▶
Recall If Setu suddenly changed its API response format, which single file would you expect to edit — and why not the other two?
▸ click to reveal answer
ConsentRequests.py — it's the only file that actually talks to Setu over HTTP. AAIntegration.py just routes requests, and ConsentDetails.py only validates shapes of data — neither cares about the wire format Setu uses. This separation is exactly why the three-file split exists.

Only three Python files, each with a distinct role:

AAIntegration.py
The Router
  • Defines all web endpoints
  • Receives incoming requests
  • Passes them to the right helper
ConsentDetails.py
The Validator
  • Pydantic models for every request
  • Checks dates, data types, filters are correct
ConsentRequests.py
The HTTP Client
  • Actually calls Setu's servers
  • Handles retries for session creation

The Six Endpoints

▶
Recall Two endpoints use POST and two use GET for "consent" and "session" respectively. Can you guess the pattern before checking the table?
▸ click to reveal answer
POST = "create / kick off something new" (postconsent creates a consent request, createsession starts a data pull). GET = "check the status / read the result of something that already exists" (getconsent checks approval status, getsession reads the fetched data).

Will It Fetch Your Real Bank Data? UAT SANDBOX

▶
Recall Even with valid Setu sandbox keys plugged in, would this code touch your actual HDFC/SBI/ICICI account? Why or why not?
▸ click to reveal answer
No. The base URL points at fiu-uat.setu.co — the UAT (test) environment, which only has fake test banks and fake test phone numbers wired into it. Reaching a real bank requires a production Setu account and a production endpoint, regardless of key validity.

Not as-is. Here's why:

✗
Placeholder keys. In ConsentRequests.py, the credentials are literally the strings "SETU Client id" and "SETU client secret key". Any live call fails with 401 Unauthorized.
✗
Sandbox endpoint. The base URL is fiu-uat.setu.co — "UAT" means test environment. Even with valid sandbox keys, it only works against fake test banks and test numbers like 9999999999@setu.
✗
No production license. Pulling real bank data requires your entity to be registered with Setu / RBI as an approved Financial Information User (FIU).
# ConsentRequests.py
self.__header = {
    'x-client-id': "SETU Client id",          # placeholder
    'x-client-secret': "SETU client secret key"  # placeholder
}

What real production access requires

✓
Production Setu account — signed business agreement, approved as an official FIU.
✓
Switch the endpoint — from fiu-uat.setu.co to fiu.setu.co.
✓
Real credentials — actual client-id / client-secret issued by Setu.
✓
Encryption keys (JWE/JWS) — production payloads are encrypted; you need RSA/ECC key pairs to decrypt them.

High-Level System Architecture

▶
Recall Inside the FIU Backend box, why does AAIntegration.py point to both ConsentDetails.py and ConsentRequests.py, but those two never point to each other?
▸ click to reveal answer
Because the router is the only file that needs both a validated request and an outbound HTTP call — validation and network calls are independent concerns that don't need to know about each other. Keeping them decoupled is what makes each file replaceable on its own.

The Analogy, as a Flow

▶
Recall In the "digital key" analogy, who actually holds the key that unlocks your bank data — the app, Setu, or you?
▸ click to reveal answer
You do. The app can only request the key and Setu can only carry it — neither can unlock anything until you approve via OTP. That approval step is the actual key-turn; everything before it is just paperwork.

The 4-Step Handshake, as a Flowchart

▶
Recall Step 2 (User Approval) has no API calls from the FastAPI app at all. What does that tell you about where control sits during that phase?
▸ click to reveal answer
Control leaves the backend entirely — it's a black box to the app. The user is interacting directly with Setu's hosted consent page, and the FastAPI app has no visibility until it polls /getconsent in Step 3. This is why real systems often need a webhook or polling strategy here, not a blocking call.

Sequence Diagram — Full Timeline

That's the OTP approval step — the user opens Setu's redirect link and approves consent on Setu's own web/app handle, not inside the fintech app's UI. It's the one moment in the whole flow where the backend isn't in the room.

Summary

▶
Recall In one sentence, without looking back — what's the actual gap between this code and a production-ready integration?
▸ click to reveal answer
The logic is production-correct (the 4-step handshake is right); the gap is entirely credentials, environment, and licensing — swap sandbox keys/URL for production ones, get RBI/Setu approval, and add payload decryption.

It's a fully working practice model of a bank-data-fetching integration — every step is correct, it's just pointed at the sandbox, not the real bank network.
