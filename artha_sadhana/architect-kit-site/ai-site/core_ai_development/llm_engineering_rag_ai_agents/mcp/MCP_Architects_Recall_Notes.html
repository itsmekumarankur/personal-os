Goal: Don't memorize MCP as a list of APIs. Understand WHY it exists → HOW it works → WHERE it fits → WHAT can go wrong → HOW an architect designs it.

  • send requests

6. The BIG THREE — Resources vs Tools vs Prompts

This is one of the most important things to remember.

Ask:

Is the AI trying to READ, ACT, or GET GUIDANCE?

                    MCP SERVER
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
        RESOURCES      TOOLS      PROMPTS
             │           │           │
             ▼           ▼           ▼
            READ        ACT       GUIDE

📚 Resources

Think:

"Give me something."

Examples:

Customer information
Documentation
Files
Database information
Configuration

🔧 Tools

Think:

"Do something."

Examples:

send_email()
create_ticket()
make_payment()
query_database()

Tools can cause side effects.

That makes them much more dangerous.

📝 Prompts

Think:

"Help structure how I should do this."

For example:

sales_analysis
       │
       ▼
"You are a sales analyst.
 Analyze this data.
 Return:
   1. Trends
   2. Risks
   3. Recommendations"

🧠 Golden recall

RESOURCE = READ

TOOL     = ACT

PROMPT   = GUIDE

Or:

Give me → Do something → Help me structure.

22. Fan-out — the hidden complexity

Suppose one user question requires three MCP servers:

                 User Question
                      │
                      ▼
                   Client
                  /   |   \
                 /    |    \
                ▼     ▼     ▼
             Server A B     C
              40ms 900ms  55ms

The overall response may be constrained by:

MAX(A, B, C)

roughly:

max(40, 900, 55)
=
900ms

unless you use timeouts, partial responses, asynchronous handling, etc.

Architect questions

Ask:

What is my timeout budget?

Can calls execute in parallel?

What happens if one server fails?

Can I return partial results?

Which failures are fatal?

Which failures are optional?

These are distributed systems questions, not merely MCP questions.

33. The 60-second Architect explanation

The value of MCP is less about replacing APIs and more about standardizing the AI-to-capability boundary. Instead of every AI application building custom integrations with every data source or tool, MCP provides a common protocol. At production scale, I would focus heavily on authorization, PII protection, auditability, timeouts, retries, idempotency, rate limiting, versioning, ownership, and potentially a gateway for centralized governance.

That answer sounds much more senior than:

"MCP is a protocol for AI tools."
