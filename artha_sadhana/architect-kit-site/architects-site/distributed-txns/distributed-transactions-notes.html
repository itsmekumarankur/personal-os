## Distributed Transactions — 26-Point Revision Notes

1 Start with the right mental model 
┌─────────────────────────────────────────────────────────────────────────────┐
│                    DISTRIBUTED TRANSACTION ≠                              │
│                    "MANY DBs BEHAVING LIKE ONE DB"                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                           │
│   Distributed Transaction =                                               │
│   ┌─────────────────────────────────────────────────────────────────┐    │
│   │  Workflow coordination                                          │    │
│   │       +                                                         │    │
│   │  Failure handling                                               │    │
│   │       +                                                         │    │
│   │  Retry safety                                                   │    │
│   │       +                                                         │    │
│   │  Compensation                                                   │    │
│   │       +                                                         │    │
│   │  Reconciliation                                                 │    │
│   └─────────────────────────────────────────────────────────────────┘    │
│                                                                           │
│   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐                   │
│   │  Order DB   │   │  Payment DB │   │ Inventory DB│                   │
│   │  (Service A)│   │  (Service B)│   │  (Service C)│                   │
│   └─────────────┘   └─────────────┘   └─────────────┘                   │
│         │                  │                  │                          │
│         └──────────────────┼──────────────────┘                          │
│                            │                                             │
│                    Each service has its own                              │
│                    commit boundary                                       │
│                                                                           │
└─────────────────────────────────────────────────────────────────────────────┘

Core question: What happens if step 2 succeeds and step 3 fails?

2 There is no natural global commit authority 
        ┌─────────────────────────────────────────────────────────────────┐
        │          NO SINGLE DB TRANSACTION CONTROLS ALL SERVICES        │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐         │
        │   │  Order DB   │   │  Payment DB │   │ Inventory DB│         │
        │   │   COMMIT ✓  │   │   COMMIT ✓  │   │   COMMIT ✗  │         │
        │   └─────────────┘   └─────────────┘   └─────────────┘         │
        │         │                  │                  │                 │
        │         └──────────────────┼──────────────────┘                 │
        │                            │                                    │
        │                    ┌───────▼───────┐                           │
        │                    │   No single   │                           │
        │                    │ coordinator   │                           │
        │                    └───────────────┘                           │
        │                                                                 │
        │   To get global atomicity:                                     │
        │   ┌───────────────────────────────────────────────────────────┐│
        │   │  Option 1: Introduce coordination (2PC)                  ││
        │   │  Option 2: Accept partial progress (Saga + compensation) ││
        │   └───────────────────────────────────────────────────────────┘│
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Key insight: No single DB transaction can control all services. You must explicitly design for coordination or recovery.

3 The real goal is business correctness 
        ┌─────────────────────────────────────────────────────────────────┐
        │              BUSINESS CORRECTNESS > DATA CORRECTNESS          │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   Wrong Starting Question:                                     │
        │   ┌───────────────────────────────────────────────────────────┐│
        │   │ "How do I make all databases commit together?"           ││
        │   └───────────────────────────────────────────────────────────┘│
        │                                                                 │
        │   Right Starting Question:                                     │
        │   ┌───────────────────────────────────────────────────────────┐│
        │   │ "What business outcome must never be wrong?"             ││
        │   └───────────────────────────────────────────────────────────┘│
        │                                                                 │
        │   Data consistency ≠ Business correctness:                    │
        │   ┌───────────────────────────────────────────────────────────┐│
        │   │  Data consistency: all DB updates commit together        ││
        │   │  Business correctness: customer sees a valid outcome     ││
        │   └───────────────────────────────────────────────────────────┘│
        │                                                                 │
        │   Example:                                                     │
        │   ┌───────────────────────────────────────────────────────────┐│
        │   │  Shipping being delayed 2 minutes → acceptable           ││
        │   │  Payment charged + order missing → NOT acceptable        ││
        │   └───────────────────────────────────────────────────────────┘│
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Design principle: Design from business invariants backward.

4 Data atomicity ≠ business atomicity 
        ┌─────────────────────────────────────────────────────────────────┐
        │          DATA ATOMICITY vs BUSINESS ATOMICITY                 │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   DATA ATOMICITY:                                              │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  All database updates commit together in one operation │  │
        │   │  ┌─────────┐  ┌─────────┐  ┌─────────┐               │  │
        │   │  │  Order  │  │Payment  │  │Inventory│   ALL or NONE │  │
        │   │  │  Insert │  │  Insert │  │  Update │               │  │
        │   │  └─────────┘  └─────────┘  └─────────┘               │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   BUSINESS ATOMICITY:                                          │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Customer sees a valid business outcome                 │  │
        │   │  ┌──────────────────────────────────────────────────┐  │  │
        │   │  │  Order created + Payment charged                 │  │  │
        │   │  │      OR                                          │  │  │
        │   │  │  Order created + Payment pending (reconciled)   │  │  │
        │   │  └──────────────────────────────────────────────────┘  │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Not every step needs strict all-or-nothing behavior         │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Trade-off: Shipping being delayed 2 minutes may be acceptable. Payment charged + order missing is not.

5 Define the strict transaction boundary carefully 
        ┌─────────────────────────────────────────────────────────────────┐
        │              TRANSACTION BOUNDARY DECISIONS                    │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   STRONG CONSISTENCY REQUIRED:                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  ✓ Money movement and transfers                        │  │
        │   │  ✓ IPO allotment                                        │  │
        │   │  ✓ Lien marking                                         │  │
        │   │  ✓ Irreversible external commitments                    │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   EVENTUAL CONSISTENCY ACCEPTABLE:                            │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  ✓ Notifications and alerts                            │  │
        │   │  ✓ Analytics and reporting                             │  │
        │   │  ✓ Recommendations                                     │  │
        │   │  ✓ Cosmetic UI updates                                 │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Golden Rule:                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Don't let a confirmation email failure block a         │  │
        │   │  financial workflow!                                    │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
6 Four major building blocks 
        ┌─────────────────────────────────────────────────────────────────┐
        │                  FOUR BUILDING BLOCKS                          │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Strong atomicity        → 2PC                         │  │
        │   ├─────────────────────────────────────────────────────────┤  │
        │   │  Distributed workflow   → Saga                         │  │
        │   ├─────────────────────────────────────────────────────────┤  │
        │   │  Reliable event publish → Outbox                       │  │
        │   ├─────────────────────────────────────────────────────────┤  │
        │   │  Crash/retry safety     → Idempotency + Reconciliation│  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Mature systems use different patterns for different   │  │
        │   │  boundaries. There is no single "company-wide          │  │
        │   │  transaction pattern" that fits everything.            │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
7 2PC — what it tries to achieve 
        ┌─────────────────────────────────────────────────────────────────┐
        │                     TWO-PHASE COMMIT (2PC)                     │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   Phase 1: PREPARE (Voting)                                    │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │                 Coordinator                             │  │
        │   │                      │                                  │  │
        │   │          ┌───────────┼───────────┐                     │  │
        │   │          ▼           ▼           ▼                     │  │
        │   │      ┌─────────┐ ┌─────────┐ ┌─────────┐              │  │
        │   │      │  Order  │ │ Payment │ │Inventory│              │  │
        │   │      │PREPARE? │ │PREPARE? │ │PREPARE? │              │  │
        │   │      └────┬────┘ └────┬────┘ └────┬────┘              │  │
        │   │           │           │           │                    │  │
        │   │           ▼           ▼           ▼                    │  │
        │   │         YES          YES          YES                   │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Phase 2: COMMIT (Decision)                                   │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │                 Coordinator                             │  │
        │   │                      │                                  │  │
        │   │          ┌───────────┼───────────┐                     │  │
        │   │          ▼           ▼           ▼                     │  │
        │   │      ┌─────────┐ ┌─────────┐ ┌─────────┐              │  │
        │   │      │  Order  │ │ Payment │ │Inventory│              │  │
        │   │      │  COMMIT │ │  COMMIT │ │  COMMIT │              │  │
        │   │      └─────────┘ └─────────┘ └─────────┘              │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   All YES → COMMIT                                             │
        │   Any NO  → ROLLBACK                                           │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Main benefit: Genuine all-or-nothing atomicity.

8 Why 2PC hurts availability 
        ┌─────────────────────────────────────────────────────────────────┐
        │              WHY 2PC HURTS AVAILABILITY                        │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   Problem 1: Blocking Locks                                    │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Participants hold locks/prepared state while waiting   │  │
        │   │  ┌─────────┐  ┌─────────┐  ┌─────────┐                │  │
        │   │  │  Order  │  │ Payment │  │Inventory│   ← Locks held │  │
        │   │  │  LOCKED │  │  LOCKED │  │  LOCKED │   ← Resources  │  │
        │   │  └─────────┘  └─────────┘  └─────────┘   ← Blocked    │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Problem 2: Slowest Participant Wins                          │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Transaction duration = MAX(all participant times)     │  │
        │   │  Slowest participant slows everything                  │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Problem 3: Coordinator Failure = Blocked Participants       │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  Coordinator ──► CRASHES!                               │  │
        │   │       │                                                 │  │
        │   │       ▼                                                 │  │
        │   │  ┌─────────┐  ┌─────────┐  ┌─────────┐                │  │
        │   │  │  Order  │  │ Payment │  │Inventory│  ← WAITING     │  │
        │   │  │ WAITING │  │ WAITING │  │ WAITING │  ← FOREVER     │  │
        │   │  └─────────┘  └─────────┘  └─────────┘                │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Conclusion:                                                  │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  2PC is better for SMALL, tightly controlled systems,  │  │
        │   │  not internet-scale microservice workflows.             │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
9 2PC vs Saga = prevent vs recover 
        ┌─────────────────────────────────────────────────────────────────┐
        │                    2PC vs SAGA                                 │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   2PC:                                                         │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  "Don't let partial commit happen."                    │  │
        │   │                                                         │  │
        │   │  ┌──────┐   ┌──────┐   ┌──────┐                       │  │
        │   │  │Step 1│──►│Step 2│──►│Step 3│   ALL or NOTHING      │  │
        │   │  └──────┘   └──────┘   └──────┘                       │  │
        │   │                                                         │  │
        │   │  Favors: Stronger immediate atomicity                  │  │
        │   │  Cost:   Availability, scalability                      │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   SAGA:                                                         │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  "Partial progress may happen; recover and converge."  │  │
        │   │                                                         │  │
        │   │  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐           │  │
        │   │  │Step 1│──►│Step 2│──►│Step 3│──►│Step 4│           │  │
        │   │  └──────┘   └──┬───┘   └──────┘   └──────┘           │  │
        │   │                │                                        │  │
        │   │                ▼                                        │  │
        │   │            ┌──────────┐                                │  │
        │   │            │ FAIL!    │   Compensate earlier steps     │  │
        │   │            └──────────┘                                │  │
        │   │                                                         │  │
        │   │  Favors: Availability, scalability, independence       │  │
        │   │  Cost:   Complexity, temporary inconsistency           │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Choose based on:                                              │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Business tolerance for temporary inconsistency         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
10 TCC is a middle-ground pattern 
        ┌─────────────────────────────────────────────────────────────────┐
        │               TCC — Try, Confirm, Cancel                      │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  Phase 1: TRY                                          │  │
        │   │  ┌──────────────────────────────────────────────────┐  │  │
        │   │  │  Reserve resources without committing            │  │  │
        │   │  │  • Lock inventory quantity                       │  │  │
        │   │  │  • Reserve payment amount                        │  │  │
        │   │  │  • Hold the order slot                           │  │  │
        │   │  └──────────────────────────────────────────────────┘  │  │
        │   │                                                         │  │
        │   │  Phase 2: CONFIRM                                       │  │
        │   │  ┌──────────────────────────────────────────────────┐  │  │
        │   │  │  Convert reservations to actual operations      │  │  │
        │   │  │  • Deduct inventory                              │  │  │
        │   │  │  • Capture payment                               │  │  │
        │   │  │  • Confirm order                                 │  │  │
        │   │  └──────────────────────────────────────────────────┘  │  │
        │   │                                                         │  │
        │   │  Phase 3: CANCEL                                        │  │
        │   │  ┌──────────────────────────────────────────────────┐  │  │
        │   │  │  Release reservations without side effects      │  │  │
        │   │  │  • Release inventory                             │  │  │
        │   │  │  • Release payment hold                          │  │  │
        │   │  │  • Cancel order                                  │  │  │
        │   │  └──────────────────────────────────────────────────┘  │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Advantages:                                                   │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  ✓ Uses application-level actions (not DB locks)       │  │
        │   │  ✓ Stronger coordination than plain Saga               │  │
        │   │  ✓ Avoids some 2PC limitations                         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Useful when: Resources can explicitly support reservation/confirmation/cancellation.

11 Saga = sequence of local transactions 
        ┌─────────────────────────────────────────────────────────────────┐
        │                   SAGA WORKFLOW                                │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   Forward Path:                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  ┌─────────────┐                                        │  │
        │   │  │ 1. Create   │──► Order created (local commit)        │  │
        │   │  │    Order    │                                        │  │
        │   │  └─────────────┘                                        │  │
        │   │        │                                                │  │
        │   │        ▼                                                │  │
        │   │  ┌─────────────┐                                        │  │
        │   │  │ 2. Reserve  │──► Inventory reserved (local commit)   │  │
        │   │  │  Inventory  │                                        │  │
        │   │  └─────────────┘                                        │  │
        │   │        │                                                │  │
        │   │        ▼                                                │  │
        │   │  ┌─────────────┐                                        │  │
        │   │  │ 3. Charge   │──► Payment charged (local commit)      │  │
        │   │  │  Payment    │                                        │  │
        │   │  └─────────────┘                                        │  │
        │   │        │                                                │  │
        │   │        ▼                                                │  │
        │   │  ┌─────────────┐                                        │  │
        │   │  │ 4. Create   │──► Shipment created (local commit)     │  │
        │   │  │  Shipment   │                                        │  │
        │   │  └─────────────┘                                        │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Failure Path (Compensation):                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  Step 3 fails!                                          │  │
        │   │        │                                                │  │
        │   │        ▼                                                │  │
        │   │  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐   │  │
        │   │  │    Saga     │  │ Compensate  │  │ Compensate  │   │  │
        │   │  │  orchestrator│◄─│   Step 2    │◄─│   Step 1    │   │  │
        │   │  └─────────────┘  └─────────────┘  └─────────────┘   │  │
        │   │                                                         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Each step commits locally.                                   │
        │   Saga is only as good as the recovery logic behind each step.│
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
12 Compensation ≠ rollback 
        ┌─────────────────────────────────────────────────────────────────┐
        │              COMPENSATION vs ROLLBACK                          │
        ├─────────────────────────────────────────────────────────────────┤
        │                                                                 │
        │   ROLLBACK:                                                     │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  Charge: $100.00                                        │  │
        │   │     │                                                   │  │
        │   │     ▼                                                   │  │
        │   │  Rollback: Erase the change as if it never happened    │  │
        │   │     │                                                   │  │
        │   │     ▼                                                   │  │
        │   │  Result: Transaction is undone                         │  │
        │   │                                                         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   COMPENSATION:                                                 │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │                                                         │  │
        │   │  Charge: $100.00                                        │  │
        │   │     │                                                   │  │
        │   │     ▼                                                   │  │
        │   │  Compensation: Perform a NEW action to reverse         │  │
        │   │     │                                                   │  │
        │   │     ▼                                                   │  │
        │   │  Refund: $100.00                                        │  │
        │   │     │                                                   │  │
        │   │     ▼                                                   │  │
        │   │  Result: Two separate transactions:                    │  │
        │   │  Charge (+$100) + Refund (-$100) = Net zero            │  │
        │   │                                                         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   EXAMPLES:                                                    │
        │   ┌─────────────────────────────────────────────────────────┐  │
        │   │  Charge     → Compensation is Refund                  │  │
        │   │  Reserve    → Compensation is Release                 │  │
        │   │  Create     → Compensation is Cancel                  │  │
        │   │                                                         │  │
        │   └─────────────────────────────────────────────────────────┘  │
        │                                                                 │
        │   Key difference: A refund is NOT literally the same as      │
        │   the original charge never occurring.                        │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘

Remember: Compensation has its own side effects and failure modes.

Best Interview Sentence

"I don't start by choosing 2PC or Saga. I first identify the business invariant, classify each step by reversibility and failure semantics, then choose the coordination pattern, idempotency, and reconciliation strategy that keeps the business outcome correct even when the network doesn't tell me the truth."

# Topic Key Takeaway
1 Mental model Distributed transaction = workflow + failure + retry + compensation + reconciliation
2 No global commit No single DB controls all services; must design coordination or recovery
3 Business correctness Start with business invariants, not DB atomicity
4 Data vs business atomicity Not every step needs all-or-nothing
5 Transaction boundary Strong for money, eventual for notifications
6 Building blocks 2PC, Saga, Outbox, Idempotency + Reconciliation
7 2PC PREPARE → COMMIT/ROLLBACK, all-or-nothing
8 2PC availability cost Locks, slowest participant, coordinator failure
9 2PC vs Saga Prevent vs recover
10 TCC Try → Confirm → Cancel, middle-ground
11 Saga Sequence of local transactions with compensation
12 Compensation ≠ rollback Refund is a new action, not an undo
13 Reversibility Reversible → less reversible → irreversible (LAST)
14 Not everything is compensatable Push irreversible steps later
15 Compensation idempotency Compensation itself must be idempotent
16 Orchestration vs choreography Centralized coordinator vs event-driven
17 When orchestration is easier Clear visibility, easier debugging
18 Choreography risk Invisible spaghetti, hard to debug
19 Outbox DB update + event insert in one transaction
20 Outbox ≠ exactly-once At-least-once + idempotent consumers
21 Idempotency Repeated request, one business effect
22 Timeout = UNKNOWN Never blindly retry/compensate/cancel
23 Explicit workflow states FAILED and UNKNOWN are different
24 Reconciliation Query external truth for UNKNOWN
25 Effectively-once At-least-once + idempotency + reconciliation
