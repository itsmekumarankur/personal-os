NoSQL Databases — Easy Notes

1. NoSQL — The Right Mental Model

Don't think:

App → Database → Put/Get

Think:

App
 ↓
Coordinator
 ↓
Which partition?
 ↓
Which node?
 ↓
Which replicas?
 ↓
Disk

A NoSQL cluster is mainly about:

WHERE does the data live?
HOW many copies exist?
HOW fresh is the data?
HOW durable is the data?

Is NoSQL faster than SQL?

Not automatically.

NoSQL gives different trade-offs:

NoSQL
 ├── Horizontal scaling
 ├── Flexible schema
 ├── High write throughput
 └── Often relaxed consistency

The reason to choose NoSQL should be:

A specific access pattern or scale requirement — not simply "NoSQL is faster."
2. Four NoSQL Families
                    NoSQL
                      |
       +--------------+--------------+
       |              |              |
   Key-Value      Document      Wide-Column
       |              |              |
  lookup by key   related fields   huge/time
                                  ordered data
                      |
                    Graph
                      |
                relationships

Key-Value

user:1001 → {entire object}

Best when:

I always read/write the entire object using its key.

Document

user:1001
   ↓
{name, city, orders, ...}

Best when:

Data is semi-structured and related fields are read together.

Wide-Column

customer_id = 1001

10:00 → transaction
10:05 → transaction
10:10 → transaction

Best for:

Huge datasets + time/range-based queries.

Graph

Account A
   |
   ├── owns → Account B
   |
   └── linked → Customer C
                    |
                    └── owns → Account D

Best when:

Relationships and traversal are the query.

Most important NoSQL question

Before designing:

"What are my access patterns?"
             ↓
"At what scale?"
             ↓
"How should I partition the data?"

Schemaless ≠ No schema.

The schema moves into:

Application
    +
Access patterns
    +
Partition design
3. Partitioning

Partitioning answers:

WHERE does this record live?

Range Partitioning

User 1–10000     → Node A
User 10001–20000 → Node B
User 20001–30000 → Node C

Good for:

Range queries

But can create hotspots.

Hash Partitioning

hash(customer_id) % N
          ↓
      Partition

Example:

Customer A → Node 2
Customer B → Node 7
Customer C → Node 1
Customer D → Node 5

Good for:

Even distribution

But range queries become harder.

Hot partition

Suppose an IPO has:

scheme_id = ABC123

Thousands of users hit it simultaneously:

ABC123
  ↓
Partition X
  ↓
🔥🔥🔥🔥🔥🔥
HOT PARTITION

Adding nodes may not solve this if the hot key itself remains on one partition.

Hash vs Range

RANGE
Adjacent values stay together
       ↓
Great range scans
       ↓
Possible hotspots


HASH
Values spread out
       ↓
Great load distribution
       ↓
Range scans become scatter-gather

Best of both

Use a composite design:

customer_id
     ↓
HASH → chooses partition

transaction_time
     ↓
SORT/RANGE within partition

Result:

Customer A partition
 ├── Jan 1
 ├── Jan 2
 ├── Jan 3
 └── Jan 4
4. Partitioning vs Replication

Very important distinction:

PARTITIONING
     ↓
Where does the data live?

REPLICATION
     ↓
How does the data survive failure?

They solve different problems.

5. Replication

Leader-Based

             Leader
               A
             /   \
            ↓     ↓
          B         C
       Replica    Replica

Writes normally go through the leader.

Advantage

One authoritative writer
        ↓
Simpler consistency

Disadvantage

Leader dies
    ↓
Failover
    ↓
Temporary interruption

Leaderless / Quorum

Partition P

Node A ← write
Node B ← write
Node C ← write

All can participate

Correctness is based on quorum.

W = Write quorum
R = Read quorum
N = Number of replicas
6. Replication Factor ≠ Durability

Suppose:

N = 3

You have three copies.

But:

Write
 ↓
Node A ACK
 ↓
Client gets success
 ↓
B and C haven't received it

If A crashes:

Write LOST

So:

Durability depends on how many replicas must acknowledge the write, not merely how many copies eventually exist.

Replica Placement

Don't put replicas too close physically:

BAD

Rack 1
 A
 B
 C

A rack failure can kill all three.

Better:

AZ 1 → A
AZ 2 → B
AZ 3 → C

Why?

Failures are often correlated.
7. Write Path

Typical flow:

Client
  ↓
Coordinator
  ↓
Leader
  |
  +──→ WAL / Commit Log
  |
  +──→ Memtable
  |
  +──→ Replicas
  |
  ↓
 ACK

Why WAL first?

WAL = recovery source of truth

If:

Memory updated
     ↓
Process crashes
     ↓
WAL wasn't written

The update cannot be recovered.

Therefore:

WAL
 ↓
Memtable
 ↓
Replication

When should ACK happen?

Fast but risky:

Memtable updated
      ↓
ACK
      ↓
Replicate later

Leader crashes:

          LOST WRITE

Safer:

Write
 ↓
Enough replicas confirm
 ↓
ACK

More latency, but stronger durability.

8. Read Path

Example:

Customer redeems MF
      ↓
Write accepted
      ↓
Refresh after 200 ms
      ↓
Old balance appears

Why?

Write → Leader
          ↓
       Replicas
          ↓
      propagation delay

The read may hit:

Replica that hasn't caught up yet

This is replication lag.

9. Read-Your-Writes

Means:

After I write something, I should immediately see my own change.

Example:

Redeem MF
   ↓
Refresh
   ↓
Must see updated balance

Possible solution:

After write
    ↓
Route user's reads
    ↓
Leader / caught-up replica

Trade-off:

More consistency
      ↓
Less read scalability
10. Quorum — W + R > N

Suppose:

N = 3
W = 2
R = 2

Then:

W + R = 4
4 > 3

Therefore read and write sets must overlap.

WRITE
[A][B]

READ
[B][C]

       ↑
   overlap

So the read can find the latest version.

Weak configuration

N = 3
W = 1
R = 1

1 + 1 = 2
2 <= 3

No overlap guarantee.

WRITE → A

READ  → C

A ≠ C

Potential stale read.

11. Strong vs Eventual Consistency

Strong

Write
 ↓
Wait for required replicas
 ↓
Confirm
 ↓
Return

More:

Consistency ↑
Latency ↑

Eventual

Write
 ↓
Return quickly
 ↓
Replicas catch up later

More:

Speed ↑
Freshness ↓ temporarily

Operationally

Don't just say:

"Eventually it will be consistent."

Measure:

Replication lag

p50 = typical
p99 = worst important case

This gives you a real staleness window.

12. Access-Pattern Design

This is one of the most important NoSQL concepts.

SQL:

Create table
    ↓
Later
    ↓
CREATE INDEX
    ↓
New query

NoSQL:

Query pattern
      ↓
Partition key
      ↓
Data placement
      ↓
Performance

Therefore:

Design your access patterns before designing the table.

Example:

Requirement:

Get all orders for customer 1001
newest first

Good:

Partition = customer_id
Sort      = created_at DESC

Bad:

Partition = order_id

SQL might have:

Customers
   |
   +--- Orders
          |
          +--- Products

If you copy this structure blindly into NoSQL:

 ↓

 ↓
Product partition

Potentially:

Scatter
 +
Gather

Multiple lookups

Instead:

        ↓
Keep read path simple
14. Secondary Indexes in NoSQL

Primary data:

user_id → customer document

But now you want:

Find customer by email

Secondary index:

email → user_id

Now one logical write becomes:

Write customer
     |
     +----→ Primary storage
     |
     +----→ Secondary index

Potential problem:

Two partitions
      ↓
Two writes
      ↓
No natural atomicity
      ↓
Index can temporarily lag

So secondary indexes can introduce consistency challenges.

Local vs Global Secondary Index

Local

Same partition
     ↓
Base data + index
     ↓
Cheap consistency

But usually requires knowing the partition key.

Global

Base data
   ↓
Partition A

Index
   ↓
Different partition

Supports new query patterns, but:

More distributed work
+
Potential async lag
15. LSM Storage Engine

LSM = Log-Structured Merge Tree

Typical write path:

Write
 ↓
WAL
 ↓
Memtable
 ↓
Flush
 ↓
SSTable
 ↓
Compaction
 ↓
Merged SSTables

Why is LSM good for writes?

Writes are mostly:

Sequential
   ↓
Append
   ↓
Fast

Instead of constantly modifying disk pages in place.

16. LSM Trade-off

You gain:

High write throughput

But pay with:

Read amplification
+
Compaction cost

A key may exist in multiple SSTables:

Read key X

SSTable 1 → check
SSTable 2 → check
SSTable 3 → check
SSTable 4 → check

Compaction eventually merges them.

Compaction Storm

During a huge write workload:

Writes
 ↓
SSTables created quickly
 ↓
Compaction can't keep up
 ↓
More SSTables
 ↓
Reads check more files
 ↓
p99 latency ↑

So:

LSM is excellent for write-heavy workloads, but compaction must be managed.
17. Routing & Rebalancing

Clients may cache:

Partition → Node

Example:

Before:

P1 → A
P2 → B
P3 → C

Add Node D:

After:

P1 → A
P2 → D
P3 → C

If the client still thinks:

P2 → B

it sends requests to the wrong node.

Therefore:

Partition map
     ↓
Must detect changes
     ↓
Refresh
18. Why Rebalancing Is Hard

Rebalancing means moving live data:

Node A
  |
  | move data
  ↓
Node D

while:

Reads continue
Writes continue

Problems:

Data movement
+
Network usage
+
Disk usage
+
Ownership change
+
Concurrent writes

So rebalancing itself can affect production performance.

19. Split-Brain

One of the most dangerous failures.

          Network partition
             /       \
            /         \
         Node A      Node B
           ↓           ↓
       "I am leader" "I am leader"
           ↓           ↓
        WRITE         WRITE

Both sides accept different writes.

When network heals:

Node A → History A
Node B → History B

        ↓

     CONFLICT

This is split-brain.

Especially dangerous for:

Money
Balances
Ledger

because there must be one authoritative history.

20. Replica Repair

Replicas can drift because replication is often asynchronous.

Instead of comparing millions of rows:

Replica A
vs
Replica B
vs
Replica C

Use hash/Merkle-like summaries:

Entire dataset
      ↓
   Hash tree
   /       \
 Hash       Hash
 /  \       /  \
... ...   ... ...

If hashes differ:

Find differing range
       ↓
Compare only that range
       ↓
Repair

Much cheaper than comparing everything.

21. Multi-Partition Transactions

Single record:

Update document
     ↓
Easy atomic operation

Two different partitions:

Account balance
       +
Transaction log
       ↓
Different partitions
       ↓
Distributed transaction

Now you may need:

2PC / database-native
distributed transaction

This is more expensive and complex.

22. TTL — Logical vs Physical Expiry

Suppose:

TTL = 24 hours

After 24 hours:

LOGICALLY EXPIRED

But physical deletion may happen later:

24h
 ↓
No longer logically valid
 ↓
Background cleanup
 ↓
Physical deletion

So:

Expired does not always mean physically deleted immediately.

Important for compliance requirements.

23. Multi-Region Writes

Single region:

Region A
   ↓
Leader

Multi-writer:

Region A → WRITE X
Region B → WRITE Y

       ↓

Same key
       ↓
CONFLICT

Because there is no single leader deciding the order.

Therefore multi-writer systems need:

Conflict resolution strategy
24. Example Architecture

A NoSQL platform might deliberately use different consistency levels:

                 NoSQL Cluster
                      |
          +-----------+-----------+
          |                       |
       Ledger                  Cache
          |                       |
      W=2, R=2                W=1, R=1
          |                       |
    Stronger safety           Faster

This is not inconsistent engineering.

It is:

Consistency level chosen per table based on the value of the data.

The 7 questions to ask in every NoSQL design

1. What are my access patterns?
2. What is my partition key?
3. Can this key become HOT?
4. How many replicas do I need?
5. When do I ACK a write?
6. How stale can a read be?
7. What happens when a node/network/AZ dies?

CTO-level takeaway

NoSQL is not "SQL without joins." It is a deliberate trade-off around data placement, scalability, availability, consistency, and access patterns.

And the most important rule:

SQL:
Data → Add index → Query

NoSQL:
Query → Design partition → Design data

Design the access pattern first. The database structure follows from it.
