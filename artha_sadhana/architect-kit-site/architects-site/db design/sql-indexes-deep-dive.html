SQL Indexes — Easy Notes

1. Clustered vs Non-Clustered Index

Basic idea

Think of a table as a bookshelf.

CLUSTERED INDEX
= The bookshelf itself

[Book A] [Book B] [Book C] [Book D]
        ↑
   Data is physically
   ordered this way

Only ONE physical order is possible.
NON-CLUSTERED INDEX
= Card catalog beside the shelf

Author Index  ──────> Book position
Title Index   ──────> Book position
Date Index    ──────> Book position

Many indexes can exist.

Key difference

ClusteredNon-Clustered
Determines physical row orderSeparate structure
Leaf contains actual row dataLeaf contains key + pointer
Only 1 per tableMany possible
Usually faster for direct row retrievalMay require extra lookup
Clustered:
B-Tree → Actual Row
          ↓
       DONE

Non-clustered:
B-Tree → Pointer → Table Row

Why only one clustered index?

Because rows can physically be ordered only one way.

Rows:
A → B → C → D

Cannot simultaneously store:

A → B → C → D
AND
D → B → A → C

Insert behavior

Sequential ID

[1][2][3][4][5]
             ↓
           insert 6
[1][2][3][4][5][6]

Usually efficient
Random UUID

[...][...][...][...]
       ↑
     insert

May need PAGE SPLIT
       ↓
Move existing rows
       ↓
More I/O + fragmentation

Good clustering key: generally stable + sequential/append-friendly.

Heap table

A table without clustered index is a heap.

Row → physical location

file 2
page 14
slot 3
   ↑
  RID

If the row physically moves, pointers may need updating.

Example: Holdings

If most queries are:

WHERE demat_account_id = ?

Prefer:

CLUSTER BY

(demat_account_id, holding_id)

instead of only:

holding_id

Because:

By holding_id:

h1  h2  h3  h4  h5
 ↑       ↑
same customer's holdings scattered


By demat_account_id:

Account A → h1 h5 h9
Account B → h2 h6
Account C → h3 h4

Remember: Cluster according to the dominant read pattern.

2. B-Tree Internals

Why B-Tree instead of Binary Search Tree?

The key problem is disk I/O.

Binary Search Tree

        [50]
       /    \
     [25]   [75]
      ...
      
1M rows → ~20 levels
→ potentially ~20 page reads
B-Tree

             [25 | 60]
           /     |      \
       [10|20] [35|47] [75|90]
       
1M rows → only ~3–4 levels
→ ~3–4 page reads

Main idea

CPU comparison = CHEAP
Disk page read  = EXPENSIVE

B-Tree:
More comparisons
       +
Fewer disk reads
       ↓
Much faster

B-Tree and ORDER BY

B-Tree leaves are already sorted.

[10,15]
   ↕
[20,25]
   ↕
[30,35]
   ↕
[40,45]

Query:

ORDER BY created_at

The database can:

Find starting point
       ↓
Walk through leaf pages
       ↓
Already sorted
       ↓
No separate SORT needed

Why does B-Tree remain balanced?

When a page becomes full:

FULL PAGE
   ↓
 SPLIT
 /   \
A     B
 \   /
Middle key → Parent

If parent also becomes full:

Child split
    ↓
Parent split
    ↓
Root may split
    ↓
Tree grows upward

All leaves remain at the same depth.

B-Tree vs Hash Index

For:

WHERE created_at
BETWEEN '2026-01-01'
AND '2026-01-31'

B-Tree

Find Jan 1
    ↓
[Jan 1] → [Jan 2] → [Jan 3] → ...
                         ↓
                    Stop at Jan 31

Excellent for range queries.

Hash

Jan 1 → Bucket 47
Jan 2 → Bucket 12
Jan 3 → Bucket 81

No ordering.

So:

B-Tree → equality + range + ordering
Hash   → mainly exact equality
3. Composite Index & Leftmost Prefix

Suppose:

INDEX(user_id, status, created_at)

Think of a phone book:

Last Name
   ↓
First Name
   ↓
Middle Name

The database can efficiently start searching from the left.

Query examples

QueryUsage
user_id = 5✅ Full
user_id = 5 AND status='ACTIVE'✅ Full
user_id=5 AND created_at > ...⚠️ Partial
status='ACTIVE'❌ Poor/no seek
user_id + status + created_at range✅ Ideal

Remember

INDEX(A, B, C)

A       → ✅
A + B   → ✅
A + B+C → ✅
A + C   → ⚠️ Partial
B       → ❌
C       → ❌

One index or two?

Queries:

1. WHERE status = ?
2. WHERE user_id = ? AND status = ?

Use:

INDEX(user_id, status)
        +
INDEX(status)

Because:

(user_id, status)
      ↑
must start here

The first index cannot efficiently serve:

WHERE status = ?
4. When Indexes Get Ignored

Having an index doesn't mean the database will use it.

Trap 1 — Function on indexed column

Bad:

WHERE YEAR(created_at) = 2026

Better:

WHERE created_at >= '2026-01-01'
AND created_at < '2027-01-01'
Function on column
      ↓
Compute for many rows
      ↓
Index loses usefulness

Trap 2 — Leading wildcard

Bad:

WHERE name LIKE '%esh'

Good:

WHERE name LIKE 'Rag%'

Why?

Index:

A...
B...
C...
Rag...
S...
T...
'Rag%'
   ↓
Can jump to Rag

'%esh'
   ↓
Could be anywhere

For suffix/contains searches, specialized indexes such as trigram/full-text may be appropriate.

Trap 3 — Type mismatch

Column:

account_no VARCHAR

Bad:

WHERE account_no = 12345

Better:

WHERE account_no = '12345'

Otherwise the database may need to convert the column, reducing index usability.

Trap 4 — Low cardinality

Example:

is_active

TRUE  → 70%
FALSE → 30%

Query:

WHERE is_active = TRUE

If 70% of rows match:

Index lookup
    ↓
70% of table
    ↓
Many table lookups

A full scan may actually be cheaper.

Trap 5 — Tiny table

200 rows
   ↓
Probably 1–2 pages
   ↓
Full scan = very cheap

Optimizer may correctly choose:

TABLE SCAN

even though an index exists.

Debugging sequence

When an indexed query is slow:

1. EXPLAIN ANALYZE
       ↓
2. Check 5 index traps
       ↓
3. Check statistics
       ↓
4. Check leftmost-prefix issue
       ↓
5. Consider covering / partial / other index

Key principle:

Index exists ≠ Index is useful.
5. Primary Key vs Unique Key

Think:

PRIMARY KEY = IDENTITY

UNIQUE KEY = BUSINESS RULE
Primary KeyUnique Key
Identifies the rowPrevents duplicate values
NOT NULLNULL behavior is engine-dependent
One per tableMultiple allowed
Common FK targetCan also be referenced
Often clustering keyUsually separate index

Example

users

user_id      → PRIMARY KEY
pan_number   → UNIQUE

During onboarding:

user_id = 101
pan_number = NULL

Later:

pan_number = ABCDE1234F

This works because PAN is a unique business property, not the row's identity.

6. Covering Index

Normal index:

INDEX(user_id)

Query:
SELECT status
FROM orders
WHERE user_id = 5

Flow:

Index
  ↓
user_id found
  ↓
Go to table
  ↓
Get status

Covering index:

INDEX(user_id)
INCLUDE(status)

Now:

Index
 ├── user_id
 └── status
       ↓
Answer directly
       ↓
No table lookup

This is an index-only scan.

KEY vs INCLUDE

KEY columns
    ↓
Determine sorting/search
    ↓
Leftmost prefix applies

INCLUDE columns
    ↓
Only stored at leaf
    ↓
Used for retrieval

Rule:

FILTER / SORT → KEY

SELECT only   → INCLUDE

Example

Query:

SELECT policy_number, premium_amount, status
FROM policies
WHERE demat_account_id = ?
AND status = 'ACTIVE';

Good index:

(demat_account_id, status)
INCLUDE (policy_number, premium_amount)

Why not cover everything?

Because:

More columns
    ↓
Larger index
    ↓
More storage
    ↓
More write work
    ↓
Higher INSERT/UPDATE/DELETE cost

Use covering indexes for important, hot queries.

7. Index on Foreign Keys

Suppose:

demat_accounts
       |
       | parent
       ↓
holdings
       |
       +-- demat_account_id

Delete:

DELETE FROM demat_accounts
WHERE id = 100;

Database must check:

"Does holdings contain rows for account 100?"

Without FK index

Delete parent
    ↓
Scan ALL holdings
    ↓
Check every row
    ↓
Locks may be held
    ↓
Concurrent operations blocked

With FK index

holdings(demat_account_id)
          ↓
Direct lookup
          ↓
Find matching rows quickly

Important engine difference

MySQL/InnoDB
    → FK index automatically created

PostgreSQL
    → NOT automatically created

SQL Server
    → NOT automatically created

So for PostgreSQL:

CREATE INDEX idx_holdings_demat_account_id
ON holdings(demat_account_id);

Important: FK constraint ≠ FK index.

8. NoSQL Index Landscape

Different databases treat indexes differently.

DatabaseImportant idea
MongoDBB-Tree, multikey, text, geospatial, TTL, wildcard
CassandraPartition key determines data placement
DynamoDBAccess patterns designed using PK/GSI/LSI
ElasticsearchDocuments indexed by default
RedisNo native general secondary index

MongoDB Multikey Index

Document:

{
  "tags": ["a", "b", "c"]
}

Index creates:

a → document
b → document
c → document

But two arrays are problematic:

tags   = [a,b,c]
colors = [x,y,z]

Possible combinations:

a-x
a-y
a-z
b-x
b-y
b-z
c-x
c-y
c-z

= 9 combinations

This Cartesian-product explosion is why MongoDB doesn't allow a compound multikey index across two array fields in this way.

9. Cassandra Secondary Index

SQL:

Index
  ↓
Directly find row

Cassandra:

Data distributed:

Node A
Node B
Node C

Secondary index on non-partition column
        ↓
Ask ALL nodes
        ↓
Scatter + Gather
        ↓
Expensive

This can defeat Cassandra's partitioning model.

Typical solution:

Design another table
around the required query
10. DynamoDB — LSI vs GSI

LSI

Same partition key, different sort key.

Base:

PK = user_id
SK = timestamp

LSI:

PK = user_id
SK = different attribute

Use when:

"Show me different views
of ONE user's data"

GSI

Different partition key.

Base:
PK = user_id

GSI:
PK = status
SK = timestamp

Use when:

"Search/group data using
a completely different key"

Easy rule

Same PK + different sort
        ↓
       LSI

New PK / new grouping
        ↓
       GSI

Example

Want:

All FAILED KYC events
across all users today

Base:

PK = user_id

LSI ❌ — still user-specific.

GSI ✅

GSI PK = status#date
GSI SK = timestamp

Be careful with hot partitions if many records share the same partition key.

11. What SQL Does Especially Well

UNIQUE guarantee

SQL:

WRITE
  ↓
Check UNIQUE index
  ↓
Write
  ↓
ONE ATOMIC TRANSACTION

So:

No duplicate gap

DynamoDB GSI:

Base write
    ↓
Async propagation
    ↓
GSI updated later

There can be a period where the GSI hasn't caught up.

Therefore: don't use an eventually consistent GSI as your uniqueness guarantee.

SQL JOIN

Orders
  |
  | user_id
  ↓
Users

SQL can efficiently use indexes to join related data at query time.

In distributed NoSQL:

Node A
Orders
  |
  | network call
  ↓
Node B
Users

Doing this repeatedly can become expensive.

Therefore NoSQL often prefers:

JOIN at WRITE TIME
        ↓
Denormalize
        ↓
Fast READ

Cassandra: new query = potentially new table

SQL:

Table
  +
New Index
  ↓
New query supported

Cassandra:

Existing partitioning
       ↓
Cannot efficiently answer
new query
       ↓
Create another table
       ↓
New partition strategy

Big mental shift

SQL:
Model data
   ↓
Add indexes for queries


NoSQL:
Know queries first
   ↓
Model data around queries
12. Why a Financial Ledger Usually Fits SQL Better

For a ledger:

Debit/Credit
     ↓
Must be exactly consistent
     ↓
Must not double-count
     ↓
Needs relationships
     ↓
Needs auditing

Strong ACID + joins are valuable.

Don't choose NoSQL simply because:

"Need scale"

Ask:

Do we really need
horizontal partitioning here?

OR

Can SQL + replicas + sharding
solve the scale problem?
13. What NoSQL Does Especially Well

MongoDB arrays

SQL:

Order
 |
 +-- order_items table
       |
       +-- item 1
       +-- item 2
       +-- item 3

MongoDB:

Order
 |
 +-- items: [item1, item2, item3]

Multikey index can index individual array elements.

Wildcard Index

MongoDB:

Document 1:
metadata.riskScore

Document 2:
metadata.sourceChannel

Document 3:
metadata.deviceType

Wildcard index:

metadata.$**
      ↓
Index whatever fields
appear under metadata

Useful when document fields are dynamic.

SQL doesn't work this way because:

SQL schema
    ↓
Columns defined first
    ↓
Index references known columns
14. Strong vs Eventual Consistency

Strong

Write
 ↓
Update index/replicas
 ↓
Confirm
 ↓
Return success

More consistency, potentially more coordination/latency.

Eventual

Write
 ↓
Return quickly
 ↓
Index catches up

Faster, but a read immediately afterward may temporarily see stale/missing data.

Good for:

Search
Recent activity feed
Non-critical views

Bad for:

Money
Balance
Uniqueness
Critical financial state

Final Mental Model

The most important idea across all 10 topics:

             DATABASE DESIGN
                    |
          +---------+---------+
          |                   |
        SQL                 NoSQL
          |                   |
   Data + indexes       Data placement
   are separate         = access pattern
          |                   |
   Add index later       Design query first
          |                   |
   Strong ACID           Scale/flexibility

One rule to remember

Every index is a BET on a QUERY PATTERN.

Before creating an index, ask:

        "What query am I optimizing?"
                    ↓
        How often is it executed?
                    ↓
        How selective is it?
                    ↓
        What are the write costs?
                    ↓
        Is this the right data model?

CTO-level takeaway:

Don't ask "SQL or NoSQL?" globally. Ask "What does this particular data need — consistency, query flexibility, scale, schema flexibility, or speed?" Then choose the storage and indexing strategy accordingly.
