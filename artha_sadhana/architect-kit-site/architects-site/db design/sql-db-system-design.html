SQL Database Internals — Easy Notes

1. SQL Database — Mental Model

Don't think:

App → Database → Result

Think:

App
 ↓
SQL Query
 ↓
Parser
 ↓
Optimizer
 ↓
Execution Engine
 ↓
Storage Engine
 ├── Tables
 ├── Indexes
 ├── Buffer Pool
 └── WAL

The core challenge is:

Correctness
     +
Performance
     +
Concurrency
     +
Crash Recovery

SQL vs Key-Value

Key-Value:
GET key
   ↓
Direct lookup


SQL:
SELECT ...
   ↓
Which index?
Which join?
Which order?
Which execution plan?

SQL allows:

  • Joins
  • Ranges
  • Aggregations
  • Arbitrary filters
  • Ad-hoc queries

Therefore SQL needs an optimizer + cost model.

2. Declarative SQL — Hidden Risk

SQL says WHAT you want:

SELECT * FROM orders
WHERE customer_id = 1001;

You don't explicitly say HOW to retrieve it.

The optimizer decides.

SQL
 ↓
Optimizer
 ↓
Execution Plan

Problem:

Same SQL
   ↓
Statistics change
   ↓
Optimizer chooses different plan
   ↓
Performance suddenly drops

So:

Same SQL does NOT guarantee the same performance.

Use:

EXPLAIN / EXPLAIN ANALYZE

to inspect important queries.

3. Constraints — Database as a Correctness Enforcer

Without constraints:

Application
    ↓
Must enforce everything
    ↓
Database simply stores data

With constraints:

Application
    ↓
Database
    ↓
Reject invalid state

Examples:

PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK

Think:

Constraint
    ↓
Declared invariant
    ↓
Database protects it

But business rules that aren't declared as constraints remain the application's responsibility.

CTO idea

Constraints decide where correctness is enforced.
4. Storage — Pages, Not Rows

Database doesn't normally read/write individual rows directly.

It works with pages.

Disk
 |
 +-- Page 101 → [Row][Row][Row]
 |
 +-- Page 102 → [Row][Row][Row]
 |
 +-- Page 103 → [Row][Row][Row]

Why?

Because disk/OS I/O is block-oriented.

Page
 ↓
I/O unit
 ↓
Caching unit
 ↓
Locking unit

Reading one tiny row at a time would be inefficient.

5. Heap vs Clustered Storage

Heap

Rows can be stored wherever space is available.

Page 1 → Customer A, Customer F
Page 2 → Customer B, Customer Z
Page 3 → Customer C

Problem:

Related rows
    ↓
Scattered across pages
    ↓
More random reads

Clustered

Rows are physically ordered.

Page 1 → ID 1, 2, 3
Page 2 → ID 4, 5, 6
Page 3 → ID 7, 8, 9

Better locality for the access pattern matching the clustering key.

6. Random UUID + Clustered Index

Bad combination:

Cluster key = Random UUID

Because inserts go randomly:

Existing:

[100][200][300][400]

New random UUID
       ↓
[100][200][NEW][300][400]
             ↓
         PAGE SPLIT

Repeated splits cause:

Page splits
    ↓
Fragmentation
    ↓
Write amplification
    ↓
Lower write performance

Better:

Monotonic ID

1 → 2 → 3 → 4 → 5 → 6
                      ↑
                   append

Or use a separate surrogate clustering key and keep UUID as a unique secondary key.

7. Clustered Storage Must Follow Access Patterns

Clustering isn't necessarily permanent.

Example:

Initially:

Most queries:
WHERE order_id = ?

Cluster by:

order_id

Later:

90% queries:
WHERE customer_id = ?
ORDER BY created_at

Now the original clustering may be wrong.

Changing it means:

Re-clustering
     ↓
Data migration
     ↓
Operational cost

Important: Physical design decisions eventually become migration decisions.

8. B+ Tree Index

Why B+ Tree?

Because:

Disk I/O = expensive
CPU comparison = cheap

B+ Tree keeps the tree shallow.

             [50]
           /      \
        [20]      [80]
        /  \      /  \
      ...  ...  ...  ...

Leaf nodes contain:

Keys → row locations

or sometimes actual row data depending on the storage model.

Why B+ Tree?

High fan-out
     ↓
Shallow tree
     ↓
Few page reads
     ↓
Fast

And leaf nodes are linked:

[10][20] ↔ [30][40] ↔ [50][60] ↔ [70][80]

Excellent for range queries.

9. Composite Index — Column Order Matters

Suppose:

INDEX(customer_id, created_at)

Data is ordered like:

customer 1001
   ├── Apr 1
   ├── Apr 2
   └── Apr 3

customer 1002
   ├── Apr 1
   └── Apr 2

Query:

WHERE customer_id = 1001
ORDER BY created_at

Very efficient.

But reverse it:

INDEX(created_at, customer_id)

Now the primary ordering is:

Apr 1 → many customers
Apr 2 → many customers
Apr 3 → many customers

So finding:

customer = 1001

is much harder.

Remember

INDEX(A, B)

A → excellent
A + B → excellent
B alone → usually poor
10. Covering Index

Normal index:

INDEX(department)

Query needs:

department
name
salary

Flow:

Index
 ↓
Find rows
 ↓
Go back to table
 ↓
Fetch name + salary

Covering index:

INDEX(department, name, salary)

Now:

Index
 ├── department
 ├── name
 └── salary
        ↓
   Answer directly

No table lookup.

But there's a cost

More index columns
       ↓
Larger index
       ↓
More storage
       +
More INSERT/UPDATE/DELETE work

Therefore:

Covering indexes are targeted optimizations, not something to use everywhere.
11. Can Adding an Index Make Things Worse?

Yes.

Suppose query returns:

70% of table

Optimizer may choose:

Index scan
 ↓
Many random table lookups

when:

Full table scan

would actually be cheaper.

Also:

More indexes
   ↓
More optimizer choices
   ↓
More opportunity for a bad plan

Stale statistics can make this worse.

12. Query Optimizer

The optimizer converts:

SQL
 ↓
Logical plan
 ↓
Optimizer
 ↓
Physical execution plan

For:

Customers JOIN Orders

Possible plans:

A → Nested Loop
B → Hash Join
C → Merge Join

Nested Loop

Good when:

One side is small
+
Other side has useful index

Hash Join

Good for:

Large
+
Unsorted datasets

Merge Join

Good when:

Both sides are already sorted

The optimizer chooses based on estimated cost.

13. Optimizer Statistics

Where does the optimizer get its information?

Table statistics
 ├── Row count
 ├── Value distribution
 └── Histograms

These are generally collected periodically.

Problem:

Bulk load
   ↓
Data changes significantly
   ↓
Statistics become stale
   ↓
Optimizer sees old reality
   ↓
Wrong plan

Example:

Yesterday:
10,000 rows → Index scan is good

Today:
10,000,000 rows → Same plan may be terrible

Therefore:

Query performance depends on data state, not just SQL text.
14. ACID
A → Atomicity
C → Consistency
I → Isolation
D → Durability

Atomicity

All or nothing.

BEGIN
 ↓
Debit A
 ↓
Credit B
 ↓
COMMIT

If failure:

ROLLBACK

Consistency

Database remains within declared rules.

Constraints
   ↓
Valid database state

Important:

ACID doesn't automatically know your business rules.

If you don't declare a business invariant, the application must enforce it.

Isolation

Concurrent transactions shouldn't corrupt each other's work.

Implemented using:

Locks
+
MVCC

Durability

Once committed, data should survive crashes.

Typical mechanism:

WAL
 ↓
fsync
 ↓
ACK commit
15. Why fsync Matters

Without fsync:

Application
   ↓
Database
   ↓
OS page cache
   ↓
ACK

Power failure:

OS cache lost
   ↓
"Committed" data disappears

With durable flush:

Write
 ↓
WAL
 ↓
fsync
 ↓
ACK

The guarantee is stronger.

16. ACID Does NOT Guarantee Business Correctness

This is a very important interview point.

Suppose:

Debit wrong account

but transaction executes:

Atomically
+
Durably
+
Correctly isolated

Database says:

SUCCESS

Business says:

WRONG!

Therefore:

ACID protects transaction mechanics, not business logic.
17. Long Transactions Are Dangerous

Even if individual queries are fast:

BEGIN
 ↓
Query
 ↓
External API call
 ↓
Wait 2 minutes
 ↓
Query
 ↓
COMMIT

The transaction remains open.

This can cause:

Locks held longer
+
MVCC versions retained
+
Cleanup delayed
+
Other transactions blocked

Keep transaction boundaries short.

18. MVCC

MVCC = Multi-Version Concurrency Control

Without MVCC:

Reader
 ↓
LOCK
 ↓
Writer waits

With MVCC:

Row
 ├── Old version
 └── New version

Reader → sees appropriate snapshot
Writer → creates new version

Therefore:

Readers don't block writers

But:

MVCC does NOT eliminate writer-vs-writer conflicts.

Two writers changing the same row still need:

Locks
or
Version checks
19. MVCC's Hidden Cost — Bloat

Old versions remain until no transaction needs them.

Old row versions
      ↓
Need cleanup
      ↓
Vacuum / Garbage collection

But:

Long-running transaction
       ↓
Old snapshot stays open
       ↓
Old versions cannot be cleaned
       ↓
Bloat
       ↓
Performance degradation

So long-running transactions are dangerous for MVCC systems too.

20. Deadlocks

Classic example:

Transaction 1          Transaction 2

Locks A                Locks B
  ↓                      ↓
Waits for B            Waits for A
  ↓                      ↓
       DEADLOCK

Is this a database bug?

No.

It's an expected possibility when transactions acquire locks in inconsistent order.

Database usually:

Detect deadlock
      ↓
Rollback one transaction
      ↓
Other transaction continues

Application-level solution:

Always acquire locks
in the SAME ORDER
21. Isolation Levels

Think of isolation as a scale:

Less isolation
     ↓
More throughput
     ↓
More anomalies possible

        VS

More isolation
     ↓
More correctness
     ↓
More overhead
LevelBasic behavior
Read UncommittedDirty reads possible
Read CommittedNo dirty reads
Repeatable ReadPrevents many repeated-read changes
SerializableBehaves as if transactions run one at a time

Why not Serializable everywhere?

Because:

More locking/conflict detection
        ↓
More transaction aborts
        ↓
Lower throughput

Read Committed is often the pragmatic default.

22. Read Committed Example

Transaction:

READ balance → ₹100
       ↓
Another transaction changes it
       ↓
READ balance → ₹50

Same transaction, different result.

Is database broken?

No.

Read Committed only guarantees:

You don't see uncommitted data.

It doesn't guarantee that the value remains unchanged throughout your transaction.

23. Lost Update

Example:

Initial balance = ₹100

Two transactions:

T1 reads ₹100
T2 reads ₹100

T1 calculates ₹80
T2 calculates ₹70

T1 writes ₹80
T2 writes ₹70

Final:

₹70

T1's update disappeared.

Possible solutions:

Serializable
OR
Repeatable Read
OR
SELECT ... FOR UPDATE
24. Isolation Should Be a Per-Transaction Decision

Don't assume:

Entire DB = Serializable

Instead:

Dashboard
 → Read Committed

Normal API
 → Read Committed

Financial ledger
 → Serializable + row locks

Choose based on the business risk.

25. WAL — Write-Ahead Log

WAL is the backbone of durability.

Typical flow:

UPDATE
  ↓
WAL
  ↓
ACK
  ↓
Data page flushed later

Why?

Because sequential WAL writes are cheaper than random data-page writes.

WAL
████████████████→
Sequential write


Data pages
↘ ↑ ↗ ↓ ↘ ↑
Random writes
26. WAL vs Data Pages

Important:

A transaction can be committed even though the actual data page isn't yet updated on disk.

Example:

WAL → DURABLE
Data page → still in memory

Later:

Buffer Manager
     ↓
Flush data page

If crash occurs:

Data page old
     +
WAL contains change
     ↓
Recovery reconstructs change
27. Buffer Pool

Database keeps frequently used pages in memory.

Disk
  ↕
Buffer Pool
  ↕
Query Execution

Cache hit

Page already in memory
        ↓
Use directly
        ↓
Fast

Cache miss

Page not in memory
        ↓
Read from disk
        ↓
Slower
28. Buffer Pool Eviction

When memory is full:

New page needed
      ↓
Which old page should leave?
      ↓
Eviction policy

Often based on LRU-like strategies.

But naive LRU can have a problem:

Huge sequential scan
       ↓
Touches many pages once
       ↓
Pushes hot pages out
       ↓
Important workload becomes slower

Modern engines use smarter policies.

Bigger buffer pool?

Not always automatically better.

Working set fits
      ↓
More memory helps

Working set already fits
      ↓
Extra memory gives diminishing benefit
29. Crash Recovery

Why checkpoints?

WAL
──────────────────────────────>

Checkpoint
      ↑
Known-good point

Recovery:

Crash
 ↓
Read checkpoint
 ↓
Redo required WAL
 ↓
Undo incomplete transactions
 ↓
Consistent database

Without checkpoints:

Replay WAL from beginning
       ↓
Recovery gets slower and slower
30. REDO + UNDO

Why both?

Because WAL may contain:

Committed transactions
+
Uncommitted transactions

Recovery:

REDO
 ↓
Bring logged changes forward
 ↓
UNDO
 ↓
Remove incomplete transactions

Final state:

Only committed work remains
31. Client Timeout After Crash

Suppose:

Transaction
   ↓
COMMIT
   ↓
Client connection drops

Client doesn't know:

Did it commit?
or
Did it fail?

Important rule:

Timeout means UNKNOWN, not automatically FAILED.

After reconnecting:

Check actual state
        +
Check idempotency key

Then determine whether the transaction committed.

32. Checkpoint Frequency

Frequent checkpoints:

More I/O during normal operation
        ↓
Faster recovery

Infrequent checkpoints:

Less normal I/O
        ↓
More WAL to replay
        ↓
Longer recovery

So:

Checkpoint frequency
       =
Steady-state performance
       vs
Recovery time
33. Replication

Typical SQL architecture:

             PRIMARY
            /       \
           ↓         ↓
      Replica 1   Replica 2

Primary handles writes.

Replicas can serve reads.

Replication often works by shipping:

WAL / binlog
     ↓
Replica replays it
34. Async Replication

Problem:

Client
  ↓
Primary → WRITE
  ↓
ACK
  ↓
Replica hasn't caught up

Then:

Client
  ↓
Replica → READ
  ↓
OLD DATA

This creates the classic:

"I just updated it, but I still see the old value."

This is replication lag.

35. Synchronous Replication

With synchronous replication:

Client
 ↓
Primary
 ↓
Replica confirms
 ↓
ACK

Better freshness/durability.

But:

Replica slow
    ↓
Primary waits
    ↓
Write latency increases

If replica is unavailable:

Writes may stop

Therefore:

Async
 → faster, more available, possible stale reads

Sync
 → stronger guarantee, more latency/availability cost
36. Sharding

Sharding distributes data across multiple databases/nodes.

Example:

Customer 1–10000
       ↓
Shard A

Customer 10001–20000
       ↓
Shard B

Benefit:

More data
+
More write capacity
+
More horizontal scale

But:

Cross-shard JOIN
        ↓
Fan-out
        ↓
Multiple shards
        ↓
Merge results

Much more complex.

37. Shard Key Is a Critical Decision

Once data is distributed:

Shard key
    ↓
Data location
    ↓
Query performance

Changing it later means:

Re-sharding
    ↓
Move live data
    ↓
Keep application online
    ↓
High operational complexity

Therefore:

A shard key is one of the most expensive decisions to change later.
38. Scaling Trade-Off

The bigger picture:

Single DB
   ↓
Simple joins
Simple transactions
Simple consistency
   ↓
        SHARD
          ↓
Distributed complexity
          ↓
Cross-shard queries
Partial failures
Data movement
Consistency challenges

So don't ask only:

"Can we scale?"

Ask:

"What guarantees and simplicity are we giving up to scale?"

The source describes a deliberately different configuration for different workloads:

                    Database
                       |
       +---------------+----------------+
       |               |                |
   MF Orders        LAMF Ledger      Reporting
       |               |                |
 Read Committed   Serializable      Read Replica

10 Questions to Ask as an Architect

1. How is the data physically stored?

2. What is the page layout?

3. Which index supports the dominant query?

4. Is the composite index column order correct?

5. What execution plan will the optimizer choose?

6. What statistics is that decision based on?

7. What isolation level does this transaction actually need?

8. When exactly is the write considered durable?

9. What happens if the database crashes mid-transaction?

10. What happens when we scale to replicas/shards?

One final CTO takeaway

Application sees:
        ROW

Database sees:
        PAGE
         ↓

         ↓

The database is not a black box. Every guarantee you receive — performance, consistency, durability, recovery — is backed by a specific mechanism and a specific cost.

The architect's job is to understand what mechanism provides the guarantee, what it costs, and whether the business actually needs that guarantee.
