2. Capacity Estimation

Before adding infrastructure, estimate the workload.

Average RPS
= 100M / 86,400
≈ 1,157 RPS

Assume peak is 10× average:
Peak RPS ≈ 11,570

Capacity estimates give quantitative justification for architectural decisions.

4. Vertical Scaling

Small Server
     |
     v
Bigger Server
     |
     v
Even Bigger Server

Increase CPU, RAM, disk, or network capacity.

Advantages

  • Simple
  • No application changes
  • No distributed coordination
  • Easy operational model

Problems

  • Hardware ceiling
  • Increasing cost
  • Still one failure domain
  • Scaling is not instantaneous
  • Cannot provide unlimited capacity
Key lesson: Vertical scaling buys time; horizontal scaling changes the scalability model.

9. Sticky Sessions vs Stateless Servers

Sticky sessions keep a user attached to one server, but create uneven load and make failures disruptive.

10. What Does Stateless Mean?

19. Cache-Aside Pattern

value = cache.get(key)

if value exists:
    return value

value = database.get(key)

cache.set(key, value)

return value

The application explicitly reads the cache first and populates it after a miss.

20. Cache Invalidation

DB:
Balance = ₹10,000

Cache:
Balance = ₹10,000

DB updated → ₹8,000
Cache → ₹10,000

Common strategies: TTL, explicit invalidation, write-through, and write-behind. The correct choice depends on consistency and durability requirements.

Mitigations include TTL jitter, request coalescing, locks, rate limiting, circuit breakers, cache warming, and graceful degradation.

22. Cache Eviction

  • LRU: Least Recently Used
  • LFU: Least Frequently Used
  • FIFO: First In First Out

Eviction policies determine which entries leave when cache capacity is exhausted.

23. What Should Be Cached?

Good candidates are frequently read, rarely changed, or expensive to calculate.

  • Product catalog
  • User preferences
  • Configuration
  • Popular content
  • Reference data

Be careful with highly sensitive, frequently changing, or strongly consistent financial state unless the consistency model is explicitly designed.

24. Cache vs Database

Database
    ↓
System of Record

Cache
    ↓
Performance Optimization

The cache normally serves performance; the database remains the authoritative source unless the architecture explicitly defines otherwise.

25. Stage 6 — Database Sharding

                    Application
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
          Shard-1     Shard-2     Shard-3
          Users       Users       Users
          1-1M        1M-2M       2M-3M

Sharding horizontally partitions data across multiple database instances.

26. Sharding Key

hash(user_id) % 4

User 101 → Shard 1
User 102 → Shard 3
User 103 → Shard 0
User 104 → Shard 2

The shard key determines where a record lives and how requests are routed.

27. Range-Based Sharding

Shard 1: user_id 1 - 1M
Shard 2: user_id 1M - 2M
Shard 3: user_id 2M - 3M

Range sharding is simple but can create hotspots when new or popular data concentrates in one range.

28. Hash Sharding

hash(user_id)
      |
      v
+-----+-----+-----+-----+
| S0  | S1  | S2  | S3  |
+-----+-----+-----+-----+

Hashing generally distributes records more evenly, but changing shard count can cause substantial data movement.

29. Consistent Hashing

             Consistent Hash Ring

                 S1
              /      \
           S4          S2
              \      /
                 S3

Consistent hashing reduces the amount of data that must move when nodes are added or removed. It is particularly important in distributed caches and some distributed data systems.

30. Sharding Problems

  • Cross-shard queries
  • Cross-shard transactions
  • Rebalancing
  • Hot shards
  • Operational complexity
Transaction
   |
   +---- Shard 1
   |
   +---- Shard 2

Distributed transactions are significantly harder than a transaction within one database.

31. Choosing a Good Shard Key

A good shard key should provide:

  • High cardinality
  • Good distribution
  • Predictable routing
  • Minimal cross-shard queries
  • Minimal hotspots

Common candidates include user_id, account_id, or tenant_id depending on the workload.

39. Stage 8 — Microservices

                 API Gateway

       |             |             |

   User Service  Order Service  Payment Service
       |             |             |
       v             v             v

Microservices decompose a large application into independently deployable services aligned with business/domain boundaries.

40. Why Microservices?

  • Independent scaling
  • Independent deployment
  • Team autonomy
  • Fault isolation
  • Technology independence
  • Domain boundaries

For example, a payment service processing 10K TPS may need very different scaling characteristics from a notification service processing 100 TPS.

41. Microservices Are Not Automatically Better

Service A
   |
   | network
   v
Service B
   |
   | network
   v
Service C

Microservices introduce network calls, distributed tracing, service discovery, retries, timeouts, partial failures, consistency problems, deployment complexity, and operational overhead.

Architectural rule: A modular monolith may be the better choice when service boundaries and operational scale do not justify distributed complexity.

48. Retries Are Dangerous

Payment request
     |
     v
Payment service
     |
     | timeout
     v
Client retries

The original operation may have succeeded even though the response timed out.

Attempt 1 → ₹1,000 charged
Attempt 2 → ₹1,000 charged again

Critical operations therefore require idempotency.

49. Idempotency

Idempotency-Key: ABC123

ABC123 → Payment Result

If the same request arrives again with the same key, return the previously recorded result rather than executing the business operation twice.

Especially important for payments, orders, money transfers, bookings, and other financial transactions.

Europe → Europe DB

65. CAP Theorem

          Network Partition
                 |
       +---------+---------+
       |                   |
Consistency           Availability

CAP is specifically about behavior during a network partition: a distributed system cannot simultaneously guarantee both strong consistency and availability under the partition while also tolerating the partition.

66. Strong vs Eventual Consistency

Strong consistency

WRITE
  |
  v
Read immediately
  |
  v
Latest committed value

Eventual consistency

WRITE
  |
  v
Some replicas updated
  |
  v
Temporary stale reads
  |
  v
Eventually converge

Eventual consistency can be appropriate for social likes, search indexing, analytics, recommendations, and similar workloads. Strong consistency is generally more important for account balances, money transfers, inventory reservations, and other critical financial state.
