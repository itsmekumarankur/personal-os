System Design: Requirements

Requirements are the foundation of good system design.

Golden Rule:
Do not start with Kafka, Redis, databases or microservices. Start with requirements.

5. Scope

›

Do not try to design the entire product.

REQUIREMENTS
     |
     +--> MUST HAVE
     |
     +--> NICE TO HAVE
     |
     +--> OUT OF SCOPE

Example: Messaging

Must: Send, Receive, History

Nice: Typing indicator, Read receipt, Reactions

Out: Video calling, Voice calling

7. Non-Functional Requirements

›
How well should the system work?
ScalabilityPerformanceAvailabilityReliabilityDurabilityConsistencySecurityMaintainabilityObservabilityCost

NFRs describe system qualities and constraints rather than features.

8. Quantify Everything

›

Avoid vague statements.

"System should be fast"
"System should scale"
"Highly available"

Instead:

Users        = 10M
Messages     = 100M/day
Latency      = p95 < 200ms
Availability = 99.99%
RPO          = 0
Senior architects convert adjectives into measurable targets.

10. Capacity Estimation

›

Example: 10 million messages/day.

10,000,000
-----------
  86,400

≈ 116 messages/sec

Then estimate peak traffic.

Average = 116/sec

Peak = Average × Peak Factor

If peak factor = 10

Peak ≈ 1,160/sec

Then ask: servers, DB writes, queue partitions, storage, bandwidth.

11. Performance

›

Performance is not just average latency.

p50 < 50ms
p95 < 200ms
p99 < 500ms
99 users → 20ms
1 user   → 10 seconds

Average can hide the problem.
p99 exposes it.
Tail latency matters.

14. Durability

›
Once data is successfully written, can we lose it?
WRITE
  |
  v
DURABLE STORAGE
  |
  +--> Replication
  +--> Backup
  +--> Persistence
  +--> Recovery

RPO

Recovery Point Objective: Maximum acceptable data loss.

RPO = 5 minutes
→ Potentially lose up to 5 minutes of data

For financial transactions, the target may be close to zero data loss.

15. RTO

›

Recovery Time Objective: How quickly must the system recover?

System Failure
      |
      v
    10 min
      |
      v
System Restored

RTO = 10 min
Remember:
RPO → How much data can I lose?
RTO → How much time can I be down?

Quick Revision — 25 Points

›
  1. Start with requirements, not technology.
  2. Functional requirements = WHAT the system does.
  3. Identify all important actors.
  4. Understand user journeys.
  5. Clearly define scope.
  6. Translate core functions into APIs.
  7. NFRs = HOW WELL the system works.
  8. Quantify NFRs wherever possible.
  9. Understand scalability dimensions.
  10. Estimate average and peak capacity.
  11. Use latency percentiles such as p95/p99.
  12. Define availability targets.
  13. Understand availability vs reliability.
  14. Define durability and RPO.
  15. Define recovery time using RTO.
  16. Choose an appropriate consistency model.
  17. Understand consistency trade-offs.
  18. Design explicitly for failures.
  19. Use idempotency for retryable operations.
  20. Design for maintainability.
  21. Build security into the architecture.
  22. Make the system observable.
  23. Consider infrastructure/business cost.
  24. Map requirements directly to architecture.
  25. Choose technology only after requirements, constraints, trade-offs and patterns are clear.
