Fundamentals How Websites Work — The Client/Server/Network Model
▸ 
Client (browser) ──request──▶ Network (routers, switches) ──▶ Server
Client (browser) ◀──response── Network ◀── Server

Analogy: writing a letter
  You (client) → post office network → recipient (server)
  Recipient replies using the return address you wrote →
  same network → back to you

Both client and server need IP addresses to find each other — the same way a letter needs a destination address and a return address for the correspondence to work both ways.

Active Recall: In the letter analogy, what maps to an IP address? tap to reveal
The address written on the envelope — both the destination address (equivalent to the server's IP) and the return address (equivalent to the client's IP), which lets the recipient know how to send a reply back.
Fundamentals What's Actually Inside a Server — The "Brain" Analogy
▸
ComponentRoleHuman Analogy
CPUPerforms computationsThe reasoning part of the brain
RAM (Memory)Very fast, short-term storage for active workWorking/short-term memory
StorageLong-term data persistence (files)Long-term memory
DatabaseStructured, queryable/searchable dataAn organized filing system

CPU + RAM together are framed as "the brain" — compute plus fast working memory. Storage and databases are the longer-term memory layer. Networking is what lets all of this actually communicate with the outside world. This five-part decomposition (compute, memory, storage, database, networking) is exactly what the cloud is going to offer "on demand" throughout the rest of this course.

Active Recall: Why are CPU and RAM described together as "the brain," while storage/database are described separately? tap to reveal
CPU (computation) and RAM (very fast, immediately accessible memory) together mirror how a brain actively thinks and holds information in the moment — analogous to short-term, working cognition. Storage and databases represent longer-term, persistent memory that isn't necessarily loaded for active use at any given instant, a distinct role from the fast, active compute+memory pairing.
History The Garage-to-Data-Center Story — And Its Real Pain Points
▸

The classic narrative: startups (Google being the famous example) began with literal physical servers in a garage or home, then graduated to a dedicated data center room as they grew. This worked for years but had five compounding problems:

  • Fixed costs regardless of usage — rent, power, cooling, maintenance
  • Slow to scale — ordering and physically installing new hardware takes real time
  • Scaling is capped by physical space and budget, not just demand
  • Requires a 24/7 human team just to monitor infrastructure
  • Single point of physical failure — earthquake, fire, power outage can take everything down at once

Architect's Lens

This "garage to data center" story is a useful narrative hook, but the more interesting exam-relevant insight buried in it is the shift from CapEx to OpEx (covered explicitly later in this section) — every one of these five pain points is really a symptom of committing large capital expenditure ahead of actual, measured demand. That reframing — "the cloud isn't just 'someone else's computer,' it's a mechanism for converting unpredictable capacity planning into pay-as-you-go operating cost" — is the single most testable idea in this entire section.

Active Recall: What's the common thread underlying all five traditional data-center pain points listed here? tap to reveal
They all stem from having to commit fixed capital and physical resources upfront, ahead of and independent of actual real-time demand — rent, power, hardware purchases, staffing, and disaster exposure are all consequences of owning and operating physical infrastructure yourself, rather than consuming capacity elastically as needed.
Exam Term Cloud Computing — The Precise Definition
▸

"Cloud computing is the on-demand delivery of compute power, database storage, application, and other IT resources through a cloud service platform via pay-as-you-go pricing."

The two load-bearing words: on-demand (get exactly what you need, when you need it, instantly — not with a 24-hour or multi-week procurement lead time) and pay-as-you-go (you pay only for what you actually consume, and stop paying the moment you stop using it).

Familiar consumer cloud services used as everyday analogies: Gmail (email as a cloud service — you only "provision" storage implicitly by using it), Dropbox (cloud storage — notably, originally built on top of AWS itself), and Netflix (video-on-demand, entirely built on AWS infrastructure).

Active Recall: What are the two defining characteristics in the formal definition of cloud computing given here? tap to reveal
On-demand delivery (resources are available instantly, without advance provisioning or lead time) and pay-as-you-go pricing (you only pay for exactly what you use, for exactly as long as you use it).

Architect's Lens

Hybrid cloud is worth pausing on given your regulated-fintech background — this is precisely the model many banks actually run in practice: core banking, ledgers, and sensitive customer data often stay on-premises or in a private cloud for compliance/data-residency reasons, while less sensitive workloads (analytics, dev/test environments, customer-facing web tiers) extend into the public cloud for elasticity and cost efficiency. Worth checking whether IDFC's current architecture is explicitly framed this way internally, or whether that's implicit and unstated.

Active Recall: What's the core trade-off hybrid cloud is designed to solve? tap to reveal
It balances the need for control and security over sensitive assets (kept on private/on-premises infrastructure) against the flexibility and cost-effectiveness of the public cloud (used for everything else) — rather than forcing an all-or-nothing choice between the two.
Exam Term Five Characteristics + Six Advantages of Cloud Computing
▸

Five characteristics (what defines cloud computing):

  1. On-demand self-service — provision resources without human intervention from the provider
  2. Broad network access — resources reachable over the network, in diverse ways
  3. Multi-tenancy and resource pooling — shared physical infrastructure across customers, with isolation/privacy
  4. Rapid elasticity and scalability — quickly acquire and release resources as demand changes
  5. Measured service — usage is metered, and billing matches exactly what was consumed

Six advantages (why it's worth adopting):

  1. Trade CapEx for OpEx — rent instead of buy, reducing Total Cost of Ownership (TCO)
  2. Massive economies of scale — AWS's own efficiency at scale lowers prices over time for everyone
  3. Stop guessing capacity — scale to actual measured usage instead of forecasted-and-often-wrong estimates
  4. Increased speed and agility — no procurement blockers, build and iterate immediately
  5. Stop spending on running/maintaining data centers — eliminates that entire operational burden
  6. Go global in minutes — a small team can deploy a worldwide application leveraging AWS's existing global infrastructure

Exam Note

"Elasticity" and "scalability" are often used together but are technically distinct: scalability is the ability to grow (add resources) to meet demand; elasticity specifically implies the ability to both scale out and scale back in automatically, matching resources closely to real-time demand in both directions. The exam may test this exact distinction.

Active Recall: What's the precise difference between "scalability" and "elasticity" as distinct terms? tap to reveal
Scalability is the general ability to increase resources to handle growing demand. Elasticity specifically means the ability to automatically both scale OUT (add resources) and scale IN (remove resources) as demand rises and falls, keeping resource usage closely matched to actual real-time need in both directions — not just growth.

Architect's Lens

Your Day 5 App Runner deployment from the Vercel course actually sits closer to PaaS territory for the deployment/runtime layer (App Runner manages the container orchestration, scaling, and networking), even though you were using an IaaS-style building block (a Docker container) as the unit of deployment — a good concrete example of how these categories blur in practice rather than being perfectly clean boxes. Worth having your own deployment on hand as a working example if this distinction comes up in an interview: "I used EC2-adjacent IaaS building blocks through a PaaS-like managed deployment service."

Active Recall: In the PaaS model, what is the customer still responsible for, and what does the provider take over compared to IaaS? tap to reveal
In PaaS, the customer is only responsible for their application and data. The provider takes over everything else — runtime, middleware, OS, virtualization, servers, storage, and networking — whereas in IaaS the customer still had to manage the application, data, runtime, middleware, and OS themselves.
Exam Term AWS Pricing Fundamentals — Three Pillars
▸
ResourceHow You're Charged
ComputePay for exact compute time used
StoragePay for the exact amount of data stored
Networking (data transfer)Only charged when data LEAVES the cloud (egress) — data going IN is free

Exam Note

The data-in-free / data-out-charged asymmetry is a frequently tested detail and directly explains real cost-governance behavior — it's exactly why moving large volumes of data OUT of AWS (e.g. to another cloud, or back on-premises) can become a surprisingly significant cost line item, while ingesting data is essentially free. This is directly relevant if you ever need to reason about egress costs for a multi-cloud or hybrid architecture.

Active Recall: Which direction of data transfer is free on AWS, and which is charged? tap to reveal
Data transferred INTO AWS (ingress) is free. Data transferred OUT of AWS (egress — leaving the cloud) is what you're charged for.

Exam Term Global Infrastructure — Regions, Availability Zones, Edge Locations
▸ 
Region (e.g. ap-southeast-2, "Sydney")
  = a cluster of data centers in one geographic area
  = most AWS services are SCOPED to a region — using a
    service in one region is independent of using it in
    another (separate resources, separate configuration)

  └── Availability Zone (e.g. ap-southeast-2A, 2B, 2C)
        = usually 3 per region (min 3, max 6)
        = one or more DISCRETE data centers with redundant
          power, networking, and connectivity
        = ISOLATED from each other — a disaster in one AZ
          is designed NOT to cascade into another
        = connected to other AZs in the same region via
          high-bandwidth, ultra-low-latency private networking

Points of Presence / Edge Locations
  = 400+ locations across 90 cities in 40+ countries
  = used for delivering content to end users with the
    lowest possible latency (e.g. via CloudFront)

Exam Note — Choosing a Region: 4 Factors

  1. Compliance — some jurisdictions require data to stay within the country (data residency)
  2. Latency — deploy close to your actual user base to minimize lag
  3. Service availability — not every AWS service exists in every region; check the regional services table before committing
  4. Pricing — costs vary by region; check the specific service's pricing page

Architect's Lens

The compliance/data-residency factor is directly relevant to a regulated Indian financial institution — RBI data localization requirements for payment and financial data are exactly the kind of "compliance forces a specific region" scenario this section describes abstractly. Worth treating this exam concept as already-lived experience rather than new theory: you've almost certainly made exactly this kind of region-selection decision (or seen it made) at IDFC for regulatory reasons.

Active Recall: Why are Availability Zones within a region deliberately kept isolated from each other, and how are they still connected? tap to reveal
They're isolated (separate discrete data centers with independent power/networking) specifically so a disaster affecting one AZ — power outage, fire, etc. — doesn't cascade and take down the others, giving fault tolerance within a region. Despite this isolation, they're still connected to each other via high-bandwidth, ultra-low-latency private networking, which is what lets applications span multiple AZs for high availability while staying fast.
Console Global vs. Regional Services — A Practical Distinction
▸

Most AWS services are region-scoped (EC2, Elastic Beanstalk, Lambda, Rekognition — switching regions in the console gives you a genuinely different, separate view of your resources). A smaller set are global services — IAM, Route 53, CloudFront, and WAF — where the console shows the same view regardless of which region selector is active, since these services aren't tied to a single region at all.

Active Recall: Name two AWS services explicitly called out as "global" rather than region-scoped, and what does that mean practically in the console? tap to reveal
IAM and Route 53 (also CloudFront and WAF). Practically, this means the console for these services shows the exact same view no matter which region you have selected in the region selector — unlike region-scoped services like EC2, where switching regions shows an entirely different set of resources.
Setup Account Creation — Practical Details Worth Remembering
▸
  • Root user email + account name required, followed by email verification and a password meeting complexity requirements (8+ characters, at least 3 of: uppercase, lowercase, numbers, non-alphanumeric)
  • Choice between Free and Paid account plans — both start with credits (~$100, up to $200 total in the example given). Free plan requires no credit card and auto-closes if credits run out; Paid plan requires a card and bills beyond the credit
  • A credit card is still required even on the free plan — purely for identity verification / fraud prevention, with a refundable $1 verification charge, not an ongoing billing commitment
  • Phone number verification and a Support Plan choice (Basic/free is fine to start) are also required
Active Recall: Why does AWS require a credit card even for accounts on the free plan? tap to reveal
Purely for identity verification and fraud prevention — not for billing. A small refundable charge (around $1) is used to verify the card is real, but the free plan itself won't incur ongoing charges from that card unless the account is later upgraded to a paid plan.
Exam Term The Shared Responsibility Model — Frequently Tested
▸
Customer's Responsibility ("Security IN the cloud")AWS's Responsibility ("Security OF the cloud")
Your dataAll physical infrastructure
Your operating system configurationAll hardware
Network and firewall configurationAll underlying software (virtualization layer)
How you configure whatever services you useTheir own internal security practices

Explicitly flagged as heavily tested on the exam — questions typically present a scenario and ask you to identify whether a specific failure or misconfiguration falls under the customer's or AWS's side of the line.

Architect's Lens

This model isn't exam trivia — it's the exact framework that determines liability and audit scope in any real cloud security incident. "Security IN the cloud vs. OF the cloud" is the same distinction your own security/compliance teams at IDFC would apply when scoping a penetration test or an audit against a cloud-hosted service: AWS's physical/hypervisor security isn't your concern or your audit surface, but anything you configured — IAM policies, security groups, data encryption settings — is entirely yours to answer for.

Active Recall: If a data breach happens because a customer left an S3 bucket publicly accessible by mistake, whose responsibility is that under the Shared Responsibility Model? tap to reveal
The customer's — bucket access configuration is a "security IN the cloud" concern, which is entirely the customer's responsibility. AWS is responsible for the underlying security of the S3 service infrastructure itself, but not for how the customer configures access permissions on their own resources.
