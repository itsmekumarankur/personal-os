Fine-Tuning & Customization

If a model can already follow instructions reasonably well, what exactly are you buying when you fine-tune it — and is it ever the wrong purchase?

§ 01 — FIRST PRINCIPLES
Thought experiment

A general-purpose model can already write reasonably fluent text, follow instructions, and reason about most topics. If you can already just tell it what you want in the prompt, what is fine-tuning actually changing that a well-written prompt cannot?

What fine-tuning buys you that prompting can't

Prompting steers a fixed set of weights toward a desired behavior at inference time — every instruction, every example, every constraint has to be re-stated (and re-paid-for, in tokens) on every single call. Fine-tuning instead updates the model's weights themselves, so the desired behavior becomes baked into the model's default response pattern, without needing to be re-explained each time.

This distinction matters most along a few axes:

  • Consistency at scale — a fine-tuned model produces the target style/format reliably without depending on a long, carefully-worded system prompt surviving every edge case.
  • Token/cost efficiency — instructions and even few-shot examples baked into weights don't consume prompt tokens on every call, which matters enormously at high request volume.
  • Learning patterns too subtle for prompting — some behaviors (a very specific tone, a domain-specific reasoning pattern, a structured output format used thousands of times) are easier to demonstrate through hundreds of examples than to describe in words.
  • Latent knowledge the prompt can't reach — fine-tuning can shift how a model uses what it already knows, though it's a poor tool for teaching genuinely new facts (more on this in §08 — that's RAG's job).
The framing to hold onto through this whole note Fine-tuning changes behavior (how the model responds — tone, format, task-specific skill). It is a weak, expensive tool for changing knowledge (what facts the model has access to). Keep that distinction in mind — it's the backbone of §08's decision framework.
§ 02 — FULL FINE-TUNING
Thought experiment

A 70-billion-parameter model has 70 billion numbers that could, in principle, all be nudged during training. If your fine-tuning dataset only meaningfully touches on a narrow skill — say, generating a specific JSON schema — does updating all 70 billion parameters make sense, or is that solving a small problem with a wildly oversized tool?

Full fine-tuning — the original, expensive approach

Full fine-tuning updates every parameter in the model via standard backpropagation on your custom dataset, exactly like the original pretraining process, just on a smaller, task-specific dataset with typically much lower learning rates to avoid destroying pretrained capability.

Why it's expensive — and where the cost actually comes from

  • Optimizer state — training doesn't just need memory for the model weights; optimizers like Adam store additional state (momentum, variance estimates) per parameter, typically doubling or tripling the memory footprint beyond the raw weight size.
  • Gradients — a full gradient tensor, the same size as the weights, must be held in memory for every parameter being updated.
  • Activation memory — intermediate activations from the forward pass need to be retained for backpropagation, scaling with sequence length and batch size.
  • Multi-GPU orchestration — for anything beyond small models, full fine-tuning requires distributed training (data/tensor/pipeline parallelism), adding real systems-engineering complexity on top of the raw compute cost.
   MEMORY FOOTPRINT — WHY FULL FINE-TUNING IS SO EXPENSIVE

   For a 7B parameter model, fp16 training (rough order of magnitude):

   ┌─────────────────────────┬───────────────┐
   │ Model weights (fp16)    │   ~14 GB       │
   │ Gradients (fp16)        │   ~14 GB       │
   │ Optimizer state (Adam)  │   ~56 GB       │  ◀── the dominant cost
   │ Activations             │   varies (GBs) │
   ├─────────────────────────┼───────────────┤
   │ TOTAL                   │   ~85GB+       │  → needs multiple high-end GPUs
   └─────────────────────────┴───────────────┘

   Compare to LoRA (§03): only a small fraction of parameters need
   gradients + optimizer state at all → fits on a single GPU
The optimizer state, not the raw weights, is usually the single biggest memory cost in full fine-tuning — this is exactly the line item PEFT methods attack.

When full fine-tuning still makes sense

Despite the cost, full fine-tuning remains the right choice when: the target behavior requires substantial capability shift (not just style/format adaptation), you have a very large, high-quality dataset that justifies the investment, or you're building a foundation model / doing continued pretraining rather than task adaptation. For most applied, task-specific customization work, though, this is now the exception rather than the default — which is exactly why parameter-efficient methods emerged.

§ 03 — LoRA
Thought experiment

Research on fine-tuned models has repeatedly observed that the actual change a fine-tuning process makes to a weight matrix tends to have low "intrinsic rank" — meaning the update, despite being the same size as the full matrix, can be well-approximated by a much smaller, low-rank structure. If that's true, why train a full-size update at all?

LoRA — Low-Rank Adaptation

LoRA freezes the entire pretrained model and, for selected weight matrices (commonly the attention projection matrices), injects a pair of small, trainable low-rank matrices alongside the frozen original. Instead of learning a full-size weight update ΔW, LoRA learns ΔW as the product of two much smaller matrices, A and B, where the "rank" r is a small number (often 4-64) compared to the matrix's full dimensions.

   HOW LoRA MODIFIES A WEIGHT MATRIX

   Original weight matrix W (frozen, untouched):    d × d,  e.g. 4096 × 4096
                                                      ≈ 16.7M parameters

   LoRA adds:  ΔW = B × A        where
      A is  r × d     (e.g.  8 × 4096  = 32,768 params)
      B is  d × r     (e.g.  4096 × 8  = 32,768 params)
                                                      ≈ 65K trainable params

   Effective weight at inference:  W_new = W (frozen) + B·A (trained)

   → ~99.6% fewer trainable parameters for this matrix, in this example
The rank r is the key hyperparameter: higher rank = more expressive capacity to learn, but more trainable parameters and higher risk of overfitting on small datasets.

Why this works so well in practice

  • Drastically less memory — only A and B need gradients and optimizer state; the frozen base weights need neither, collapsing the dominant cost identified in §02.
  • No inference latency penalty (when merged) — after training, B·A can be mathematically merged back into the original weight matrix (W_new = W + B·A), so the deployed model has the exact same architecture and speed as the base model, with zero added inference cost.
  • Small, swappable artifacts — a LoRA adapter is often just tens to hundreds of megabytes (versus tens of gigabytes for a full model checkpoint), making it practical to train and store many task-specific adapters on top of one shared base model, and swap between them at serve time.
  • Lower overfitting risk on small datasets — because far fewer parameters are being learned, LoRA is naturally more resistant to overfitting when your fine-tuning dataset is modest in size, which is the common case for task-specific customization.
The multi-tenant serving pattern this unlocks Because a base model can stay loaded once in GPU memory while multiple small LoRA adapters are swapped in per-request (a pattern supported natively by serving engines like vLLM), you can serve many customers' or many tasks' fine-tuned behavior from a single shared deployment — a meaningfully different cost profile than needing a dedicated full-model deployment per customization.
§ 04 — QLoRA
Thought experiment

LoRA already avoids storing gradients and optimizer state for the frozen base weights — but those frozen weights still have to sit in GPU memory in full precision just to be read during the forward/backward pass. If the base weights are never being updated, do they really need to be stored at full 16-bit precision at all?

QLoRA — quantization meets LoRA

QLoRA combines LoRA with quantizing the frozen base model down to 4-bit precision (using a specialized data type — NF4, "NormalFloat4," designed to represent normally-distributed weight values with less information loss than naive 4-bit quantization). The LoRA adapters themselves are still trained in higher precision (typically bf16), so learning quality is preserved while the memory-dominant frozen base is compressed roughly 4x compared to fp16.

   LoRA vs QLoRA — WHERE THE MEMORY SAVINGS COME FROM

   LoRA:    [ Base model: fp16, frozen ] + [ LoRA adapters: fp16, trainable ]
                    ~14GB for 7B model         ~tens of MB

   QLoRA:   [ Base model: 4-bit (NF4), frozen ] + [ LoRA adapters: bf16, trainable ]
                    ~3.5GB for 7B model              ~tens of MB
                    (further reduced via
                     double quantization +
                     paged optimizers)

   → QLoRA made it practical to fine-tune 65B+ parameter models
     on a single consumer/prosumer-grade GPU (e.g. one 48GB card)
     rather than requiring a multi-GPU cluster

Additional QLoRA-specific techniques

  • Double quantization — quantizes the quantization constants themselves, squeezing out additional memory savings on top of the base 4-bit compression.
  • Paged optimizers — uses NVIDIA unified memory to page optimizer state between GPU and CPU memory when GPU memory spikes, avoiding out-of-memory crashes during training on long sequences, at some cost to training speed during those spikes.
Why QLoRA was a genuine inflection point Before QLoRA, fine-tuning a large (30B+) model realistically required institutional-scale multi-GPU infrastructure. QLoRA's contribution was showing that near-full-fine-tuning-quality results were achievable on dramatically cheaper hardware, which is a large part of why fine-tuning open-weight models became broadly accessible to individual practitioners and smaller teams, not just large labs.
§ 05 — WIDER PEFT FAMILY
Thought experiment

LoRA attacks the memory problem by shrinking how many parameters get updated. Is that the only axis you could optimize along — or could you instead change where in the model you intervene, or what kind of thing you're learning rather than raw weight deltas at all?

Beyond LoRA — the broader PEFT landscape

LoRA is the dominant, most widely-adopted PEFT method today, but it's one point in a broader design space of ways to adapt a model cheaply.

MethodCore idea
Prefix tuningPrepends a small number of trainable "virtual token" vectors to the input at every transformer layer, steering attention without touching any existing weights at all
Prompt tuningA simpler variant — learns a small set of trainable embeddings prepended only at the input layer (not every layer), even fewer parameters than prefix tuning but generally lower expressive power
Adapter layersInserts small trainable bottleneck feed-forward layers between existing frozen transformer layers, rather than modifying existing weight matrices at all
(IA)³Learns per-channel scaling vectors that rescale activations, an even more parameter-frugal approach than LoRA in some setups
DoRA (Weight-Decomposed LoRA)Decomposes weight updates into magnitude and direction components, often improving on plain LoRA's learning capacity at similar parameter budgets
Why LoRA still dominates despite alternatives LoRA's key practical advantage — that its trained update can be exactly merged back into the base weights with zero added inference latency — is not shared by all PEFT methods (prefix/prompt tuning add tokens to every forward pass, adapter layers add extra computation layers). This makes LoRA/QLoRA the default starting point for most practitioners, with the other methods used in more specialized situations.
§ 06 — INSTRUCTION TUNING
Thought experiment

A raw pretrained model, asked "explain photosynthesis," is just as likely to continue with "...to a 10-year-old" or list five more similar exam questions as it is to actually answer — because its training objective was only ever "predict the next plausible token," not "recognize this as a request and fulfill it." What has to change to turn a next-token predictor into something that reliably behaves like it understands it's being asked to do something?

Instruction tuning — teaching the shape of "being helpful"

Instruction tuning is a specific, foundational application of fine-tuning (usually the first stage after pretraining, and typically done via full fine-tuning or LoRA on top of a base model): training on a large, diverse set of (instruction, response) pairs so the model learns the general pattern of "recognize this text as a request, then produce a response that fulfills it" — across many different task types, phrasings, and domains.

What instruction tuning teaches, specifically

  • Task recognition — distinguishing "summarize this" from "translate this" from "answer this question," and responding in the appropriate mode rather than just continuing the text.
  • Format compliance — following explicit formatting requests (bullet points, JSON, specific length constraints) rather than defaulting to free-form continuation.
  • Generalization across unseen instructions — a model instruction-tuned on a sufficiently diverse dataset learns to follow novel instructions it never saw during training, not just to memorize the training examples — this generalization is the entire point, and is what separates a genuinely useful instruction-tuned model from mere memorization.
  • Conversational structure — recognizing turn-taking, multi-turn context, and system/user/assistant role structure, rather than the flat text-continuation format pretraining used.
   BASE MODEL vs INSTRUCTION-TUNED MODEL — SAME PROMPT

   Prompt: "Summarize the following in one sentence: [long paragraph]"

   BASE MODEL (pretraining only) might continue:
   "...Summarize the following in one sentence: [ANOTHER paragraph]
    Summarize the following in one sentence: ..."
   → treats it as a pattern to CONTINUE, not an instruction to FOLLOW

   INSTRUCTION-TUNED MODEL:
   "[Actual one-sentence summary of the paragraph]"
   → recognizes the instruction and fulfills it directly
This gap — between "completing plausible text" and "recognizing and fulfilling a request" — is exactly what instruction tuning closes, and it's the reason base models and their instruction-tuned counterparts (often suffixed "-Instruct" or "-Chat") behave so differently on identical prompts.
Where this sits relative to alignment (Study Note 015, §10.9) Instruction tuning is typically the supervised fine-tuning (SFT) stage of the broader alignment pipeline — it teaches the model how to respond to instructions in general. RLHF/DPO, which come after, further shape which responses are preferred among the many "instruction-following" responses the SFT stage made possible — safety, helpfulness, and tone refinement layer on top of instruction tuning, not instead of it.
§ 07 — DATASET CONSTRUCTION
Thought experiment

If a model instruction-tuned on 500 examples that are all phrased as polite, well-formed questions is then asked a terse, typo-ridden, real-world query — does its "generalization" actually hold, or did it just learn to recognize one narrow style of instruction?

What makes an instruction-tuning (or task fine-tuning) dataset actually work

  • Diversity over raw volume — a smaller dataset covering many distinct task types, phrasings, and difficulty levels generalizes better than a much larger dataset that's narrowly repetitive; this is a well-documented finding (LIMA-style results showed a relatively small number of very high-quality, diverse examples can rival much larger, noisier datasets).
  • Response quality over response quantity — since the model is learning to imitate the style and correctness of the target responses, low-quality or inconsistent responses in the training set directly teach the model those same flaws.
  • Realistic input distribution — training examples should reflect the actual phrasing, length, and messiness of real user queries, not an idealized, cleaned-up version of them, or the model will generalize poorly to production traffic.
  • Consistent formatting/schema — for task-specific fine-tuning (e.g. structured extraction), consistent input/output formatting across every training example is critical, since the model is partly learning the format itself, not just the content.
  • Held-out evaluation set — a portion of curated examples should be set aside, never trained on, and used to actually measure whether the fine-tune improved the target behavior (tying back to Study Note 015's evaluation frameworks) rather than assuming success from training loss alone.
A common trap in applied fine-tuning projects Training loss going down does not mean task performance is going up — a model can overfit to superficial patterns in a small, homogeneous dataset (identical phrasing, identical formatting) while actually getting worse at the underlying task on realistic inputs. Always evaluate on held-out, diverse examples, not training loss curves alone.
§ 08 — THE DECISION FRAMEWORK
Thought experiment

Someone on your team says "the model keeps getting our fund's expense ratio wrong — let's fine-tune it to know the correct number." Is fine-tuning actually the right fix for that specific complaint — or does the complaint itself reveal exactly why it's the wrong tool?

Fine-tuning vs RAG vs prompt engineering — matching the tool to the problem

The single most common applied-AI mistake is reaching for fine-tuning to solve a knowledge problem. Fine-tuning is a poor mechanism for teaching new facts reliably — it doesn't guarantee the model will recall a specific fact correctly at inference time (facts get blended into weights probabilistically, not stored discretely), and every time the underlying fact changes (a rate, a policy, a NAV), you'd need to fine-tune again. That's precisely the problem RAG was built for (Study Note 014).

ApproachChangesBest forPoor fit for
Prompt engineeringNothing persistent — steers behavior per-call via instructions/examplesFast iteration, low volume, behavior that's easy to describe in words, one-off or evolving requirementsHigh-volume cost efficiency, very subtle style patterns hard to describe, large few-shot examples eating context budget
RAGWhat the model can see at query timeFresh/volatile facts, private/proprietary data, source attribution requirements, frequently-changing informationTeaching a new skill, style, or reasoning pattern — RAG doesn't change how the model behaves, only what it can reference
Fine-tuning (incl. LoRA/QLoRA)The model's default behavior/weightsConsistent tone/style/format at scale, teaching a specific task-execution pattern, reducing prompt length/cost at high volume, domain-specific reasoning styleTeaching volatile or frequently-updated facts, anything requiring source attribution/auditability, low-data situations
   A SIMPLE DECISION TREE

   Is the problem "the model doesn't know a FACT"?
        │
        ├── YES ──▶ Is that fact static/rarely changing and small in volume?
        │               ├── YES ──▶ Prompt engineering (put it directly in the prompt/system prompt)
        │               └── NO  ──▶ RAG (retrieve it fresh at query time)
        │
        └── NO, it's a BEHAVIOR problem (wrong tone/format/style/reasoning pattern)
                │
                ├── Can you describe the desired behavior clearly in words,
                │   and is call volume low/moderate?
                │       └── YES ──▶ Prompt engineering first — cheapest, fastest iteration
                │
                └── Is the behavior hard to describe in words, but easy to
                    DEMONSTRATE with examples, at meaningful call volume?
                        └── YES ──▶ Fine-tuning (LoRA/QLoRA as the default starting point)
Prompt engineering and RAG are almost always cheaper and faster to iterate on than fine-tuning — the strong default is to reach for fine-tuning only after prompting/RAG have been genuinely tried and found insufficient for a behavior problem, not a knowledge problem.
These are not mutually exclusive Production systems very commonly combine all three: a fine-tuned model (for consistent domain tone/format and task-specific skill) that's also given RAG-retrieved context (for current facts) inside a well-engineered prompt (for task framing and edge-case instructions). The question isn't "which one," it's "which layer is this specific problem actually a symptom of."
§ 09 — APPLIED WALKTHROUGH
FINTECH GROUNDED
Thought experiment

Picture three real complaints from a wealth-platform AI assistant: (1) it gives today's NAV incorrectly, (2) its answers don't sound like your compliance team's approved tone and always forget to add the mandatory risk disclaimer, (3) it can't reliably extract structured fields (scheme code, folio number, amount) from messy free-text customer requests into a fixed JSON schema for downstream processing. Are these the same problem wearing different clothes, or three genuinely different problems needing three different fixes?

Mapping three real complaints to three different tools

Complaint 1 — wrong NAV / stale numbers

Diagnosis: a knowledge-freshness problem, not a behavior problem. Fine-tuning would bake in today's NAV as if it were a permanent fact — actively harmful the moment the NAV changes tomorrow.
Fix: RAG routed to a live data source/API for volatile numeric facts (as covered in Study Note 014, §13), not a static vector index and definitely not fine-tuning.

Complaint 2 — wrong tone, missing mandatory disclaimer

Diagnosis: a consistent-behavior-at-scale problem. This is describable in words (a system prompt instruction) but the failure is happening because the instruction isn't being followed reliably across many varied real queries — a classic sign that prompting alone is hitting its ceiling for volume/consistency.
Fix: start with prompt engineering (explicit instruction + a couple of strong few-shot examples) and measure compliance rate; if compliance still isn't reliable enough at production volume, a LoRA fine-tune on a curated dataset of correctly-toned, disclaimer-included responses directly bakes the behavior in — this is a textbook case for instruction-style fine-tuning.

Complaint 3 — unreliable structured extraction into a fixed schema

Diagnosis: a task-execution-skill problem with a precise, learnable input→output mapping — a strong candidate for fine-tuning because the pattern (messy text in, exact schema out) is easy to demonstrate with hundreds of examples and hard to fully guarantee with prompting alone at high volume, especially against edge cases and messy real input.
Fix: a LoRA/QLoRA fine-tune on a diverse, high-quality dataset of (messy input, correct JSON output) pairs, likely combined with structured-output constraints (schema validation as an output guardrail, per Study Note 015 §10.7) as a safety net even after fine-tuning.

The pattern across all three Notice that only one of the three genuinely called for fine-tuning, and even that one started with the cheaper prompt-engineering attempt first. This mirrors the general rule from §08: fine-tuning is usually the last tool reached for, and only after the problem has been correctly diagnosed as a behavior/skill problem rather than a knowledge/freshness problem.
§ 10 — ACTIVE RECALL

Test yourself — click each question to reveal the answer

Cover the answers first. Try to answer from memory before expanding.

What's the fundamental distinction between what fine-tuning changes and what RAG changes?
Fine-tuning changes the model's behavior — its default tone, format, and task-execution pattern — by updating weights. RAG changes what the model can see at query time — the facts/context available to it — without touching weights at all. Fine-tuning is a poor tool for teaching new or frequently-changing facts; RAG is a poor tool for teaching a new skill or behavioral pattern.
In full fine-tuning, why does optimizer state (not the raw weights) dominate the memory cost?
Optimizers like Adam store additional per-parameter state (momentum and variance estimates) alongside the gradient, typically doubling or tripling the memory footprint beyond just the weights and their gradients. For large models this optimizer state is usually the single largest memory line item during training.
How does LoRA reduce trainable parameters, and why does this not add any inference latency once training is done?
LoRA freezes the original weight matrix and learns a low-rank decomposition (two small matrices A and B) that approximates the needed weight update, requiring far fewer trainable parameters than the full matrix. After training, B·A can be mathematically merged directly back into the original frozen weights, so the deployed model has identical architecture and speed to the base model — no added computation at inference time.
What does QLoRA add on top of LoRA, and why did it matter practically?
QLoRA quantizes the frozen base model down to 4-bit precision (using the NF4 data type) while still training the LoRA adapters in higher precision, cutting the dominant memory cost (the frozen base weights) roughly 4x. This made it practical to fine-tune very large models (65B+) on a single GPU rather than requiring a multi-GPU cluster, significantly broadening who could afford to fine-tune large models.
What specifically does instruction tuning teach a base pretrained model that pretraining alone does not?
Pretraining only teaches next-token prediction over raw text, with no inherent notion of "this is a request, fulfill it." Instruction tuning trains on diverse (instruction, response) pairs so the model learns to recognize text as a request and generate a response that fulfills it, generalizing that pattern to novel instructions it wasn't explicitly trained on — rather than simply continuing the text as if it were more of the same pattern.
Why is dataset diversity generally more important than raw dataset size for instruction/task fine-tuning?
A model learns to generalize from the range of task types, phrasings, and difficulty levels it sees during training. A large but repetitive/narrow dataset teaches the model to handle only that narrow style well, while a smaller but genuinely diverse, high-quality dataset produces better generalization to novel, real-world inputs — a finding borne out by results like LIMA showing a small number of high-quality diverse examples can rival much larger datasets.
A team wants to fine-tune a model so it "knows" a frequently-changing interest rate. Why is this the wrong fix, and what should they do instead?
Fine-tuning doesn't reliably store discrete facts and would require re-training every time the rate changes — an operationally unsustainable and factually unreliable approach for volatile data. The correct fix is RAG routed to a live data source/API for that specific fact, reserving fine-tuning for behavior/skill problems rather than knowledge-freshness problems.
Why should prompt engineering and RAG typically be tried before fine-tuning, even when fine-tuning is ultimately the right tool?
Prompt engineering and RAG are cheaper, faster to iterate on, and don't require building/curating a training dataset or managing a training pipeline. Fine-tuning is comparatively expensive and slower to iterate, so the practical default is to exhaust the cheaper options first and confirm the problem is genuinely a behavior/skill problem that words and retrieved context can't solve, before committing to a fine-tuning effort.
