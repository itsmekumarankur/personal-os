01

Why MCP was invented

Language models could think, reason and talk years before they could reliably act. MCP is the response to that gap — the moment the field stopped building custom bridges per tool and standardized the bridge itself.

2018

BERT

Could understand context — the first widely deployed model that reasoned about meaning, not just tokens.

2020

GPT-3

Could generate fluent text at scale, but still had no way to reach outside its own context window.

2022

ChatGPT

Could converse — a brain with a voice, but still no hands. Every external action needed bespoke glue code.

2023

GPT-4

Could reason over multi-step problems, sharpening the mismatch between what the model could plan and what it could actually execute.

2024 →

MCP

Could act and connect — a standard interface between the model's reasoning and the world's tools and data.

Analogy — traditional AI was a brain with no limbs: it could think, reason, and talk, but couldn't open a file, query a database, call an API, or run code.
2020–22

Chatbots

Text in, text out. No world access at all.

2022–23

Assistants

Could use APIs, but every integration was custom code — one snowflake per tool.

2024+

MCP-era agents

Reason, act, and use tools through one standardized protocol instead of N bespoke ones.

02

The problem before MCP

Every AI application wired its own adapters to every tool it needed. Multiply apps by tools and you get a combinatorial mess — the classic N×M integration problem.

Three AI apps, three tools, three completely separate adapters — none of it reusable:

App A → Custom Adapter #1 → Database A App B → Custom Adapter #2 → Service B App C → Custom Adapter #3 → Tool C // every app: custom code // every integration: from scratch // every tool: a unique interface
Fragmentation

No shared interface

Each AI tool speaks a different API. Each app needs a different integration. One upstream update breaks the chain.

Context nightmare

Everything crammed into the prompt

Without a standard way to fetch live data, files, or query results, the old fix was pasting it all into the prompt — token explosion, context overflow.

Security as afterthought

Auth bolted on, or missing

"Please access my database" with no authentication layer at all — every app rebuilding auth from zero.

Real-world cost

Without MCP

  1. Write custom Slack API integration — roughly two weeks of work
  2. Hand-roll auth, rate limiting, webhooks
  3. Works only for Slack — Teams and Discord each need their own build
  4. Postgres, MongoDB, Salesforce each get a separate wrapper codebase

With MCP

  1. Point the client at an existing MCP Slack server — roughly an hour of configuration
  2. Same interface as every other connected tool
  3. Works with any MCP-compatible client, no rebuild per platform
  4. Postgres, MongoDB, Salesforce each expose an MCP server behind one client interface
03

Architecture, top to bottom

Four layers sit between a model's intent and the system that fulfills it: the model itself, the client that speaks MCP, the transport that carries the bytes, and the server that exposes capabilities.

1

AI Model (Client)

Decides, from the user's request, that it needs external data or an action.

2

MCP Client (Protocol handler)

Formulates the request as a standard MCP call and manages session state.

3

Transport (stdio / SSE / HTTP)

Carries the JSON-RPC 2.0 message between client and server.

4

MCP Server → capabilities

Resources, Tools, and Prompts — routed to the right handler and executed.

5

External systems

Databases, APIs, and files — the actual source of truth the server talks to.

Walking through a request

"Summarize the sales data from last quarter" — traced end to end:

User → AI Model "I need sales data" AI Model → MCP Client translates intent into a request MCP Client → MCP Server get_resource: sales_data MCP Server → Database executes the underlying query Database → MCP Server rows returned MCP Server → MCP Client data in a standard format MCP Client → AI Model generates the summary AI Model → User "Here's your summary…"
04

The five components

Client and Server are the two ends of the wire. Resources, Tools, and Prompts are what the server offers across it — data, actions, and templates, respectively.

MCP Client — the brain

Where the AI model lives and makes decisions

Initiates connections to servers, formulates requests, and manages session state across a conversation. It can hold connections to multiple servers at once and route each intent to the right one.

  • Initiate connections to servers
  • Send tool calls & resource requests
  • Parse and process responses
  • Handle errors and retries
  • Manage authentication tokens
  • Route across multiple servers

MCP Server — the hands and eyes

Provides capabilities to the AI

Listens for connections, validates incoming requests, and routes them to the right handler — Resources, Tools, or Prompts — before returning a structured response.

  • Register available resources
  • Expose executable tools
  • Provide prompt templates
  • Handle authentication
  • Manage access control
  • Return structured responses

Resources — the library

Data the model can read

Static (a policy PDF), dynamic (a live query), or computed (an on-the-fly analytics report) — addressed by a URI, e.g. mcp://database/customers/123.

{ "uri": "mcp://database/customers", "name": "Customer Database", "mimeType": "application/json", "capabilities": ["read", "query"] }

Tools — the appliances

Actions the model can perform

Read, write, execute, or compute — tools make changes rather than just returning data. Each is declared with a name, a description, and a parameter schema the model uses to call it correctly.

{ "name": "send_email", "parameters": { "to": "string", "subject": "string", "body": "string" } }

Prompts — the recipes

Templates that structure a response

System, user, task, and context prompts give an interaction its shape — role definitions, workflow scaffolds, or background the model should reason from.

{ "name": "sales_analysis", "template": "You are a sales analyst. Analyze: {{sales_data}} Return trends, risks, recommendations." }
05

Protocol internals

Underneath the concepts is plain JSON-RPC 2.0 — a request/response envelope with an id, a method name, and typed params.

Request
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "send_email", "arguments": { … } } }
Response
{ "jsonrpc": "2.0", "id": 1, "result": { "content": [ { "type": "text", "text": "Email sent" } ] } }

06

Lifecycle of a request

A real sequence, start to finish — from handshake to the answer landing back with the user.

1

Discovery

Client asks "what can you do?" — server replies with its full capability list of resources, tools, and prompts.

2

Decision

The model decides, from the user's ask, which capability it needs — e.g. "I need to send an email."

3

Action

Client issues a tools/call request with the tool name and its arguments.

4

Execution

Server validates the call, executes it against the real system, and prepares a result.

5

Response

Server returns the structured result — "Email sent successfully."

6

Presentation

Client formats the result into the model's reply and surfaces it to the user.

Worked example — a chat app wired to five servers

📁 Files

Read/write access to documents and folders.

🗄️ Database

Structured queries against live tables.

📧 Email

Composing and sending messages.

🔍 Search

Web search for current information.

📊 Analytics

Report and summary generation.

User: "What are my top customers?"

1. Identify need → customer data 2. Select tool → database/query 3. Execute → SELECT * FROM customers ORDER BY revenue DESC LIMIT 10 4. Format results → table 5. Present to user → done
07

Transport layer

The protocol is transport-agnostic — the same JSON-RPC messages travel over any of three carriers, chosen by deployment shape rather than by capability.

📟 stdio

Process pipes

Process-based communication over simple stdin/stdout pipes. Best for local tools and CLI apps.

Pros
Simple, no network issues
Cons
Can't run remotely
📡 SSE

Server-sent events

Event-based streaming over an HTTP connection with keep-alive. Best for real-time updates.

Pros
Persistent connection
Cons
One-way by default
🌐 HTTP

Request / response

Standard RESTful request/response. Best for web services and public APIs.

Pros
Widely supported, stateless
Cons
Overhead for streaming

Client configuration — three servers, one client

{ "servers": [ { "name": "files", "transport": "stdio", "command": "node files-server.js" }, { "name": "database", "transport": "sse", "url": "http://localhost:3000/sse" } ] }
The client spawns the server as a child process and talks to it purely through stdin/stdout. There's no socket, no port, no network stack to secure — the operating system's process boundary is the whole transport. This is why it's the default choice for local developer tools: nothing to expose, nothing to firewall, and it disappears the moment the parent process exits.
A server running on the same machine as the client — a filesystem tool, a local script runner — has nothing to gain from a network transport and everything to gain from stdio's simplicity. A server shared across a team or reached over the internet needs SSE or HTTP precisely because stdio can't leave the host. The protocol above this layer never changes; only how the bytes travel does.

Rough sketches — the way you'd draw it on a whiteboard

Before the polished diagrams, this is what it actually looks like on a napkin when you're arguing about a design in a room. Four sketches: the trust boundary, the fan-out problem, what happens when a server dies mid-call, and the gateway pattern that saves you from server sprawl.

sketch 1 — where does trust actually break?
TRUSTED ZONE : UNTRUSTED-ish ZONE : EXTERNAL (your app) : (mcp servers, 3rd party) : (world) : : +--------------+ : +----------------+ : | AI MODEL | : | MCP SERVER A |----------> Database | (client) |----auth----> | (files) | : +--------------+ | : +----------------+ : | | : : | | : +----------------+ : | +-------> | MCP SERVER B |----------> 3rd-party API | : | (payments!) | : $$$ | : +----------------+ : | ^ : | | : '---- every arrow crossing ---' : this dotted line needs its OWN auth check. don't assume the client's trust carries through.
⚠ the model choosing to call a tool ≠ the model being authorized to call it. check both.
sketch 2 — fan-out and the aggregation headache
+------------+ ,--->| server A |--- 40ms / +------------+ +----------+ / +------------+ | client |--+------>| server B |--- 900ms <-- slowest wins +----------+ \ +------------+ (or times out \ +------------+ and drags the '--->| server C |--- 55ms whole answer) +------------+ one user question -> N parallel mcp calls -> 1 merged answer. the client is now doing orchestration, not just protocol handling. ask: what's the timeout budget PER server, and what do we show the user if server B never comes back?
→ set a hard per-call timeout budget and degrade gracefully — a partial answer beats a frozen spinner.
sketch 3 — happy path vs. the path that actually happens
HAPPY PATH client --req--> server --exec--> ok --resp--> client done. REAL PATH client --req--> server --exec--> [ crashes / times out / rate-limited ] | | | v | client waits... | | +--- retry? ---------- only if idempotent! ------+ | | v v READ tool (get_customer) WRITE tool (charge_card) -> safe to retry -> retrying can double-charge -> needs an idempotency key, not a blind retry
⚠ this is the one architects get bitten by: retries are free for Resources, dangerous for Tools.
sketch 4 — server sprawl vs. a gateway
WITHOUT A GATEWAY WITH A GATEWAY client A --\ /-- server 1 client A --\ client B ---+-+--- server 2 \ client C --/ \-- server 3 client B ------> MCP GATEWAY --+--> server 1 / (registry, +--> server 2 every client has to know client C --/ auth, quota, +--> server 3 every server + its creds. logging) 6 wires to babysit. every client -> 1 wire. no central audit log. one place to see EVERY tool call across the org.
→ this is the pattern most platform teams land on once they pass ~5 internal MCP servers.
09

The architect's lens

Everything above is "how MCP works." This is "what it costs you, what breaks, and what to decide before you ship it" — the questions a CTO or staff architect actually gets asked in the design review.

Decision — build vs. adopt

Don't build a custom protocol just because MCP feels heavy at first

The temptation on a small team is "we only have 3 tools, a REST wrapper is faster." That's true for month one. The cost MCP is paying for is every integration after the third — a new hire's agent, a second AI product, an external partner — that gets the connector for free instead of another bespoke adapter.

SignalLean toward MCPLean toward a direct API call
Number of tools/data sources5+ and growing1–2, stable
Number of AI clients consuming themmultiple products/teamsone internal script
Need for audit/governanceyes — regulated datano — internal & low-stakes
Team maturity to run a registryplatform team existsno one owns it yet
Security — every server is a new attack surface

Treat each MCP server like a new microservice, not a plugin

The protocol standardizes the wire format; it does not standardize how much you should trust the thing on the other end. A server that exposes a "charge_card" or "transfer_funds" tool is a privileged action executor sitting behind a chat interface — the same scrutiny you'd give a payments microservice applies here, arguably more, because the caller is a model choosing to invoke it, not a human clicking a confirmed button.

  • Scope credentials per-server, per-tool — never hand the model's client a god-mode API key
  • Put a human-approval gate in front of any tool with financial, destructive, or irreversible side effects
  • Log every tool call with who/what/when at the gateway, not just inside each server
  • Sandbox third-party MCP servers you didn't write — they can see every argument you pass them
Resilience — design for the server that doesn't answer

Idempotency is the whole ballgame for write tools

Read-heavy Resources are forgiving — a retried query just costs you latency. Tools that mutate state are not. Every write tool needs an idempotency key baked into its schema from day one, or a retry after a timeout can silently duplicate the action. This is the single most common production incident pattern in agent-tool systems.

  • Per-server timeout budgets, not one global timeout for the whole fan-out
  • Circuit breakers so one dead server doesn't stall every request that touches it
  • Explicit "what do we show the user" fallback when a server degrades mid-answer
Governance — the registry is the org chart made visible

At scale, the question stops being "does it work" and becomes "who owns it"

Past a handful of internal servers, you need a central registry: what's exposed, who owns it, what's its SLA, when was it last reviewed for scope creep. This is also your best answer to a compliance auditor asking "what can this AI system actually do" — point at the registry instead of grepping fifteen codebases.

  • Versioned tool schemas — a silent breaking change in a tool's parameters breaks every client at once
  • A deprecation policy, the same way you'd retire a public API endpoint
  • One team owning the gateway/registry; domain teams owning their own servers behind it
Fintech / regulated-data specific

The audit trail is the deliverable, not an afterthought

In a regulated domain, "the model decided to call a tool" is not sufficient justification in an audit — you need the full chain: which user's session, which prompt led to the decision, which tool, which arguments, which downstream system, which result. Design the logging schema for that chain before you design the tools themselves.

  • PII-bearing Resources need the same masking/access-control rules as any other data API
  • Consider a "dry-run" mode for write tools during rollout — return what would happen without executing
  • Rate-limit and quota per model/session, not just per API key — a runaway agent loop is a new failure class
