Part Two — Enterprise & Production

MCP at enterprise scale
patterns, tradeoffs, and the banking floor

Part one covered how MCP works. This part covers how it survives contact with a real IT estate — legacy mainframes, five deployment topologies, multi-agent orchestration, and the specific demands of a regulated banking stack.

FIG. 1 — the enterprise landscape: agents never touch the mainframe directly, the gateway does
01

Five enterprise integration patterns

These are shapes, not competitors — a real deployment usually stacks two or three of them. A gateway sits in front of everything; behind it, some servers are aggregators, some are adapters wrapping legacy systems, some ride along as sidecars.

Every client talks to one gateway; the gateway handles auth, rate limiting, routing, caching, and logging before forwarding to the right MCP server behind it.

Client ──▶ API Gateway ──▶ MCP Server Registry ──▶ [Server 1] [Server 2] [Server 3] (auth, rate limit, routing, logging)

Use it when: you have more than a couple of clients and more than a couple of servers — the N×M wiring problem is exactly what this collapses to N+M.

One high-level request ("customer 360 view") fans out to CRM, billing, and support servers in parallel, and a single aggregator server merges the results into one response.

"Get complete profile for customer #123" │ Aggregator ──┬──▶ CRM MCP ├──▶ Billing MCP └──▶ Support MCP │ merged JSON response

Use it when: the model shouldn't have to reason about which of five backends holds which fact — give it one clean view instead.

A proxy sits between client and the real server — rewriting requests, enforcing policy per client context, caching, or terminating TLS — without the backend server knowing any of that happened.

MCP Client ──▶ MCP Proxy (security, caching) ──▶ MCP Server (real backend)

Use it when: you need to change behavior at the edge — new policy, new cache layer — without redeploying every server.

The workhorse for legacy systems. The adapter translates MCP requests into whatever the old system actually speaks — SOAP, a JDBC connection, a mainframe screen-scrape — and translates the response, errors, and retries back into MCP shape.

MCP Client ──MCP──▶ MCP Adapter ──SOAP / REST / JDBC──▶ Legacy System

Use it when: the system of record isn't going to be rewritten this decade, but it still needs to be reachable by an agent.

An MCP server runs as a second container in the same pod as a microservice, handling all MCP traffic on its behalf — the microservice itself never needs to know the protocol exists.

┌─ Pod ─────────────────────────────┐ │ Microservice (Node.js) │ │ ▲ │ │ │ localhost │ │ MCP Sidecar (Go) ──▶ MCP Client │ └────────────────────────────────────┘

Use it when: you don't want to touch a service's codebase to give it an MCP interface — common in polyglot microservice fleets like a wealth/demat platform.

MCP vs REST vs GraphQL vs Plugins vs Function Calling

The honest framing: these aren't all solving the same problem. REST and GraphQL are for humans and services calling services. MCP, Plugins, and Function Calling are all AI-first — the real comparison is between those three.

PurposeStandardized AI context/tool protocolGeneral API designFlexible query languagePlug-in ecosystem (ChatGPT)Direct tool calling from the LLM

StatefulnessSession-basedStatelessStatelessSession-basedStateless

Decision tree

Is this for AI consumption? ├─ No → standard REST/GraphQL (human-first APIs) └─ Yes → Do you need multiple tools/resources across servers? ├─ No → Function Calling is enough (single tool, single API) └─ Yes → Do you also need dynamic prompt management? ├─ No → MCP, using resources + tools └─ Yes → MCP, using the full resources + tools + prompts model

vs. Function Calling

Function calling hard-codes every function definition into each request. MCP discovers capabilities at runtime — the model queries the server instead of the request payload carrying every schema up front, and can hold several servers open at once.

vs. Plugins (ChatGPT-style)

Plugins are separate web services described by an OpenAPI manifest — REST/HTTP only, no standard resource or prompt model. MCP is transport-agnostic and composable: one client can reach many servers with a consistent interface for all three capability types.

03

Multi-agent architecture

MCP is also the language agents use to talk to each other, not just to tools — an agent can expose its own capability as an MCP server that another agent calls.

Direct

Agent-to-agent

Agent A exposes a tool ("research"). Agent B's MCP client calls it directly — no orchestrator required.

Hub

Orchestrator / Coordinator

One orchestrator holds the goal and delegates subtasks to specialized agents — Research, Data, Creative — each with its own MCP client.

Async

Event-driven / message bus

Agents publish MCP notifications to a bus; interested agents subscribe. No agent needs to know who's listening.

Worked example — customer service, four agents deep

1

Query lands

"I want to return a product" arrives at the orchestrator agent.

2

Intent understood, work delegated

Orchestrator fans out to Policy Agent, Order Agent, and Logistics Agent in parallel.

3

Each sub-agent calls its own MCP server

Policy → return-policy server, Order → order-lookup server, Logistics → label-generation server.

4

Orchestrator composes the answer

Combines eligibility, order details, and a shipping label into one reply — the customer sees a single coherent response.

Why it matters — every agent added later just plugs into the same MCP servers; nothing about the existing agents has to change.

04

Enterprise deployment

Three questions decide the deployment shape: how many servers, where do they run, and how do you see what's happening across all of them.

Dev / small scale

Standalone

One server, all capabilities. Fine until a second team wants in.

Growth

Distributed

One server per domain (CRM, DB, API, AI), each independently deployed — typically on Kubernetes.

Latency-sensitive

Edge vs Cloud

Cloud for centralized, high-capacity workloads; edge for on-premise or IoT paths that can't tolerate a round trip.

Metrics that actually matter

• Request rate (per server, per tool) • Error rate (4xx, 5xx) • Latency (p50, p95, p99) • Resource usage (CPU, memory) • Tool success ratio • Active session count

Auth flow

Client ──1.Auth──▶ OAuth2 Server │ 2.Token│ ▼ MCP Server ──3.Validate token & permissions──▶ allow/deny

Secrets & data privacy

API keys and DB credentials live in a vault (e.g. HashiCorp Vault), fetched at runtime — never hard-coded. PII-bearing resources get masking/filtering, and every access is logged for audit.

HA & disaster recovery

Multiple replicas per server, a load balancer or service mesh (Istio) for distribution, health checks with auto-restart, and backed-up config/state.

06

Production challenges

Six recurring failure modes and what actually mitigates each one — not the happy-path guide.

MCP is an extra hop between the AI and the backend. Mitigate with the right transport per deployment (stdio locally, SSE for streaming), caching for frequently-read resources, parallelizing independent calls, and binary serialization where JSON overhead actually shows up in profiling.

Servers fail, backends slow down. The standard toolkit: timeouts with exponential backoff, circuit breakers, graceful degradation to a fallback response, and health checks with auto-restart.

1st attempt: immediate 2nd attempt: +1s 3rd attempt: +2s 4th attempt: +4s 5th attempt: +8s (then give up)
Servers evolve; clients need to keep working. Servers advertise their protocol version at initialization, clients negotiate or fall back, and resource/tool schemas evolve rather than break outright — treat a tool's input schema the way you'd treat a public API contract.
MCP is session-based by design, which is awkward once you're running multiple stateless server instances behind a load balancer. Store session state externally (Redis) and lean on idempotent operations so a retry against a different instance doesn't double up on side effects.
Exposing an MCP server to the internet means TLS termination at the gateway, least-privilege access per tool, and the same penetration-testing cadence you'd run against any other externally reachable service.
Dashboards (Grafana) on the metrics from the deployment section, explicit SLOs (e.g. 99.9% availability, p95 < 200ms), and alerts on error spikes, latency regressions, or resource exhaustion before a customer notices.

Rough sketches — the enterprise version

The whiteboard version of the patterns above — how you'd actually draw them mid-argument about a design.

sketch 1 — where the N×M problem actually gets collapsed
WITHOUT A GATEWAY (N x M wires) WITH A GATEWAY (N + M wires) agentA--\ /--serverCRM agentA--\ agentB---+-+--serverDB \ agentC--/ \--serverAPI agentB-----> GATEWAY --+--> serverCRM / +--> serverDB 3 agents x 3 servers = 9 wires agentC----/ +--> serverAPI each agent must know every server's address + creds 3 agents -> 1 wire each = 3 gateway -> 3 servers = 3 total wires = 6
→ the saving isn't just wire count — it's that ONE place now owns auth, quota, and the audit log.
sketch 2 — the adapter is doing more work than it looks like
MCP Client --MCP--> [ MCP ADAPTER ] --COBOL screen-scrape--> Mainframe | +--------+--------+ | translate req | MCP shape -> legacy shape | translate resp | legacy shape -> MCP shape | translate ERRORS| legacy error codes -> MCP errors | own retry logic | mainframe has no concept of "retry" +-------------------+ the adapter is now the thing that has to understand BOTH worlds. underestimate this and it becomes the most fragile box in the stack.
⚠ budget adapter work like you'd budget a real migration project, not a weekend wrapper.
sketch 3 — session state once you scale horizontally
ONE INSTANCE (fine) MANY INSTANCES (breaks quietly) client <-session-> server client --req1--> server instance #1 session lives in memory (session created HERE) client --req2--> server instance #2 (load balancer sent it here -- this instance has NEVER heard of that session) FIX: session state -> Redis (or similar), not instance memory. any instance can then pick up any request.
→ this is the classic "worked in dev, broke at 3 replicas" bug.
09

The architect's lens — enterprise edition

The judgment calls that show up specifically once MCP leaves a single team's laptop and becomes shared infrastructure.

Pattern choice — don't over-pattern on day one

Start with a gateway and an adapter. Add the rest when pain shows up.

Of the five patterns, only two are load-bearing from the start in most orgs: a gateway (because auth/logging/routing shouldn't live in N places) and adapters for whatever legacy systems you can't avoid. Aggregators, proxies, and sidecars are answers to specific pains — don't build an aggregator until a client is actually stitching together three calls by hand.

The legacy adapter is the real project

Everyone budgets the gateway. Almost no one budgets the adapter correctly.

Wrapping a mainframe or a 15-year-old SOAP service in an MCP-shaped interface isn't a translation layer, it's an integration project with its own error taxonomy, its own retry semantics, and its own testing surface. If the enterprise architecture review only scrutinizes the shiny gateway and rubber-stamps "we'll just adapt the legacy system," that's where the schedule slips.

Multi-agent — the orchestrator is a single point of failure by design

Decide up front what happens when the orchestrator itself is wrong or down

An orchestrator pattern concentrates decision-making in one place, which is exactly what makes it debuggable — and exactly what makes it a bottleneck and a blast radius. Before shipping a multi-agent system, know the answer to: what happens to in-flight sub-agent work if the orchestrator crashes mid-delegation, and can a sub-agent's MCP server be called directly as an escape hatch.

Banking-specific — latency budgets aren't uniform across use cases

Don't put your KYC server's SLA on your trade-execution server

The same document lists fraud detection, KYC, and high-frequency trade execution side by side — but they don't share a latency budget. A KYC check tolerating 2 seconds is fine; an order-placement tool tolerating 2 seconds is a different SLA class entirely and probably shouldn't share infrastructure, connection pools, or even a transport choice with the rest of the estate.

  • Segment MCP servers by latency class, not just by domain
  • Trade-adjacent tools may justify a custom low-latency transport instead of default HTTP/SSE
  • Zero-trust auth on every call is non-negotiable — but measure its overhead against the latency-sensitive paths specifically
Versioning — the schema is a contract the moment a second team depends on it

Treat a tool's input schema like a public API from the day a second consumer shows up

A single team iterating on their own MCP server can change a tool's schema freely. The moment another agent, another team, or an external partner starts calling it, that schema is now a contract — silently widening a required field or renaming a parameter breaks every caller at once, often invisibly until a production incident traces back to it.
