Project 1 — Running ML Containers: JupyterLab + MLflow with Docker

Notes from the hands-on lab: pulling real ML tooling images, running them as containers with port mapping and persistent volumes, and connecting two separate containers (a notebook and an experiment tracker) to talk to each other. Structured as both a conceptual walkthrough and a command reference you can use directly at the terminal.
↗ Open on Udemy — Mastering AI/ML with Docker
Goal What This Project Actually Builds
▸

Two ML tools, run as containers instead of local installs, then connected to each other:

  • MLflow — experiment tracking (what algorithm, what hyperparameters, what evaluation metrics, per run)
  • JupyterLab — the actual notebook development environment where you write and run code

End state: a notebook running inside one container executes a training experiment and logs the results (metrics, model artifact) to an MLflow instance running in a separate container — two independently running, independently manageable pieces of infrastructure, talking to each other over a network connection, exactly like two microservices would.

Architect's Lens

This is a small-scale, local rehearsal of exactly the kind of service-to-service communication pattern you deal with across your 80+ microservices — one container's job isn't to know how the other was built, only how to reach it over a known port. Getting comfortable with this pattern locally (two containers, one connection) is the same mental model that scales up to production service mesh communication, just without the complexity of service discovery, load balancing, or TLS yet.

Anatomy Decoding an Image Name — It's Like a Fully Qualified Domain Name
▸ 
ghcr.io  /  mlflow  /  mlflow  :  latest
  │          │          │           │
registry   org/user   repo name    tag
(GitHub    (mlflow)   (mlflow)    (version)
Container
Registry)

Defaults when fields are omitted:
  registry  → docker.io       (Docker Hub, if unspecified)
  org/user  → library         (official Docker images)
  tag       → latest

Docker Hub isn't the only registry — GitHub itself now serves as a container registry (ghcr.io), a genuinely surprising fact for many, meaning GitHub is simultaneously a code host and an image registry. Both MLflow and the Jupyter notebook images used in this lab come from different registries (GHCR and Docker Hub respectively) — the four-part naming scheme is what makes that transparent and unambiguous regardless of source.

Active Recall: What are the four components of a fully-qualified image name, and what are the default values if the shorter fields are omitted? tap to reveal
Registry / organization-or-user / repository / tag. If unspecified, registry defaults to docker.io (Docker Hub), organization defaults to "library" (official images), and tag defaults to "latest".
Pulling Images Are Layered, Not Monolithic
▸ 
docker pull ghcr.io/mlflow/mlflow:latest

Watching the pull happen shows Docker fetching the image as multiple separate layers, not one giant file. Each layer roughly corresponds to a stage of the image's build (base OS, runtime, dependencies, application code) — meaning that upgrading just the application (MLflow itself) to a new version typically only requires re-downloading the top layer or two, while the OS and dependency layers stay cached and unchanged. This layering is why container image distribution is efficient at scale — versioned incrementally, not as full re-downloads every time.

Architect's Lens

This is directly the same principle behind the multi-stage Dockerfile from the AWS App Runner deployment in the Vercel production course — layer caching is why that Day 5 Docker build was "instant the second time" after the first full build. Understanding layers isn't trivia; it directly explains observed build/pull speed behavior you've already seen firsthand.

Active Recall: Why does upgrading just an application's version inside an image usually only require downloading 1-2 new layers instead of the whole image again? tap to reveal
Because images are built from layered, cacheable stages — the base OS, runtime, and dependency layers typically stay identical between versions, so only the layer(s) containing the actual application code that changed need to be re-downloaded; the unchanged layers are reused from what's already cached locally.
Running Port Mapping — Why You Can't Just Connect Directly to a Container
▸ 
Your laptop (Mac/Windows)
  └── Docker host (a lightweight Linux VM Docker creates)
        └── Container (running MLflow, listening on port 5000 INSIDE the container)

You (the browser on your laptop) can reach the Docker host VM,
but NOT the container directly — there's a boundary in between.

  -p 5555:5000
      │     │
   host   container
   port    port

"Traffic hitting port 5555 on my host gets forwarded
 to port 5000 inside the container."

This is called port mapping (or port forwarding). Without it, a service running inside a container is completely unreachable from outside — the container's internal network is isolated by design.

Active Recall: In `-p 5555:5000`, which number is the host port and which is the container's internal port? tap to reveal
5555 is the host port (what you connect to from your browser, e.g. localhost:5555) and 5000 is the container's internal port (what the application inside the container is actually listening on). The syntax is always host_port:container_port.
Running Attached vs. Detached — And Why -d Is What You Actually Want
▸ 
docker run -p 5555:5000 ghcr.io/mlflow/mlflow:latest mlflow server --host 0.0.0.0
  → runs ATTACHED: your terminal is now "stuck" showing the
    container's live logs. Ctrl+C doesn't just detach — it
    STOPS the container entirely.

docker run -d -p 5555:5000 --name mlflow ghcr.io/mlflow/mlflow:latest mlflow server --host 0.0.0.0
  → runs DETACHED (-d): container keeps running in the
    background, terminal is immediately free, container
    survives after you move on to other commands.

A crucial early lesson: attached mode's Ctrl+C is not a "step back" — it kills the container. Detached mode (-d) plus a readable --name (instead of Docker's auto-generated adjective-noun names) is the practical default for anything you want to keep running while you continue working.

Risk Flag — Easy Early Mistake

Running attached and pressing Ctrl+C thinking you're just "getting your terminal back" actually terminates the container. If you need your terminal back without stopping the service, you must run detached from the start (-d) — there's no clean way to detach from an already-attached foreground run without a separate detach key sequence that this course doesn't rely on; it just recommends always using -d for anything long-running.

Active Recall: What actually happens if you press Ctrl+C while attached to a container's foreground logs? tap to reveal
The container is stopped entirely — Ctrl+C in this attached mode doesn't just return you to your shell, it terminates the running process inside the container, which stops the container. This is why detached mode (-d) is the recommended default for anything meant to keep running.
Reference Container Lifecycle Command Cheat Sheet
▸
CommandWhat it does
docker psList only RUNNING containers
docker ps -aList ALL containers, running or stopped
docker ps -lShow only the most recently run container
docker ps -n 2Show the last N containers
docker start <name/id>Restart a stopped (not deleted) container — its data/state is preserved
docker stop <name/id>Gracefully stop a running container
docker rm <name/id>Delete a stopped container (permanently — unlike stop)
docker rm -f <name/id>Force-remove a container even if it's currently running
docker container pruneBulk-delete ALL stopped containers at once — use carefully
docker logs <name/id>View a container's output/logs
docker logs -f <name/id>Follow logs live (like `tail -f`) — Ctrl+C just exits the log view, doesn't stop the container
docker exec -it <name/id> shOpen an interactive shell INSIDE a running container

Architect's Lens

The distinction between stop and rm is the one most worth internalizing precisely: "exited" or "died" does NOT mean gone — a stopped container retains its filesystem state and can be restarted with docker start. Only rm actually deletes it. This matters operationally: if you're debugging a crashed container, don't reflexively `rm` it — `docker logs` on the stopped container first, since the evidence is still there until you explicitly delete it.

Containers can be referenced by full ID, container name, or even a unique ID prefix (e.g. docker start 799 works if no other container ID starts with those digits) — useful for quick terminal work without copy-pasting full IDs.

Active Recall: If a container shows as "Exited" in `docker ps -a`, is its data gone? tap to reveal
No — "Exited" just means the container is stopped, not deleted. Its filesystem state is preserved and it can be restarted with `docker start`. Data is only actually lost once the container is explicitly removed with `docker rm` (or `docker container prune`).
Persistence Volumes — Making Your Notebooks Survive Container Deletion
▸ 
mkdir -p ~/ml-docker/notebooks

docker run -d -p 8888:8888 --name notebook \
  -v ~/ml-docker/notebooks:/home/jovyan/work \
  jupyter/scipy-notebook
             │                          │
        host directory          container directory
      (survives container       (where Jupyter is
       deletion)                 configured to save
                                  notebooks — the "work" dir)

Without a volume mount, anything created inside a container disappears the moment that container is deleted — containers are meant to be disposable/replaceable, so persistent data must live outside them. The -v host_path:container_path flag bind-mounts a real directory on your machine into a path inside the container; files created in either location are immediately visible in the other, since it's the same underlying storage, not a copy.

On Windows specifically: relative paths (like ~ for home) don't work reliably — always use an absolute path for volume mounts there.

Architect's Lens

"Containers are disposable, data that matters lives outside them" is one of the most important operational principles in all of container-based infrastructure — it's the same reasoning behind why production databases run on managed persistent storage (EBS volumes, RDS) rather than inside ephemeral application containers. Getting this instinct right locally (notebooks in a mounted volume, not baked into the container) is good practice for the same discipline at production scale.

Active Recall: What happens to a notebook file saved inside a Jupyter container if that container is later deleted, WITHOUT a volume mount configured? tap to reveal
The file is permanently lost — containers are ephemeral by design, and anything written only to the container's own filesystem (not a mounted volume) disappears when the container is deleted. This is exactly why the -v volume mount to a host directory is used, so notebook files persist independently of the container's lifecycle.
Access Finding the Jupyter Access Token — Don't Guess, Check the Logs
▸

JupyterLab's container starts with token-based authentication enabled by default (a security measure) — the token isn't shown anywhere obvious; you have to check docker logs notebook, which prints a full URL with the token embedded (http://127.0.0.1:8888/lab?token=...). Visiting that exact URL (or copying just the token into the login prompt) is the only way in.

Active Recall: Where do you find the access token needed to log into a freshly-launched Jupyter container? tap to reveal
In the container's logs — running `docker logs ` prints a startup message containing the full access URL with the token embedded as a query parameter, which you either visit directly or copy the token from into the login page.
Connecting Two Containers Talking to Each Other — host.docker.internal
▸ 
Both containers run on the SAME laptop, but each is its own
isolated environment. From inside the Jupyter container, you
can't reach the MLflow container by "localhost" — that would
mean localhost INSIDE the Jupyter container itself, not your
actual machine.

Solution: host.docker.internal
  → a special DNS name Docker provides specifically so a
    container can reach services running on ITS HOST machine
    (including other containers' mapped ports).

mlflow.set_tracking_uri("http://host.docker.internal:5555")

This connects back to the same host port (5555) that was mapped to MLflow's container earlier — the Jupyter container reaches out through the host, to the mapped port, back down into the MLflow container. Two independently running, independently manageable containers, connected purely via network addressing — no shared filesystem, no special container-to-container link required.

Architect's Lens

host.docker.internal is a Docker Desktop convenience specific to local development — it does not exist the same way in a real Kubernetes or multi-host production environment, where service discovery is handled differently (DNS via service names, service mesh, etc.). Worth flagging explicitly: this exact hostname is a "local dev only" pattern, not something to hardcode into anything meant to run in production — a good example of where local-Docker convenience diverges from production container orchestration.

Active Recall: Why can't the Jupyter container simply use "localhost:5555" to reach the MLflow container? tap to reveal
Because "localhost" inside the Jupyter container refers to the Jupyter container's OWN internal network namespace, not the actual host machine — the two containers are isolated from each other's localhost. host.docker.internal is the special DNS name Docker provides specifically to let a container reach services on its host machine (including other containers' host-mapped ports) instead.
Code The Actual Experiment-Logging Code — What Each Line Does
▸ 
mlflow.set_tracking_uri("http://host.docker.internal:5555")  # where to send logs
mlflow.set_experiment("simple-linear-demo")                   # groups runs together

with mlflow.start_run():
    X, y = make_regression(n_samples=100, n_features=1, noise=10, random_state=42)
    model = LinearRegression()
    model.fit(X, y)

    y_pred = model.predict(X)
    mse = mean_squared_error(y, y_pred)

    mlflow.log_param("model_type", "LinearRegression")   # records a config value
    mlflow.log_metric("mse", mse)                          # records an evaluation number
    mlflow.sklearn.log_model(model, artifact_path="model") # saves the trained model itself

Each run inside the with mlflow.start_run(): block is automatically tracked as a distinct, timestamped experiment entry — visible in the MLflow UI with its parameters, metrics, and a downloadable model artifact (a pickled model file). Running the same notebook cell multiple times creates multiple separate tracked runs, letting you compare them side by side later.

Active Recall: What three distinct pieces of information does MLflow capture for each run in this example? tap to reveal
A logged parameter (the model type/configuration, via log_param), a logged metric (the evaluation score — mean squared error, via log_metric), and the trained model artifact itself (a downloadable, versioned pickle file, via log_model) — together giving a full record of what was run, how it performed, and the resulting model.
