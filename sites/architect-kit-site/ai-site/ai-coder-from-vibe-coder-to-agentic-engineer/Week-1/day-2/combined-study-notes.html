1. Context Engineering
🧠 Context Engineering — Architect's Recall → Visual Model

Based on the uploaded material, let's learn this as an AI architect, not as a list of definitions.

1️⃣ Recall First — Don't Look at the Answer Yet

Try to answer these mentally.

Q1 — The Stateless Problem

Suppose we have:

User → "My name is Ankur"

The LLM replies.

Five minutes later:

User → "What is my name?"

Question: If the LLM is stateless, where does the knowledge of "Ankur" come from?

Q2 — The Architect's Question

If:

OUTPUT = f(INPUT)

then what does this imply about the quality of the input?

Q3 — Prompt vs Context

Which is bigger?

Prompt Engineering
        VS
Context Engineering

And what additional things might exist in the context besides the user's prompt?

Q4 — Coding Agent

Imagine you give an AI agent this task:

"Implement payment retry logic in our Java service."

Would you give it only that sentence?

What else should the agent know?

Q5 — Tools

If the agent can use:

Git
Database
Python
File System
Web Search

How does the LLM know what these tools do and when/how to use them?

Q6 — The Dangerous Question

Suppose your model supports:

1,000,000 tokens

Does that mean:

"More context = better answers"?

Yes or No? Why?

Q7 — Coding Agent Memory

Why would a coding agent need something like:

AGENTS.md
CLAUDE.md
GEMINI.md

instead of relying entirely on the conversation?

Q8 — Context Explosion

Imagine this:

Conversation
   ↓
100 messages
   ↓
Tool outputs
   ↓
Generated code
   ↓
Reasoning
   ↓
Logs
   ↓
More files

What eventually becomes the problem?

2️⃣ Now Let's Build the Architecture

The Big Idea

The source makes one fundamental point:

                 ┌───────────────────────┐
                 │         INPUT         │
                 │       CONTEXT         │
                 └───────────┬───────────┘
                             │
                             ▼
                    ┌────────────────┐
                    │      LLM       │
                    │                │
                    │ Predict next   │
                    │ most likely    │
                    │ tokens         │
                    └────────┬───────┘
                             │
                             ▼
                 ┌───────────────────────┐
                 │        OUTPUT         │
                 └───────────────────────┘

Architect's takeaway:

The LLM can only reason over what you put into its context.

So:

Better Context
      ↓
Better Information Available
      ↓
Better Probability of Useful Output

1️⃣1️⃣ Bigger Context ≠ Better Context

This is one of the most important architectural lessons.

A common assumption:

More Context
     │
     ▼
More Information
     │
     ▼
Better Answer

But the actual behavior can look more like:

Context Size
     │
     │          ┌──────────
     │        /
     │      /
Quality   /
     │   /
     │  /
     │ /
     └──────────────────────
       ↑
       │
   useful context

              ↓
       too much noise

              ↓
       quality can degrade

So:

                 LESS
                  │
                  ▼
        ┌──────────────────┐
        │ Relevant Context │
        └────────┬─────────┘
                 │
                 ▼
              GREAT
             OUTPUT

is often preferable to:

                 MORE
                  │
                  ▼
        ┌──────────────────┐
        │ Everything       │
        │ Everywhere       │
        │ All at once      │
        └────────┬─────────┘
                 │
                 ▼
            INFORMATION
              NOISE
                 │
                 ▼
        POSSIBLE QUALITY DROP

Architectural principle:

Optimize for relevant context, not maximum context.

1️⃣2️⃣ Context Compaction — The "Compression" Event

Eventually:

Context

████████████████████████████████████████
████████████████████████████████████████
                 ↓
            Almost FULL

Instead of simply failing, systems such as coding agents can perform compaction.

        HUGE CONVERSATION
                │
                ▼
       ┌─────────────────┐
       │    COMPACTOR    │
       │                 │
       │ What matters?   │

       └────────┬────────┘

                ▼
        ┌───────────────┐
        │   SUMMARY     │
        │               │
        │ Key decisions │
        │ Important     │
        │ context       │
        │ Current state  │

                │
                ▼
       FREED CONTEXT SPACE
                │
                ▼
             CONTINUE
1️⃣3️⃣ Why Compaction Can Be Dangerous

Imagine the conversation contains:

100 decisions
   │
   ▼
Compactor
   │
   ├── remembers 95 ✅
   │
   └── misses 5 ❌

One of those five might be:

"NEVER modify the payment
 settlement table."

If that disappears...

Agent
  │
  ▼
"Let's modify settlement table."
  │
  ▼
💥 Architecture violation

That's why maintaining persistent project instructions can be valuable.

Conversation
     │
     │ temporary
     ▼
  Compaction
     │
     X
  details may disappear


AGENTS.md
     │
     │ persistent project guidance
     ▼
  Agent

The uploaded material also notes that compaction has improved substantially and is often worth trusting rather than automatically fighting it.

PART 2 — The Evolution of Trust 🚦

The easiest way to understand the entire topic is:

LESS TRUST
    │
    ▼
MORE HUMAN CONTROL
    │
    ▼
MORE TRUST
    │
    ▼
MORE AGENT AUTONOMY

The source describes six workflow levels, evolving from tight human control toward autonomous multi-agent systems.

1️⃣ Workflow #1 — MICROMANAGEMENT

This is:

"I don't trust you yet."

             HUMAN
               │
               ▼
        Detailed Prompt
               │
               ▼
            AGENT
               │
               ▼
          Small Change
               │
               ▼
        HUMAN REVIEWS
               │
        ┌──────┴──────┐
        │             │
       OK          NOT OK
        │             │
        ▼             ▼
      Next        Rewrite
                   Prompt
                     │
                     ▼
                  Restart

This is essentially:

Human = Driver
Agent = Very fast junior developer

You are constantly checking:

"Did you do exactly what I asked?"
2️⃣ Workflow #2 — PLAN → EXECUTE → REVIEW → TEST

Now we give the agent more freedom.

                 HUMAN
                   │
                   ▼
                 PLAN
                   │
                   ▼
             ┌─────────────┐
             │   EXECUTE   │
             └──────┬──────┘
                    │
                    ▼
                 REVIEW
                    │
                    ▼
                  TEST
                    │
                    ▼
                COMPLETE

But usually this happens phase by phase:

Phase 1
  ↓
Build
  ↓
Review
  ↓
Test
  ↓
✓

Phase 2
  ↓
Build
  ↓
Review
  ↓
Test
  ↓
✓

Phase 3
  ↓
...

Think of it as:

Human
  │
  ├── Defines direction
  ├── Reviews work
  ├── Validates tests
  └── Approves next phase

More trust, but still substantial human supervision.

3️⃣ Workflow #3 — SPEC-DRIVEN DEVELOPMENT

Now we move another step back.

Instead of repeatedly telling the agent what to do:

"Do this..."
"Now change this..."
"Actually, undo that..."
"Try this..."

we create a strong specification:

                SPECIFICATION
                     │
        ┌────────────┼────────────┐
        │            │            │
      Goal        Rules       Acceptance
                                Criteria
        │            │            │
        └────────────┼────────────┘
                     │
                     ▼
                   AGENT
                     │
                     ▼
               IMPLEMENTATION
                     │
                     ▼
                 VERIFY

The mindset becomes:

Trust, but verify.

You don't constantly watch the agent.

You return later and verify the result.

4️⃣ Workflow #4 — YOLO 🤖

Now we cross into the 2026-style autonomy described in the source.

YOLO means:

"Just go."

No constant approvals.

              HUMAN
                │
                │
             "Build it"
                │
                ▼
        ┌────────────────┐
        │     AGENT      │
        │                │
        │ Think          │

                │

               TRUST
                 │
                 ▼

                 │
                 ▼

The source describes this as a major increase in trust and notes that it has increasingly moved beyond hobby projects into real use cases.

5️⃣ Workflow #5 — RALPH LOOPS 🔄

Now things get really interesting.

An agent already operates internally in a loop:

       ┌───────────────┐
       │     AGENT     │
       └───────┬───────┘
               │
               ▼
             THINK
               │
               ▼
             TOOL
               │
               ▼
            OBSERVE
               │
               ▼
             ACT
               │
               └───────────┐
                           │
                           ▼
                         AGAIN

A Ralph Loop essentially puts this entire agent process inside another loop.

          OUTER LOOP
     ┌─────────────────────┐
     │                     │
     │     ┌───────────┐   │
     │     │   AGENT   │   │
     │     │   LOOP    │   │
     │     └─────┬─────┘   │
     │           │         │
     │           ▼         │
     │         RESULT      │
     │           │         │
     │           ▼         │
     │         TEST        │
     │           │         │
     │           ▼         │
     │       FEEDBACK      │
     │           │         │
     │           └─────────┤
     │                     │
     └─────────────────────┘

The magic is:

Agent
  ↓
Build
  ↓
Evaluate
  ↓
Feedback
  ↓
Agent AGAIN
  ↓
Build
  ↓
Evaluate
  ↓
Feedback
  ↓
Agent AGAIN
  ↓
...

So instead of:

Human feedback
      ↓
Agent

we increasingly get:

Agent
  ↓
Self-evaluation
  ↓
Feedback
  ↓
Agent
  ↓
Self-evaluation
  ↓
Feedback
  ↓
Agent

3. AGENTS.md — Field Manual
🧠 AGENTS.md — Your AI Agent's Field Manual

Let's learn this as an AI architect designing an agentic software system.

The key idea from the material is that AGENTS.md is not merely documentation. It is a way of injecting project-specific operating instructions into the agent's context.
