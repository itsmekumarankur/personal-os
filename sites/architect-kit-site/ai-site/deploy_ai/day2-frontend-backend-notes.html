Structured for a Senior Engineering Manager who already knows backend deeply and is filling in front-end gaps.

Fundamentals Front End vs. Back End — The Base Definitions
▸
  • Front end = code running in the user's browser: HTML (structure), CSS (appearance), JavaScript (interactivity — button clicks, animations).
  • Back end = business logic on the server: database access, calling LLMs, calling other APIs, holding secrets.

Two ways the back end is used:

Mode 1 — API mode
  Browser (front end) → hits a web endpoint (URL)
                       → back end runs logic, returns JSON
                       → front end updates the UI using that JSON

Mode 2 — Full page rendering
  Browser requests a URL (e.g. "/home")
                       → back end generates the ENTIRE HTML page
                       → sends the whole page back to the browser

Both modes will be used across the course's labs.

Architect's Lens

This is the classic client-server contract you've enforced for years in payments/demat systems — the interesting design decision is always which of the two modes a given screen should use. JSON-API mode suits highly interactive, stateful screens (a live portfolio dashboard); full-page rendering suits simpler, mostly-static, SEO-relevant screens (a marketing/landing page). Mixing both badly in one app is a common source of unnecessary complexity — worth asking, for every screen you design, which mode it actually needs before defaulting to "everything is an SPA."

Active Recall: What are the two distinct ways a back end can respond to a front-end request? tap to reveal
(1) Return a JSON object that the front end uses to update parts of the existing page (typical API call). (2) Generate and return an entire HTML page for a given URL, which the browser then renders in full.
Aside Where Does Gradio Fit? (And Why Not Use It Here)
▸

Gradio is technically a back-end (Python) framework, but it auto-generates the front end for you behind the scenes — you describe a UI purely in Python, and Gradio produces the HTML/CSS/JS. That makes it a "front end + back end in one," which is great for fast prototyping but is explicitly not used in this course, since the goal here is building real, separately-controllable front ends and back ends ("doing stuff for reals").

Question worth sitting with

  • For your own rapid-prototype needs (e.g. an internal Optimus dashboard or squad tracker demo), is Gradio still the right tool — fast to stand up but ultimately a dead end if the tool needs to graduate into a real customer-facing product later?
History The Three Eras of Front-End Development
▸ 
Era 1 — Vanilla web
  Hand-written HTML + CSS + JavaScript (maybe jQuery)
  JS manipulates the DOM (Document Object Model — the browser's
  live in-memory representation of the rendered page) directly

Era 2 — JS Frontend Frameworks
  React, Vue, Angular, Svelte, ...
  Build UIs from small reusable "components"
  Most commonly used to build a Single Page Application (SPA):
  the whole app loads once, then all navigation is just API calls
  re-rendering parts of that same page — not real page reloads

Era 3 — Application Frameworks (built ON TOP of a framework)
  Next.js (built on React, by Vercel) — bundles routing,
  data-fetching, server-side rendering, and more, "out of the box"
  so you don't have to hand-pick a dozen React add-ons yourself

Architect's Lens

This progression mirrors backend framework evolution almost exactly — vanilla HTTP handlers → micro-frameworks (Flask-like) → opinionated "batteries-included" frameworks (Django/Next.js-like). The underlying architectural lesson: opinionated frameworks trade flexibility for fewer decisions and faster onboarding — the same trade-off you weigh every time a squad picks a new internal framework at IDFC versus rolling their own.

Active Recall: What does SPA (Single Page Application) actually mean, mechanically? tap to reveal
The entire front-end application code loads once on the first URL hit. After that, even though it feels like the user is navigating between different pages, it's really the same loaded React app making API calls and re-rendering parts of itself — no full browser page reload happens.
React Core React Concepts — Declarative UI, Props, State
▸
  • Component-based: each component packages its markup, styling, and logic together; you assemble UIs by composing components.
  • Declarative: you describe what the UI should look like for a given state — you don't write step-by-step DOM-mutation instructions.
  • Reconciliation: React diffs the DOM before/after a state change and updates only what changed — no full-screen redraw.
  • Props (properties): data passed down from parent components to children, controlling how they render.
  • State: the mutable data a component owns and manages; React re-renders automatically when state changes.
  • JSX / TSX: a hybrid syntax mixing HTML-like markup directly into JavaScript/TypeScript — replaces the older, clumsier pattern of building markup as raw strings inside JS.
  • Component libraries: pre-built suites of components (Material UI, Chakra) you can drop in rather than build from scratch.

Architect's Lens

Declarative UI + automatic diffing is the same conceptual shift distributed systems went through with declarative infra (Terraform/Kubernetes) vs. imperative scripts — you describe the desired end state, and the framework/tool figures out the minimal diff to get there. Recognizing that pattern once makes it much faster to pick up in a new domain, which is exactly the kind of transferable mental model worth calling out to your squads when they hit React for the first time.

Question worth sitting with

  • Given your systems background, is "React's reconciliation = Kubernetes reconciliation loop, just for DOM instead of pods" a good enough analogy to teach your team React faster?
Active Recall: What's the difference between props and state? tap to reveal
Props are data passed DOWN into a component from its parent, controlling how it renders — the component doesn't own or change them. State is data a component owns itself and can change; when it changes, React automatically re-renders the affected UI.
Next.js Why Next.js, and the Two Router Systems
▸

Next.js is built by Vercel (same company as yesterday's deployment platform) on top of React, and bundles routing, data fetching, server-side rendering, TypeScript transpiling, and JS bundling out of the box — so you're not hand-assembling a dozen separate libraries.

Pages RouterApp Router
Folderpages/app/
MaturityOlder, most trusted, widest supportNewer, more powerful, now Next.js's official recommendation
Used whenWeek 1 (chosen because the course's auth framework only supports Pages Router)Introduced Week 2 for exposure

Other Next.js mechanics worth knowing: transpiling converts modern TypeScript into vanilla JavaScript browsers can run; bundling packs that output efficiently for delivery. The course uses client-side rendering (the more traditional, simpler approach) rather than server-side rendering, though SSR exists and is increasingly common.

Architect's Lens

Notice the instructor picked Pages Router not because it's "better" in the abstract, but because a specific dependency (the auth framework) forced the decision — and he explicitly admits getting burned by building it in App Router first and having to rip it out. That's a useful, honest data point: framework/router choice in real projects is often driven by your weakest-link dependency, not by which is objectively newer or more powerful. Worth remembering next time a squad wants to adopt the "newest recommended" pattern without first checking whether every dependency actually supports it.

Questions worth sitting with

  • When your own team evaluates a new library/pattern for idfc-coder tooling, is there a step that explicitly checks "does every dependency we need actually support this," or does that only surface after the fact, the way it did here?
Active Recall: Why does the course start Week 1 with the Pages Router instead of the newer, officially-recommended App Router? tap to reveal
Because the authentication framework being used only supports the Pages Router — the instructor discovered this the hard way after building everything in App Router first and having to pull it all out and rebuild.
Backend Python Backend Frameworks — Django vs. Flask vs. FastAPI
▸
FrameworkPhilosophyNotes
Django"Batteries included" — heaviestBuilt-in ORM, auth, templating, even an admin UI
FlaskMicro-framework — lightestJust routing + request handling; you pick everything else
FastAPIModern middle groundAsync-first, built on Starlette + Pydantic, schema-driven routes — used throughout this course

Architect's Lens

This is a textbook build-vs-batteries-included spectrum, and FastAPI's popularity is largely because Pydantic gives you request/response schema validation "for free" at the framework level — directly relevant to any fintech API surface where malformed input has real financial consequences. Worth comparing against whatever's standard for new microservices on your Wealth/Demat platform today: is validation happening at the framework boundary the way FastAPI+Pydantic enforces it, or is it scattered across handler code?

Active Recall: What two underlying libraries is FastAPI built on, and what does each contribute? tap to reveal
Starlette (the async web toolkit underneath, handling requests/responses) and Pydantic (schema validation for request/response objects — the same library used heavily across agent/LLM frameworks).
Course Admin Repo Strategy — One Repo Per Week, Not One Repo For the Course
▸ 
production   (main repo — cloned once)
  └── week1/                (Day 1 instructions — used yesterday)

SaaS         (new repo, built from scratch today)
  ├── guides/                self-study docs (Docker, front end, etc.)
  ├── community-contributions/   markdown write-ups + PRs from students
  └── (app code)

Unlike his previous single-repo courses, this course spins up a separate repo per week — deliberately mirroring real production practice: one repo = one deployable application, which is also required for GitHub Actions to auto-deploy on push. Monorepos are acknowledged as a valid alternative but intentionally avoided here to keep things simple.

Architect's Lens

"One repo per deployable app, mainly to keep CI/CD simple" is a completely reasonable default for a teaching context, but it's worth noting explicitly for your own team: the monorepo-vs-polyrepo decision at IDFC across 80+ microservices is a much higher-stakes version of this same trade-off — deployment isolation and blast-radius control (polyrepo) vs. atomic cross-service changes and shared tooling (monorepo). Good to keep this simple teaching example in mind as the "why polyrepo" baseline case when explaining the trade-off to less experienced engineers.

Questions worth sitting with

  • Does your Wealth/Demat platform's current repo strategy (polyrepo across 80+ microservices) have the same "one repo = one deployable, CI/CD drives the boundary" rationale, or has it evolved for different reasons over time?
