Week 1 · Day 1 — "Instant Gratification": Ship First, Learn Why Later

Notes from Ed Donner's opening lecture of the "Gen AI & Agentic AI in Production" course. Structured for a Senior Engineering Manager evaluating this as both a learning path and a hiring-manager signal — not just a transcript summary.
↗ Open on Udemy — Generative and Agentic AI in Production (Lecture 52442087)
Framing Why "Deploy First, Explain Later"?
▸

Donner deliberately skips the usual objectives/curriculum/logistics opener. Day 1 minute 1 is a live Vercel deployment of a Python FastAPI app — before any AI concept is even mentioned. The pedagogical bet: a working URL in your browser in the first 20 minutes beats a slide about "what you'll learn."

Architect's Lens

This is the same instinct behind a "walking skeleton" in software architecture — get a thin, ugly, end-to-end path into production before you add any real logic. It de-risks the deployment pipeline early, so that when Week 4's multi-agent capstone breaks, you're debugging agent logic, not rediscovering that your Vercel routes were misconfigured all along.

Questions worth sitting with

  • In your own team's onboarding at IDFC — does a new engineer get something live in production (even a "hello world" microservice) on day one, or do they spend week one reading wiki pages first?
  • Could this "walking skeleton first" approach be applied to your Optimus Project rollout — i.e., get one squad shipping via idfc-coder end-to-end before writing the full playbook?

Pipeline The Deployment Stack, Step by Step
▸

The toolchain assembled in real time:

GitHub repo (instructions)
   └── Vercel account (cloud host, "sign up is one click from first deploy")
         └── Cursor IDE (VS Code fork — any IDE works)
               └── local project folder "instant"
                     ├── instant.py        (FastAPI app)
                     ├── requirements.txt  (fastapi, uvicorn → later + openai)
                     └── vercel.json       (build + routing config)
                           └── Node.js (installed, npm confirms via --version)
                                 └── npm i -g vercel  (CLI installed)
                                       └── vercel login
                                             └── vercel .   (deploy!)

Architect's Lens

Notice vercel.json maps all incoming routes to a single Python module (instant.py). That's a serverless-function pattern — Vercel spins up your FastAPI app as a function-per-request, not a long-running server. Good for near-zero idle cost; something to watch if you later need persistent connections (websockets, long-lived DB pools) since serverless functions are stateless and short-lived by design.

Questions worth sitting with

  • Vercel's serverless model trades cold-start latency for near-zero idle cost — where does that trade-off break down for a fintech workload like yours (e.g. demat order placement, KYC callbacks)?
  • What's the equivalent "5-minute deploy" story for idfc-coder — could a new BA/TL see a live artifact within their first working session with it?
Active Recall: What does vercel.json actually configure? tap to reveal
Two sections — "builds" (tells Vercel to build instant.py as the deployable unit) and "routes" (tells Vercel to route all incoming requests to that same Python module).
Security The "Production" URL Isn't Really Public Yet
▸

First deploy is gated by Vercel Authentication (Deployment Protection) — only the signed-in Vercel team can view it, even though it has a public-looking URL. Donner manually disables this in Project Settings to make it visible to anyone (verified via an incognito window).

Architect's Lens

This is a good, small, real example of a secure-by-default platform choice — new deployments are private until a human explicitly opens them up. Worth noting for your own team: does your internal idfc-coder tooling default new environments to locked-down access, or does it default open and rely on someone remembering to lock it down later? Secure-by-default is cheaper to enforce than secure-by-review.

Questions worth sitting with

  • What's your team's default posture for newly spun-up microservices at IDFC — locked down until reviewed, or open until flagged?
AI Layer Adding the First LLM Call
▸

Part 2 wires OpenAI into the same app:

  • Get an OpenAI API key (platform.openai.com), pre-fund $5, disable auto-recharge as a spend guardrail.
  • Store the key as a Vercel environment variable via vercel env add OPENAI_API_KEY — applied to all three environments (dev/preview/production), never hardcoded in the repo.
  • Add openai to requirements.txt — explicitly not an "LLM", just an open-source HTTP client wrapper that also works against many other providers using the same interface.
  • Code calls client.chat.completions.create() with model gpt-5-nano (the lightest/cheapest tier), one user-role prompt, returns response.choices[0].message.content.

Architect's Lens

Two things worth flagging for a fintech context: (1) storing secrets as platform env vars rather than in code/repo is the bare minimum — your IDFC environment likely has a secrets manager or vault; this Vercel pattern is the "toy" version of that same discipline. (2) The OpenAI Python SDK being provider-agnostic in shape (same interface works for many LLM vendors) is exactly the abstraction you'd want if you're evaluating multi-LLM vendor lock-in risk for Optimus — same client code, swap the base_url/model, minimal blast radius if you ever need to switch providers.

Questions worth sitting with

  • If idfc-coder or a future internal tool needs an LLM call, what's your bank's approved pattern for secret storage — and does it map cleanly onto this "env var per environment" model?
  • Given your multi-LLM bootcamp work — is "same SDK shape, swap the provider" a pattern you can formalize into a reusable internal wrapper for Optimus, so squads aren't hand-rolling provider-specific code?
Active Recall: Why does Donner insist the OpenAI Python package "contains no LLM code"? tap to reveal
Because it's just a convenience HTTP client — it builds a web request and parses the JSON response into Python objects. The actual model/intelligence lives entirely on OpenAI's servers, not in the library.

Cost Governance API Spend — Pay-as-you-go vs. Enterprise Cloud Billing
▸

Expected total course spend: ~$5–10 (mostly OpenAI, small AWS charges), plus optional domain registration. Key distinction he draws:

  • OpenAI: pre-paid drawdown model — you can't overspend beyond what you've funded.
  • AWS / GCP / Azure: no hard spending ceiling — a card is on file, usage accrues, and you're responsible for setting your own budget alerts and quotas. There's no built-in floor below which billing simply stops.

Architect's Lens

This is a real and recurring cost-governance gap in cloud-native orgs, not just a beginner's tripwire — enterprises solve it with budget alerts, tagging + chargeback, and hard service quotas, but the underlying billing model is the same "no ceiling" one Donner describes. Worth asking whether your own Optimus/idfc-coder rollout has equivalent guardrails defined before squads start calling LLM APIs at scale internally.

Mindset Debugging Environment Issues — Root Cause vs. Band-Aid
▸

Roughly 80% of student frustration on this kind of course comes from environment/setup issues (typos in .env keys, region-string typos, architecture mismatches when a binary built on Mac is deployed to AWS Lambda), not from AI concepts themselves.

The one genuinely useful technique called out: when using an LLM to debug a stack trace, it will tend to patch the symptom rather than question the root cause. His own example — a Mac-built binary failing on Lambda threw a "pydantic" error; the LLM's advice chased the pydantic symptom for a long detour before he stepped back and asked "why would this only fail on deploy, not locally?" — which pointed at the real cause (CPU architecture mismatch), not the reported one.

Architect's Lens

This is a textbook "five whys" failure mode, just mediated through an LLM instead of a junior engineer's first guess. The fix isn't "don't use LLMs to debug" — it's constantly re-inject the constraint that's ruled out ("this works locally, so it can't be a code logic issue") so the model's search space narrows toward environment/infra causes instead of application causes. Same discipline you'd expect from a senior engineer pairing with a junior one.

Questions worth sitting with

  • Have you seen this same "LLM patches the symptom, not the root cause" pattern show up in idfc-coder usage across your squads — and if so, is it worth adding an explicit prompt-template rule ("state what's ruled out before asking for a fix") to your Optimus prompt library?
Active Recall: What was the actual root cause of the "pydantic" error, and why did the LLM's first advice miss it? tap to reveal
A CPU/system architecture mismatch — a binary built locally on a Mac was deployed to AWS Lambda's different architecture. The LLM chased the surface-level pydantic error message instead of questioning why the same code worked fine locally, which was the clue pointing to an environment/architecture issue rather than an application bug.
