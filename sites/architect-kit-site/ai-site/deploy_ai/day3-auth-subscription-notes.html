Auth Why Clerk, and What JWT Is Doing Under the Hood
▸

Clerk is chosen as a lightweight, powerful auth platform (AWS has its own more sophisticated built-in user auth, but isn't used here). Users sign in via email or social auth (Google, GitHub, Apple). Under the hood, Clerk issues a JWT (JSON Web Token) that the front end attaches to backend requests to prove "this is a signed-in user" — treated deliberately as a black box for this course ("ask ChatGPT if you want the deep dive").

Architect's Lens

The instructor's choice to explicitly not go down the JWT rabbit hole is itself a useful signal: for a demo/teaching app, trusting a managed IAM provider's token issuance is fine. In a regulated fintech context, though, this is exactly the boundary you can't treat as a black box — token expiry/rotation policy, audience/issuer validation, and where the JWT secret material lives are all things your team would need to own explicitly, not delegate blindly to a third-party's defaults.

Active Recall: What mechanism does the front end use to prove to the back end that a request comes from a signed-in user? tap to reveal
A JWT (JSON Web Token) issued by Clerk, attached to backend requests, which the FastAPI backend verifies using the fastapi-clerk-auth library before allowing access to protected routes.
Setup Wiring Clerk Into the App — The Steps
▸ 
1. Create Clerk account → sign up (Google/GitHub) → Clerk dashboard
2. Create application "SaaS" → choose sign-in methods (email, Google, GitHub)
3. Install SDKs:
     npm install @clerk/nextjs        (front end)
     npm install fetch-event-source   (streaming, by Microsoft)
4. Collect 3 keys from Clerk dashboard → Configure → API Keys:
     NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY   (safe to expose client-side)
     CLERK_SECRET_KEY                    (server-side only)
     JWT verification URL                (used by the backend)
5. Store all 3 in .env.local (auto-covered by .gitignore — never pushed to the repo)
6. Wrap the whole app in <ClerkProvider> inside _app.tsx
7. Create a protected route: pages/product.tsx (only for logged-in users)
8. Rebuild pages/index.tsx as a public landing page using Clerk's
   <SignedIn> / <SignedOut> components — Clerk decides which renders
9. Backend: add fastapi-clerk-auth to requirements.txt
   → route now requires valid credentials before executing
10. Push the same 3 keys to Vercel: vercel env add ... (×3, all environments)
11. Test locally: vercel dev  (runs the JS/Next.js part only — Python
    backend does NOT run locally this way, so LLM calls can't be tested locally)
12. In Vercel → Settings → Deployment Protection: turn OFF Vercel's own
    auth wall, since Clerk is now the auth layer — don't stack two auth systems
13. vercel --prod → deploy

Risk Flag

Two very "one typo away from disaster" moments are called out explicitly: (1) the three env var names must match exactly what Clerk expects, or auth silently breaks; (2) forgetting to disable Vercel's own Deployment Protection after adding Clerk means visitors hit Vercel's auth wall before ever reaching Clerk's — a classic "two authentication layers stacked without realizing it" misconfiguration.

Architect's Lens

Step 12 is a small but real lesson in layered-security bookkeeping — when you introduce a new auth layer, you must also audit and retire whatever the previous layer was doing, or you end up with silent double-gating (annoying) or, worse, a forgotten permissive layer nobody remembers to check (dangerous). Worth a mental checklist item any time IDFC introduces a new auth/session layer on top of an existing one across your 80+ microservices: "what does this replace, and did we actually turn the old thing off?"

Questions worth sitting with

  • Where in your own systems might two access-control layers currently be silently stacked because nobody explicitly retired the older one after a newer one was introduced?
Active Recall: Why does vercel dev not let you fully test the app locally? tap to reveal
Because vercel dev only runs the JavaScript/Next.js front-end part locally — it does not run the Python FastAPI backend locally, so anything depending on the backend (like the LLM call) can't be tested that way; you can only verify the Vercel connection and front-end auth flow.
Billing Adding Subscriptions — Clerk Billing
▸

Clerk doubles as a billing platform, either through its own built-in Clerk payment gateway (used here, test mode only) or by connecting a real Stripe account for production payments. Setup: Clerk dashboard → Configure → Subscription Plans → create a plan (name, key like premium_subscription — underscores only, no hyphens — monthly price, optional annual discount).

Front end (product.tsx):
  <Protect plan="premium_subscription" fallback={...pricing table...}>
     ...idea generator UI...
  </Protect>

  → If subscribed: idea generator renders
  → If not: Clerk-generated pricing table renders instead (auto-priced
    correctly — unlike the hardcoded price on the landing page, which
    the developer must manually keep in sync)

Risk Flag

The landing page's pricing display is hand-written and can drift out of sync with the actual Clerk-configured price (exactly what happens in the demo — $100/month configured in Clerk, but a stale number shown on the public landing page). The <Protect> component's own fallback pricing table, by contrast, is generated live from Clerk's config and can't go stale.

Architect's Lens

This is a "single source of truth" lesson in miniature — any place you hardcode a value that's also defined authoritatively somewhere else (a price, a rate, a limit) is a guaranteed future inconsistency bug. The fix here is simple: prefer the live-generated component over the hand-written one wherever both exist. Same principle applies to things like interest rates or fee schedules shown in multiple places across your Wealth/Demat surfaces — one canonical source, everything else reads from it.

Question worth sitting with

  • Are there any hardcoded values in IDFC-facing UIs today (fees, rates, limits) that have a canonical source elsewhere and could silently drift the same way this demo's landing-page price did?
Active Recall: What's the difference between Clerk's built-in payment gateway and connecting Stripe? tap to reveal
Clerk's built-in gateway is the simple, out-of-the-box option (used here, in test mode) — no external payment provider needed. Connecting Stripe is the more sophisticated option for real production payments if you already use or want Stripe specifically; both are accessed through the same Clerk billing configuration.
Verification The End-to-End Test — Two Personas
▸

Two flows were verified live in production:

  • Existing subscriber (Google sign-in, already subscribed from earlier testing) → straight through to the idea generator, no payment prompt.
  • Brand-new user (signed up fresh via Apple ID) → hit the pricing table → chose the plan → paid with a Clerk test card → payment confirmed → access granted.

A subtle detail: signing in via Apple with the same underlying Gmail address that was already used for Google auth would have been recognized by Clerk as the same person (account linking by email) — the instructor had to use "Hide My Email" specifically to force a genuinely new, distinct user for the test.

Architect's Lens

That account-linking behavior — Clerk silently merging identities that share an email across different social-auth providers — is worth flagging as a design decision with real implications: convenient for users, but it means "provider used to sign in" isn't a reliable way to distinguish accounts if identity linking is on. If your own systems ever integrate multi-provider social auth, this is exactly the kind of default behavior to test for explicitly rather than assume.

Active Recall: Why did the instructor need to use "Hide My Email" when testing Apple sign-in? tap to reveal
Because Clerk automatically links accounts that share the same underlying email address across different social-auth providers. Since his Apple ID resolved to the same Gmail address already used for Google sign-in, Clerk would have treated it as the same existing user rather than creating a genuinely new one — so he hid the email to force a distinct new-user test.
Big Picture What Clerk Just Saved You (And What It Hides)
▸

Explicit framing: hand-building social login + Stripe billing from scratch used to be a multi-month, multi-engineer project. Clerk collapsed the auth portion to roughly one lecture and the billing portion to a second. The summarized request flow for /product:

1. User hits /product
2. Clerk checks subscription status (via the JWT + backend credential check)
3. No subscription → <Protect> renders Clerk's live pricing table
4. User subscribes → Clerk billing handles payment (test card or real Stripe)
5. Subscribed → idea generator UI renders
6. User can self-manage their subscription later via Clerk's account UI

Architect's Lens

The speed here is real, but it's speed bought by fully outsourcing identity and payment trust boundaries to a third party. That's a completely reasonable trade for a demo or an early-stage SaaS — but worth naming explicitly as a build-vs-buy decision with real long-term lock-in: your user identity graph and your payment/subscription data now live in Clerk's system, not yours. For a regulated institution, that's precisely the kind of dependency that needs its own risk review (data residency, vendor lock-in, exit strategy) before it goes anywhere near production — a good contrast case to bring up if this course's "just use Clerk" framing ever gets pitched internally as a pattern for anything beyond a prototype.

Questions worth sitting with

  • If a squad proposed "just use Clerk" for a real IDFC-facing product, what would your first three questions be — data residency, vendor exit strategy, and audit/compliance controls being the obvious candidates? What else would you add?
