AI Resume & Cover Letter Assistant — Pydantic + OpenAI/Gemini

Notes from a hands-on project — a pipeline that compares a resume against a target job description, identifies gaps, generates a tailored resume with tracked changes, and drafts a matching cover letter, using Pydantic for structured output and both OpenAI and Gemini as swappable backends. Structured for a Senior Engineering Manager who is actively job hunting — this project maps directly onto your own Sarvam AI / PhonePe / Razorpay applications, not just an abstract exercise.
Framing What This Tool Actually Does — And the One Rule That Matters Most
▸
Think First: this tool can write "increased revenue by 30%" on your resume in one second. If you never told it that number, where did it come from — and what does that tell you about the ONE rule you must follow before using any of its output? tap to reveal
It made it up. LLMs generate plausible-sounding numbers to sound impressive — not because they know your actual achievements, but because confident, specific-sounding text is what they're good at producing. The one rule: never submit an AI-written metric unless YOU can personally verify it's true and you actually did it. Submitting a fabricated number is both unethical and a real risk if an interviewer asks you to walk through it. The tool's job is to suggest phrasing and flag gaps — verifying facts is entirely on you.

What it does, in three steps: old resume + target job → (1) find the gaps (what's missing, what matches, what's a hidden strength) → (2) rewrite the resume with tracked changes → (3) write a matching cover letter.

Rough Sketch

 old resume  +  job description
         |
         v
 STEP 1: GAP ANALYSIS
   what's missing?  what already matches?  what's a hidden strength?
         |
         v
 STEP 2: REWRITE RESUME  (+ a visible diff of every change)
         |
         v
 STEP 3: WRITE COVER LETTER  (tone-matched to the company)
         |
         v
 output ready ... BUT every number in it is a DRAFT, not a fact

 THE RULE, in one line:
   AI writes the WORDS.  YOU verify every NUMBER.
   never submit a metric you can't personally stand behind

The Non-Negotiable Rule

Every generated metric ("increased X by 30%") is invented to sound impressive — none of it is real unless you already did it. Submitting a number you can't back up is both unethical and risky if an interviewer asks about it. Use the tool to improve phrasing and spot real gaps — you verify every specific claim before it goes anywhere near a real application.

Architect's Lens

Think First: you're actively applying to Sarvam AI, PhonePe, Razorpay — companies that will absolutely probe any specific claim on your resume. Given that, is this tool actually SAFER or RISKIER to use than writing your resume by hand? tap to reveal

Neither, automatically — it depends entirely on discipline. Used carelessly it's riskier, because it can generate a confident, specific-sounding number faster than you can fact-check it, and confident fabrication is exactly what an experienced interviewer at an AI-focused company will probe hardest. Used deliberately — as a phrasing and gap-finding tool, with every number replaced by your own verified data — it's genuinely useful and arguably safer than hand-writing, since the gap analysis surfaces things you might have under-sold. The tool doesn't change the risk; your discipline applying it does.

Pydantic 101 Why Structured Output Validation Matters
▸
Think First: before Pydantic, you'd just ask the LLM in plain English for "a JSON object with name, age, email." What could go wrong with that approach that a strict schema fixes? tap to reveal
Plain-English instructions are a request, not a guarantee — the model can still return age as the string "thirty" instead of 30, forget the email field, or wrap the JSON in extra prose. Your code then either crashes downstream or silently works with bad data. Pydantic turns "please return this shape" into "return this shape or get an explicit error right now" — catching the problem at the boundary instead of three steps later in your pipeline.
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int
    email: str

User(name="Mira Hero", age=30, email="mira@gmail.com")   # ✓ valid
User(name="Mira", age="not a number", email="...")        # ✗ raises
                                                            #   a validation error

Rough Sketch

 PLAIN DICTIONARY                      PYDANTIC MODEL
 -----------------                     ---------------
 dict = {"age": "banana"}              User(age="banana")
       |                                     |
       v                                     v
 accepted silently                     ✗ VALIDATION ERROR, right away
 (breaks later,                        (breaks HERE, loud and clear,
  somewhere else,                       exactly where the bad data
  hard to trace)                        entered the system)

 the blueprint:
   class User(BaseModel):
       name: str     <- must be text
       age: int      <- must be a whole number
       email: str    <- must be text

 wherever untrusted/generated data enters your system
 (an API request, an LLM's reply) -- put a Pydantic
 blueprint right at that boundary

Pydantic defines a data "blueprint" from Python type hints, then checks any data assigned to it — clear error instead of silently accepting bad data.

Architect's Lens

Think First: you already used Pydantic for FastAPI request validation in the Vercel course — checking data coming IN to an API. Here it's checking data coming OUT of an LLM. Is that really the same problem, or a different one wearing the same solution? tap to reveal

Genuinely the same problem: untrusted data crossing a boundary into your system. An API request from an unknown caller and an LLM's generated reply are both "data you didn't fully control the shape of," arriving at the edge of your code. The direction (in vs. out) doesn't change the fix — schema validation at that boundary, not manual parsing or hoping for the best. Worth recognizing this as one unified pattern rather than two separate skills, so the instinct to reach for Pydantic fires the same way regardless of which direction the untrusted data is flowing.

Integration Getting Structured JSON Directly From OpenAI
▸
Think First: section 2 showed Pydantic catching bad data AFTER it arrives. Here, the same Pydantic model gets handed straight to OpenAI's API call. What's the difference between "validate after" and "enforce during"? tap to reveal
"Validate after" means the model can still generate malformed JSON, and your code catches it once it lands. "Enforce during" — what response_format=Destination does — means the API itself constrains generation to match the schema, so you get guaranteed-structured output back, not "output you then have to hope parses correctly." Same schema, two very different guarantees: one catches problems, the other prevents them.
class Destination(BaseModel):
    city: str
    country: str
    top_attractions: list[str]

response = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[...],
    temperature=0,
    response_format=Destination      # ← the Pydantic model itself
)

 OLD WAY                              NEW WAY
 --------                             -------
 prompt: "please return JSON          response_format=Destination
 with city, country,                        |
 top_attractions"                           v
        |                             OpenAI CONSTRAINS its own
        v                             output generation to match
 free text back                       that exact schema
        |                                   |
        v                                   v
 you PARSE it yourself                guaranteed-structured reply
 and HOPE it matches                  back, every time
 (sometimes it won't)

 list[str] field  -->  tells the model "return a LIST here,
                        not a single string" (top_attractions)

The .beta.chat.completions.parse() call takes a Pydantic model directly as response_format — OpenAI's own generation is constrained to match that schema.

Design A Dual-Purpose Generate Function — Plain Text or Structured
▸
Think First: this one function can return either plain text OR a structured object, depending on one optional argument. Why not just write two separate functions — one for each — instead of branching inside one? tap to reveal
Two functions means two things to remember, document, and keep in sync whenever the underlying LLM call logic changes — near-duplicate code drifting apart over time. One function with an optional response_format parameter keeps a single, simple call surface: callers who don't need structure just omit the argument and get sensible defaults; callers who do need it pass a schema. Same underlying logic, one place to maintain it.
def openai_generate(
    prompt: str,
    model: str = "gpt-4o",
    temperature: float = 0.7,
    max_tokens: int = 1500,
    response_format: dict | None = None
) -> str | dict:
    if not response_format:
        # plain chat.completions.create(...)
        ...
    else:
        # structured .beta.chat.completions.parse(...)
        ...

Rough Sketch

 openai_generate(prompt, ...)
              |
              v
      response_format given?
         /            \
       NO              YES
        |                |
        v                v
  plain text call   structured .parse() call
  (chat.completions   (schema-enforced)
   .create)
        |                |
        v                v
   returns str      returns dict/object

 defaults:  model="gpt-4o", temperature=0.7, max_tokens=1500
 caller only overrides what's DIFFERENT from the default
 (same "sensible defaults" pattern as FastAPI/LangChain)

One function, two behaviors, picked by whether response_format was passed — defaults mean callers only specify what's different from the norm.

Architect's Lens

Think First: if you were wrapping this exact pattern for Optimus, where would "one function, two behaviors" stop being clean and start being a hidden trap for the next engineer who reads it? tap to reveal

It stays clean as long as the branch is shallow and the two behaviors are close cousins — same provider, same call shape, just structured vs. not. It becomes a trap the moment someone adds a THIRD behavior via another optional flag, then a fourth — now the function silently does five different things depending on which combination of arguments got passed, and nobody can read the signature and know what they'll get back. The pattern is worth lifting directly for a wrapper like this, but the discipline that keeps it clean is: one clear branch, well-documented, and a hard stop before it becomes a maze of optional parameters.

Comparison OpenAI vs. Gemini — Same Prompt, Different Providers, Different Results
▸
Think First: same prompt, same instruction, sent to both OpenAI and Gemini. If the two came back with genuinely different numbers for "blog posts written," what does that alone prove about whether either number is real? tap to reveal
It proves neither number came from real data — if both models had access to your actual achievements, they'd converge on the same figure. Two different confident-sounding numbers (100 vs. 50) for the same vague bullet is a direct, visible demonstration that both are invented to sound plausible, not recalled facts. This is the fabrication problem from Section 1, caught red-handed by simply asking twice.

Two near-identical functions (openai_generate, gemini_generate) — same prompt, different providers. Live test findings:

Architect's Lens

Think First: OpenAI caught the extra instruction once, missed it on an identical re-run. If you were building an Optimus pipeline that MUST always follow a specific instruction, would picking "the more reliable model" actually solve this problem? tap to reveal

No — because the problem isn't that one model is worse, it's that no single LLM call is fully deterministic even at fixed settings. Picking Gemini over OpenAI here might reduce the miss rate, but it doesn't eliminate it, and today's "more reliable" model can regress on a future update. The real fix is structural, not a model choice: explicit output validation (Pydantic again — did the required field actually appear?) or a retry/self-check step that catches a missed instruction and re-runs, rather than trusting any single generation to comply every time.

Core Logic The Gap Analysis Function — The Heart of the Tool
▸
Think First: this prompt asks for four sections — requirements, matches, gaps, AND potential strengths. Why not just "gaps"? What does a resume tool miss if it only ever looks for what's missing? tap to reveal
A resume can contain real, relevant experience that isn't literally named in the job posting but still strengthens the application — a "gaps only" tool would never surface it, leaving the candidate to only react defensively to what's missing rather than proactively highlighting what's already there but under-sold. Section 4's "potential strengths" isn't padding — it's the difference between a defensive tool and one that actively finds your best material.

Rough Sketch

 resume  +  job description
              |
              v
      ONE prompt, FOUR sections back:

      1. requirements  -- what the job actually asks for
      2. matches       -- what the resume ALREADY covers
      3. gaps          -- required, but NOT evidenced in resume
      4. hidden strengths -- resume has it, job didn't ask for
                             it by name, but it's still valuable

              |
              v
      same function, works with EITHER provider:
        if model == "openai":  ...
        elif model == "gemini": ...
      (one interface, swappable backend -- same pattern as
       section 5's provider comparison)

Same function, either provider, via a simple branch on a model parameter.

Iteration Prompt Tuning — Surfacing AI/Prompt-Engineering Skills as a Strength
▸
Think First: adding "explicitly flag AI/prompt-engineering skills" to the prompt made Gemini catch it every time, but OpenAI still missed it on some runs. Before reading the result — do you expect a MORE specific instruction to always make an LLM MORE reliable, or can extra specificity sometimes get lost just as easily as a vague one? tap to reveal
Extra specificity helps on average but doesn't guarantee reliability — an instruction is still just one more thing competing for the model's attention inside a long prompt, and non-determinism means it can be followed on one run and dropped on the next with literally identical input. This is exactly what happened: Gemini reliably caught it, OpenAI didn't, on the same prompt. Specific instructions raise the odds; they don't eliminate the need to verify the output actually followed them.

Refinement: explicitly instruct the model to flag AI-adjacent skills (prompt engineering, ChatGPT familiarity) as a valuable strength, even if the job posting never asked for them by name.

Rough Sketch

 prompt BEFORE: "find potential strengths"
 prompt AFTER:  "find potential strengths, AND specifically
                  flag AI/prompt-engineering skills as valuable"

 same resume + job, both providers, prompt AFTER:
   Gemini -----> caught it, every single run
   OpenAI -----> caught it once, missed it on a re-run,
                 only reliable after adjusting temperature

 takeaway: more specific instruction != guaranteed compliance
           still needs verification, not just better wording

Architect's Lens

Think First: this tool's own logic says "AI/prompt-engineering fluency is a real hiring signal, flag it explicitly." Looking at your own Optimus/idfc-coder work honestly — is that already called out as its own line on your resume, or is it currently buried inside a generic "engineering management" bullet? tap to reveal

Worth checking directly rather than assuming. Leading AI adoption across 80+ microservices and designing prompt templates for idfc-coder is exactly the kind of evidenced, concrete AI-fluency signal this tool's own gap analysis would flag as a "potential strength" if it weren't already explicit — the same way OpenAI sometimes missed the AI-skills instruction here. If it's folded into a generic bullet, it's at real risk of the same kind of miss a reader (human or model) makes when the signal isn't called out by name.

Generation Producing the Tailored Resume — With Tracked Changes
▸
Think First: the tool could just hand you the final rewritten resume. Instead it also generates a separate "diff" showing exactly what changed. Given Section 1's rule about verifying every number — why does that design choice matter more here than it would for, say, a grammar fix? tap to reveal
A grammar fix doesn't introduce new facts — a rewrite might. Without a diff, verifying the final resume means comparing two full documents line by line, hunting for what changed, which people skip when tired or in a hurry — exactly when a fabricated metric slips through unnoticed. A diff makes every addition/change/removal visible at a glance, turning "carefully re-read the whole thing" into "scan the changes and verify each one" — which is the difference between the human-in-the-loop rule being followed and being skipped.

Rough Sketch

 original resume + job description + gap analysis
              |
              v
      resume-rewriting prompt
              |
        +-----+-----+
        v           v
 updated resume   diff markdown
 (final text)     (+ added, - removed, ~ changed, line by line)

 WITHOUT the diff:                 WITH the diff:
   compare two full docs             scan just the CHANGES
   line by line, easy to               |
   miss something                      v
        |                          verify each one against
        v                          what you actually did
   fabricated number slips
   through unnoticed

Two outputs: the rewritten resume, and a markdown diff of exactly what changed — so every modification can be reviewed and approved before use.

Generation Cover Letter — Tone Control as a Real Parameter
▸
Think First: "tone" (professional vs. informal) is a fuzzy, judgment-heavy quality — not a hard fact like a name or date. Why turn something fuzzy like that into an explicit function parameter instead of just writing two separate prompts by hand each time? tap to reveal
Turning it into a parameter makes a subjective decision explicit and repeatable instead of buried inside a one-off prompt you'd have to rewrite from scratch each time. Same function, same underlying logic — just swap tone="professional" for tone="informal" — rather than maintaining two near-duplicate hand-written prompts that drift apart over time. It's the same "make the qualitative choice an input, not a hardcoded assumption" instinct as any other config value.

A tone parameter lets the same function write either a formal or an informal letter, depending on the target company's culture.

Architect's Lens

Think First: this tool makes you actively choose a tone before it writes anything. What does that force you to do that a one-size-fits-all "write me a cover letter" prompt wouldn't? tap to reveal

It forces you to actually go read the company's culture first — you can't set tone="informal" vs. tone="professional" without deciding which one fits, and that decision requires looking at their careers page or LinkedIn voice before you write anything. A generic prompt lets you skip that research and default to whatever the model picks. Tone-as-parameter turns a step people often skip into a step you can't avoid — arguably the tool's most practical career advice is baked into its function signature, not its output.

Pipeline The Unified "Resume Rocket" Function
▸
Think First: this function chains gap-analysis → rewrite → cover letter with zero pauses for a human to look at the middle steps. Given everything this project just taught about fabricated metrics, is chaining all three steps automatically a convenience — or does it quietly remove the one checkpoint that mattered most? tap to reveal
As written, it removes the checkpoint — the function prints intermediate output but doesn't actually pause for review before feeding the gap analysis into the rewrite, or the rewrite into the cover letter. That's fine for a demo, but it means a fabricated metric introduced at step 2 flows straight into step 3 unexamined. The convenience of one function call and the human-in-the-loop rule from Section 1 are in direct tension — a production version would need an explicit pause (or at least a return-and-confirm step) between "rewrite" and "cover letter," not just a print statement.
def run_resume_rocket(resume: str, job_description: str):
    gaps = analyze_resume_against_job_description(resume, job_description, model="openai")
    print(gaps)

    updated_resume, diff_markdown = generate_updated_resume(resume, job_description, gaps)
    print(updated_resume)
    print(diff_markdown)

    cover_letter = generate_cover_letter(job_description, updated_resume, model="openai")
    return updated_resume, cover_letter

Wrap-up Project Recap
▸
Think First: across all 9 build sections, one warning kept resurfacing in different forms — fabricated metrics, non-deterministic instruction-following, missed AI-skills flags. What's the ONE underlying property of LLMs that all three of those symptoms trace back to? tap to reveal
LLMs generate plausible text, not verified truth — every symptom in this project is a variation of that one fact. Fabricated metrics: plausible-sounding numbers, not recalled ones. Inconsistent instruction-following: plausible compliance most of the time, not guaranteed every time. Missed AI-skills flags: plausible relevance judgment, not a reliable rule. The fixes (Pydantic validation, diffs, human review, tone-as-parameter) are all different ways of putting a human or a schema between "plausible" and "trusted" — which is really the single lesson under this whole project.
