Pydantic fundamentals

Q5Imagine asking an LLM for JSON with name, age, and email. The model returns age as "forty" instead of 40. Your application expected an integer. Before reading the solution — what problems could this cause, and WHEN would they surface?reveal

Your application expected:

The problem: The error doesn't happen immediately — it surfaces later when your code tries to do math with "forty" or store it in a database column expecting integers.

Function design choices

Q11Before reading the solution, think: If you wanted ONE function that could return either plain text OR structured data, how would you design it? What would the parameter look like, and how would the function decide which behavior to use?reveal

Instead of:

function A → text
function B → structured data

the design uses:

              generate()
                  │
                  ▼
        response_format?
             /       \
           NO         YES
           │           │
           ▼           ▼
      plain text    structured
        API call       API
           │           │
           ▼           ▼
         str        Pydantic

So:

generate(prompt, response_format=None)

means:

response_format=None
        ↓
    normal text

response_format=User
        ↓
    structured output

Design choice: One function, one call pattern, one place to maintain.

Q12What's wrong with having generate_text() and generate_structured() as separate functions? Think about maintenance, duplication, and what happens when the underlying API changes.reveal

Without dual mode:

generate_text()
generate_structured()

Now you maintain:

logic A ─────────────┐
                     │
                     ├── duplicated
                     │
logic B ─────────────┘

With one function:

                generate()
                    │
             ┌──────┴──────┐
             │             │
           text        structured

One interface.

One place to maintain.

The problem with two functions: They inevitably drift apart. A bug fix in one doesn't automatically apply to the other. A change to the provider's API needs to be updated in two places.

Q13Where's the line between "one flexible function" and "a function that does way too much"? When does optional parameter convenience become a maintenance nightmare?reveal

Good:

generate(
    response_format=None
)

Dangerous:

generate(
    structured=True,
    retry=True,
    tone="formal",
    provider="openai",
    validate=True,
    async_mode=False,
    streaming=True,
    ...
)

Eventually:

             generate()
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
     flag 1    flag 2    flag 3
       │         │         │
       ▼         ▼         ▼
     branch    branch    branch
       │         │         │
       └────┬────┴────┬────┘
            │         │
         💥 complexity

Rule of thumb: Shallow branching = good. A maze of optional parameters = time to refactor.

The inputs: Old resume + job description + gap analysis. The gap analysis tells it WHAT to change; the rewrite step produces both the new version and a visible diff of what changed.

Q25Imagine you get back a completely rewritten resume. How would you verify it without a diff? What's the risk of having to compare two full documents line by line, especially when you're in a hurry?reveal

Without diff:

OLD RESUME ──────────┐
                     │
                     ▼
                  COMPARE
                     ▲
                     │
NEW RESUME ──────────┘

You have to manually find:

"What changed?"

With diff:

              DIFF
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
    ADDED    REMOVED   CHANGED
      │        │        │
      ▼        ▼        ▼
    Review   Review    Review

Why this matters: When you're tired or in a hurry, you'll skip line-by-line comparison. A diff makes verification as simple as scanning the changes. This is the difference between catching a fabricated metric and letting it slip through.

Q26Why is the diff positioned as a "security boundary" between AI generation and human review? What is it "securing" against?reveal
                 AI
                  │
                  ▼
             NEW RESUME
                  │
                  ▼
                 DIFF
                  │
                  ▼

                  │
          ┌───────┴────────┐
          ▼                ▼

The security boundary: The diff is the checkpoint where AI-generated claims are flagged for human verification. Without it, fabricated claims flow directly into the final document. With it, every change is surfaced and reviewable.

The pattern underneath all of it: AI writes fluent words; only you can verify facts. Structure (Pydantic) can guarantee shape, never truth. Non-determinism means the same prompt can pass once and fail the next time. And every step that can introduce or repeat a claim needs a human gate — a print statement is not a checkpoint.
