offset 03

Chunking

Q5Imagine a 100-page compliance document. What happens if you embed the entire document as one single vector? What semantic problem does this create?reveal

You don't want:

100-page document
       |
       v
   ONE VECTOR

Because one vector becomes a semantic mixture of everything.

Instead:

                  Document
                     |
                     v
        +-------------------------+
        |      Chunking           |
        +-------------------------+
          |      |       |      |
          v      v       v      v
       Chunk1 Chunk2  Chunk3  Chunk4
          |      |       |      |
          v      v       v      v
        Vec1   Vec2    Vec3    Vec4
          |      |       |      |
          +------+-------+------+
                     |
                     v
                 Vector DB

Now:

"What's the SIP eligibility?"
             |
             v
       semantic search
             |
             v
       [eligibility chunk]

instead of:

"What's the SIP eligibility?"
             |
             v
        [entire policy]
             |
             v
       weak semantic match
Q6Consider a compliance rule split across two chunks. If the split happens in the middle of a condition, what semantic risk does this create for the LLM?reveal

Consider:

Chunk 1
--------------------------------
Customer is eligible if age < 60
AND annual income exceeds ₹10L
UNLESS transaction...
--------------------------------

Chunk 2
--------------------------------
exceeds ₹50L or special approval
is required.
--------------------------------

If you split badly:

Chunk 1:
"Customer is eligible if age < 60
AND annual income exceeds ₹10L
UNLESS transaction..."

Chunk 2:
"exceeds ₹50L..."

The semantic meaning can change.

The LLM sees:

"eligible if..."

without the complete condition.

Therefore:

Generic website
      |
      v
Character-based chunking
      |
      v
Usually acceptable


Compliance / Legal / Financial
      |
      v
Structure-aware chunking
      |
      +--> Section
      +--> Clause
      +--> Sub-clause
      +--> Complete condition
      |
      v
Much safer

Architectural takeaway: Chunking isn't merely a performance parameter. For regulated content, it is part of semantic correctness.

Q9Why isn't retrieving more documents always better? What trade-offs exist between retrieving 1 document versus retrieving 100?reveal

The example uses:

similarity_search(...)
             |
             v
           k = 3
             |
             v
      Chunk A
      Chunk B
      Chunk C

But increasing k isn't automatically better.

k = 1
 |
 +--> high precision
 +--> low coverage


k = 10
 |
 +--> more coverage
 +--> more irrelevant context
 +--> more tokens
 +--> potentially more confusion

So:

              Retrieval
                 |
                 v
          Precision / Recall
                 |
                 v
          Choose appropriate k

In a real enterprise RAG system, think beyond plain top-k:

Query
  |
  v
Initial Retrieval
  |
  v
Top 20-50 candidates
  |
  v
Re-ranking
  |
  v
Top 3-8 high-quality chunks
  |
  v
LLM

That's a much more scalable architecture than blindly relying on similarity_search(k=3).

Where LangChain fits & the production insight

Q14Is LangChain the same as RAG? If you implement RAG with and without LangChain, what are the trade-offs in visibility vs. development speed?reveal

Don't confuse LangChain with RAG.

RAG is the architecture/pattern.

LangChain is a framework that helps implement it.

             RAG Architecture
                    |
     +--------------+--------------+
     |              |              |
   Load           Retrieve       Generate
     |              |              |
     +--------------+--------------+
                    |
                    v
                LangChain

Without LangChain:

Python
 |
 +--> OpenAI API
 +--> Chroma API
 +--> custom chunking
 +--> custom prompt
 +--> custom orchestration

With LangChain:

LangChain
 |
 +--> loaders
 +--> splitters
 +--> embeddings
 +--> vector stores
 +--> retrievers
 +--> chains
 +--> prompts

The trade-off:

                    LangChain
                       |
          +------------+------------+
          |                         |
       Faster                    Abstraction
       development                  |
                                    v
                              Less visibility
                              into internals

Therefore: Framework abstraction is useful until it obscures the failure boundary.

For production, you need tracing around:

Retrieve
   ↓
Rank
   ↓
Prompt
   ↓
LLM
   ↓
Post-process
Q15What's the hardest silent failure in RAG? Why is bad retrieval more dangerous than bad generation, and what makes it so hard to detect?reveal
                  RAG SYSTEM
                     |
                     v
              ┌─────────────┐
              │  RETRIEVAL  │  <── hardest silent failure
              └──────┬──────┘
                     |
              Are chunks correct?
                     |
             +-------+-------+
             |               |
            NO              YES
             |               |
             v               v
       Fix retrieval      LLM / Prompt
       ├─ chunking        ├─ prompt
       ├─ embedding       ├─ model
       ├─ query           └─ generation
       ├─ k
       └─ reranking

Why?

Because:

Bad retrieval
      |
      v
Wrong context
      |
      v
LLM
      |
      v
Excellent-looking wrong answer

The LLM is not necessarily going to tell you that retrieval failed.

That's why RAG observability must inspect the middle of the pipeline.

The 6 things to remember as an architect:

  1. RAG changes context, not model weights.
  2. Chunking determines retrieval granularity and can affect semantic correctness.
  3. Retrieval quality is an independent subsystem and must be evaluated independently.
  4. Top-k similarity alone doesn't necessarily scale; re-ranking/hybrid retrieval often become important.
  5. Citation proves provenance, not freshness or correctness.
  6. For enterprise RAG, auditability means recording the retrieval → prompt → model → answer chain, not merely showing a source link.

The strongest lesson:

          RAG is NOT

        "LLM + Vector DB"


          RAG is

   KNOWLEDGE RETRIEVAL SYSTEM
              +
       CONTEXT ASSEMBLY
              +
       GENERATIVE MODEL
              +
       OBSERVABILITY

That is the mental model to use before looking at the LangChain implementation.
