offset 00

The core mindset — the 80/20 rule

Q1When an LLM gives you a poor answer, where do you think the problem usually lies? A. The model is not intelligent enough
B. The model needs more training
C. The prompt did not sufficiently constrain the model
D. The model is randomly generating answersreveal

The most important mindset is:

Prompting is closer to programming a probabilistic system than having a normal conversation.

An LLM receives your prompt and computes a probability distribution over possible next tokens.

Simplified:

                 YOUR PROMPT
                     |
                     v
        +---------------------------+
        |        LLM / Neural       |
        |          Network          |
        +---------------------------+
                     |
                     v
          Probability distribution
                     |
          +----------+----------+
          |          |          |
         65%        20%        10% ...
        Answer A   Answer B   Answer C
          |
          v
       OUTPUT

Your prompt influences that probability distribution.

The fundamental principle

Vague Prompt
     |
     v
Many possible interpretations
     |
     v
High uncertainty / entropy
     |
     v
More variable output

Whereas:

Precise Prompt
     |
     v
Fewer possible interpretations
     |
     v
Lower uncertainty / entropy
     |
     v
More predictable output

Think like an architect

You are not simply saying: "Give me something good."

You are designing an interface contract between the human and the model.

              PROMPT
                 |
     +-----------+-----------+
     |           |           |
  Context      Rules       Goal
     |           |           |
     +-----------+-----------+
                 |
                 v
              LLM
                 |
                 v
          Structured Output

GIGO — Garbage In, Garbage Out

The classic computing principle applies here:

Bad Input
   |
   v
Ambiguous requirements
   |
   v
Model has to GUESS
   |
   v
Unreliable Output

Versus:

Good Input
   |
   +--> Clear objective
   +--> Relevant context
   +--> Constraints
   +--> Expected format
   +--> Examples
          |
          v
       LLM
          |
          v
   More reliable output

Important correction to the original statement

It is useful to think: "If the AI misunderstands me, first inspect the prompt."

But not every incorrect answer is the prompt's fault.

LLMs can still fail because of: hallucination, insufficient knowledge, reasoning errors, ambiguous source material, context-window limitations, retrieval failures, model limitations.

So the architect mindset is:

Bad Output
   |
   +--> Was the prompt ambiguous?
   |
   +--> Was the context sufficient?
   |
   +--> Were constraints explicit?
   |
   +--> Was the task within model capability?
   |
   +--> Was external knowledge required?
   |
   +--> Did the model reason incorrectly?

This is much more useful than simply blaming either the model or the prompt.

Advanced technique 1 & 2 — Chain-of-Thought and Few-Shot

Q9Imagine asking: "Calculate 15% of 250 + 20% of 300." Would you trust the model more if it simply gave "97.5" or if it performed intermediate calculations?reveal

The key idea is:

Complex Problem
      |
      v
Intermediate reasoning
      |
      v
Final answer

Example

15% of 250
    |
    v
0.15 × 250
    |
    v
37.5

20% of 300
    |
    v
0.20 × 300
    |
    v
60

37.5 + 60
    |
    v
97.5

Important modern prompt-engineering nuance

The original idea says: "Force the AI to show its work." That is not always necessary.

A better practice is to ask for: a concise rationale, verification, or intermediate result when useful, rather than demanding hidden/internal chain-of-thought.

For example:

Solve the problem.
Show the key calculation steps.
Then provide the final answer.

Architect's mental model

                 HARD TASK
                     |
                     v
              Decompose problem
                     |
          +----------+----------+
          |          |          |
        Step 1     Step 2     Step 3
          |          |          |
          +----------+----------+
                     |
                     v
              Verify result
                     |
                     v
                Final answer

This is particularly useful for: mathematics, coding, architecture, troubleshooting, multi-step analysis.

That is much closer to engineering decision-making.

The prompt engineering workflow

Q15Suppose you wrote this prompt: "Act as a senior architect and design a scalable payment system." The AI gives you a very generic architecture. What should you do? A. Rewrite the entire prompt from scratch
B. Blame the model
C. Identify exactly what was missing and add a targeted constraint
D. Make the prompt 10× longerreveal

Answer: C

Professional prompt engineering is iterative optimization.

You don't try to create the perfect prompt immediately. You follow:

Draft
  |
  v
Run
  |
  v
Observe failure
  |
  v
Identify root cause
  |
  v
Add targeted constraint
  |
  v
Run again
  |
  v
Evaluate
  |
  v
Repeat
  |
  v
Production Prompt

This is essentially the same mindset as software engineering.

Prompt engineering = iterative development

Think about writing a prompt like writing code:

Software Engineering             Prompt Engineering
---------------------------------------------------------
Write code                       Write prompt
Run program                      Run prompt
Observe bug                      Observe bad output
Debug                             Diagnose failure
Change code                       Add/change constraint
Run tests                         Run prompt again
Regression test                   Evaluate output
Deploy                            Productionize prompt

A prompt is not a one-time piece of text. It is an artifact that you iteratively engineer.

Step 1 — Draft 1

Start simple: ROLE + TASK

Act as a Senior Software Architect.

Design a scalable payment processing system.

Don't spend 30 minutes trying to make Draft 1 perfect.

Step 2 — Run it

Look at the output. Suppose you get:

OUTPUT
   |
   +--> Architecture is good
   |
   +--> Too generic
   |
   +--> Missing failure scenarios
   |
   +--> No capacity assumptions
   |
   +--> No database choice

Now you have evidence. This is critical. Don't randomly modify the prompt.

Step 3 — Diagnose the failure

Ask: Exactly what did the model do wrong? Create a failure taxonomy:

                 BAD OUTPUT
                     |
       +-------------+-------------+
       |             |             |
    Content       Format        Behavior
       |             |             |
   Missing info   Wrong JSON     Too verbose
   Wrong facts    Wrong fields   Too vague
   Hallucination  Wrong schema   Wrong tone

This is much better than saying: "The AI answer isn't good."

Step 4 — Add one targeted constraint

Suppose the model invented information. Don't rewrite everything. Add:

If required information is missing,
output "N/A".

Do not infer or invent missing values.

Now:

Original Prompt
      |
      v
Observed Failure
      |
      v
Specific Constraint
      |
      v
Improved Prompt

Step 5 — Run again

                    PROMPT V1
                       |
                       v
                     LLM
                       |
                       v
                  Bad Output
                       |
                       v
                 Diagnose
                       |
                       v

                       |

Step 6 — Add negative prompting

Sometimes telling the model what not to do is useful. For example:

Do NOT:
- invent missing facts
- use overly technical jargon
- mention competitors
- rewrite the entire codebase
- introduce unnecessary dependencies

Positive vs negative constraints:

              PROMPT
                 |
       +---------+---------+
       |                   |
   DO THIS              DON'T DO THIS
       |                   |
   Positive             Negative
   constraints          constraints

Example:

DO:
Explain the architecture for an engineering manager.

DON'T:
Use unnecessary low-level implementation details.

Important nuance: Don't overload the prompt with dozens of arbitrary negative rules.

Bad:

Don't do X.
Don't do Y.
Don't do Z.
Don't do A.
Don't do B.
Don't do C.
...

Better: Add negative constraints only where a known failure mode exists.

offset 08

Token economy

Q16Imagine a prompt that opens with "Please kindly act as a very experienced and highly knowledgeable senior architect who has many years of experience in designing..." followed by 2,000 words of repetitive instructions. Is a longer prompt automatically a better prompt?reveal

No.

The objective is not: Maximum prompt length

It is: Maximum useful information per token.

What is a token?

An LLM does not necessarily process text as complete words. It processes tokens.

Simplified:

"I love architecture"

        |
        v

   Tokenization

        |
        v

["I", " love", " architecture"]

Actual tokenization depends on the tokenizer and language.

The common rule: 1 token ≈ 4 English characters is only a rough approximation.

It varies substantially by: language, vocabulary, punctuation, code, numbers, whitespace, tokenizer.

So don't treat "4 characters = exactly 1 token" as a law.

Prompt token flow

                  LLM
                   |
       +-----------+-----------+
       |                       |
       v                       v
 INPUT TOKENS             OUTPUT TOKENS
       |                       |
       v                       v
   Prompt +                  Response
   Context

For API-based systems, token usage can affect: cost, latency, context-window usage, throughput.

A critical correction

The original material says: "If your prompt is 2,000 words, the AI spends 80% of its brainpower reading it." This is a useful intuition, but technically it is not correct.

LLMs don't have a fixed 80% reading / 20% reasoning budget.

Instead, long context consumes: context-window capacity, compute, latency, potentially money.

And excessive irrelevant context can make it harder for the model to focus on the information that matters.

So the better principle is: Minimize unnecessary instructions, but provide sufficient relevant context.

Token economy: the architect's view

Think about context as a system resource.

             CONTEXT WINDOW
          +-------------------+
          |                   |
          | System Prompt     |
          |                   |
          | User Prompt       |
          |                   |
          | Documents         |
          |                   |
          | Conversation      |
          |                   |
          | Tool Results      |
          |                   |
          +-------------------+

Everything competes for the available context.

Therefore:

Irrelevant Context
       |
       v
More tokens
       |
       +--> Higher cost
       |
       +--> Higher latency
       |
       +--> Less room for useful context
       |
       +--> Potentially poorer attention

The golden token rule

Be concise in instructions. Be complete in relevant context.

❌ Bad:

You are a very very experienced architect...
You are highly knowledgeable...
You have many years of experience...
You should try your best...
Please carefully think...
Please be very thoughtful...

Much of this is redundant.

Better:

Act as a Senior Distributed Systems Architect.

Then spend your tokens on useful information:

System:
- 5000 requests/sec
- Java
- Kafka
- Oracle
- Redis
- 99.99% availability
- p99 latency < 200ms
- Multi-region

Token economy example

BAD PROMPT

2,000 tokens
   |
   +--> 1,200 redundant instructions
   +-->   300 useful instructions
   +-->   500 relevant context

Better:

GOOD PROMPT

1,000 tokens
   |
   +--> 200 concise instructions
   +--> 800 relevant context

The goal isn't always fewer tokens. The goal is:

              HIGH SIGNAL
                  /
                 /
                /
               v
      +-------------------+
      | Relevant Context  |
      | Clear Instructions|

Master prompt template

The deepest principle

Prompt engineering is essentially requirement engineering for probabilistic software.

A weak prompt says: "Do something."

A good prompt says: "Here is who you are, what you must accomplish, what information you can use, what constraints apply, what alternatives to consider, and exactly how I want the result."

And a production-grade prompt goes one step further: "Here is how we will evaluate whether your output is correct."

That last concept—evaluation—is what takes you from prompting toward production AI engineering.

// final compression: prompting programs a probability distribution, not a conversation — precise prompts lower entropy and raise predictability, but not every bad output is the prompt's fault → Role, Task, Context, Format, and Tone are the five pillars that remove ambiguity one layer at a time → Chain-of-Thought asks for key steps not hidden reasoning, Few-shot teaches by example via in-context learning → Step-Back establishes general principles before diagnosing the specific case, and Self-Consistency generates alternatives and evaluates them against explicit criteria rather than taking the first answer → Delimiters separate trusted instructions from untrusted data — the same discipline that defends against prompt injection → building a prompt is iterative: draft, run, diagnose the specific failure, add one targeted constraint, retest → tokens are a budget — be concise in instructions, complete in relevant context, since irrelevant tokens cost money, latency, and attention → the master template extends Role/Task/Context/Format/Tone into Role/Goal/Context/Instructions/Constraints/Format/Tone for production use → system prompts hold permanent behavior, user prompts hold the variable request → and the discipline scales into RAG for enterprise knowledge, injection defense for untrusted content, and multimodal inputs beyond text — the real skill throughout is never prompt length, but reducing ambiguity while supplying the right information, constraints, and evaluation criteria.
