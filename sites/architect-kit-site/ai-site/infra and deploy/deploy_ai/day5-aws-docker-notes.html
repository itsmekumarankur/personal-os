Week 1 · Day 5 — First AWS Deploy: IAM, Docker, and App Runner

Notes from Ed Donner's Day 5 lecture — the "big day" moving off Vercel's PaaS convenience onto AWS: root vs. IAM users, budget guardrails, Docker fundamentals, and a first live deploy via App Runner. Structured for a Senior Engineering Manager comparing AWS's IAM/cost model against enterprise governance patterns already familiar from banking infrastructure.

Framing Today Is a Teaser, Not the Full AWS Deep Dive
▸

Explicit scope-setting: today covers "many of the core components," not "every component" — Week 2 is the real AWS deep dive. The goal for Day 5 is a working end-to-end deploy and a general flavor for AWS's operating model, not mastery.

The headline contrast set up for the whole day: Vercel felt almost too easy; AWS is the opposite — "industrial grade," built for massive scale, and deliberately more granular (and more tedious) about permissions and configuration as a direct consequence of being trusted by major enterprises.

IAM Root User vs. IAM User — The Core Discipline
▸ 
Root user  → created at signup, all-powerful, should almost NEVER be used
             day-to-day. Only two legitimate uses:
               1. Assigning permissions (creating/configuring IAM users)
               2. Budget / billing management

IAM user   → a restricted-permission identity you create and use for
             actual daily work. This course creates ONE user, "AI
             engineer" (real production setups would create MANY,
             scoped per environment / per project).

Setup flow: sign up for AWS (credit card required) → sign in as root → enable MFA (mandatory, via an authenticator app) → note the 12-digit AWS Account ID (needed repeatedly going forward) → create an IAM user → create a user group ("broad AI engineer access") → attach permission policies to the group, not the user directly → the user inherits the group's permissions.

Four policies attached in this setup: AWSAppRunnerFullAccess, AmazonEC2ContainerRegistryFullAccess, CloudWatchLogsFullAccess, IAMUserChangePassword. Explicitly flagged as broader than a real security-conscious setup would use ("full access" grants are convenient but not least-privilege) — acceptable for a learning environment, not for real production.

Architect's Lens

Group-based permission assignment (policies → group → user, never policies → user directly) is the same RBAC discipline you'd expect in any enterprise IAM system — it's the pattern that scales when you have more than a handful of users, since you manage the group's permission set once instead of touching every individual user. The explicit admission that "full access" policies are used here purely for course convenience, not least-privilege, is a useful teaching moment: it's the same corner every team is tempted to cut early on, and the same one that becomes expensive to unwind later once dozens of services depend on overly broad grants.

Questions worth sitting with

  • Across your 80+ microservices, how much of the current IAM/service-account footprint started as a convenient "full access" grant during a rushed initial setup, the same way this course explicitly does — and never got tightened afterward?
Active Recall: Why attach permission policies to a user GROUP rather than directly to the user? tap to reveal
Because it scales — with permissions on the group, you manage one set of policies that automatically applies to every user added to that group, rather than having to individually configure permissions on every single user account as your team grows.
Cost Governance Budgets, Alerts, and AWS's "No Hard Cap" Reality
▸

This week's project is estimated at $1–5 if run briefly and torn down; de minimis if left running only a couple of days. New accounts often get several months of free credits (varies by region/eligibility).

Two budgets set up, both from the root account (Billing and Cost Management → Budgets):

  • Zero-spend budget — alerts the moment spend exceeds $0.01. A safety-net tripwire.
  • Monthly cost budget — a chosen dollar ceiling (e.g. $5), with alerts at 85% actual, 100% actual, and 100% forecast (i.e. Amazon predicting you'll hit it if current usage continues).

Risk Flag — This Is the Important Part

AWS alerting is granular and reliable, but there is no hard spending cap — no "shut everything off at $X" option, unlike OpenAI's pre-funded drawdown model. AWS's own stated reasoning: an enterprise running Netflix-scale infrastructure can't have billing suddenly kill production. In theory, liability is unlimited if something runs away (e.g. misconfigured auto-scaling spinning up far more infrastructure than intended). The explicit comparison: with OpenAI's $5 pre-pay model, worst-case liability is $5; with AWS, worst-case liability is open-ended unless you're actively monitoring.

Architect's Lens

This is the exact same cost-governance gap flagged back on Day 1, now made concrete with the specific mechanism (alerts, not caps). For an enterprise this is manageable via tagging, chargeback, and service quotas set proactively — but it's worth treating "no automatic shutoff" as a standing design constraint any time your team spins up new AWS infrastructure, not just a beginner's warning. A runaway auto-scaling misconfiguration is a very plausible real incident category, not a hypothetical.

Question worth sitting with

  • Does IDFC's current AWS governance model rely on the same "alerts, not caps" mechanism as the baseline defense against runaway spend — and if so, what's the actual incident-response playbook if an alert fires at 2am for an unexplained scaling event?
Active Recall: What is AWS's stated reason for not offering a hard spending cap / auto-shutoff? tap to reveal
Because AWS is used by major enterprises running critical, always-on infrastructure — a hard cap that automatically shuts services off when a bill isn't paid or a limit is hit isn't acceptable in that context (e.g. a payment failure shouldn't be able to take down a service like Netflix), so AWS only offers alerting, never automatic cutoff.
AWS Lingo Regions and ARNs — Two Identifiers You'll See Constantly
▸
  • Region (e.g. us-east-1): almost a separate installation of AWS with its own service availability. Typo risk called out explicitly — leaving out a hyphen produces obscure, hard-to-diagnose errors ("I speak from bitter personal experience").
  • ARN (Amazon Resource Name): a unique identifier attached to essentially every object in AWS — encodes the service, region, account ID, and resource details in one string. You'll see these everywhere once you start using more services.
Active Recall: What does an ARN typically encode, and why does that matter? tap to reveal
An ARN encodes the AWS service, the region, and the account ID (plus resource-specific details) into a single unique string identifying any object in AWS. It matters because ARNs are used pervasively to reference and permission specific resources across the platform — you'll need to read and recognize them constantly.
Docker Docker Fundamentals — Dockerfile → Image → Container
▸

Analogy given: Docker is a lightweight "computer within a computer" — like a VM, but sharing the host OS instead of emulating a whole separate one, so it's much faster to start and lighter on resources. The payoff: build once, run identically on any machine.

Dockerfile  → a text "recipe": step-by-step instructions for building
              the environment (often starts FROM an existing image and
              layers changes on top)
     ↓
Image       → a snapshot/blueprint built by running the Dockerfile —
              not running, just a saved definition
     ↓
Container   → a live, running instance of an image. You can spin up
              many containers from the same image; each can be
              started and stopped independently.

Architect's Lens

"Build once, run identically anywhere" is the whole point, and it's the same reproducibility guarantee that matters most in regulated environments — a container that passed testing locally is, modulo environment variables/secrets, the exact same artifact that runs in production. Worth confirming this is actually how your Wealth/Demat services are deployed today (image built once, promoted unchanged across environments) versus rebuilt per-environment, which reintroduces exactly the "works on my machine" risk containers are meant to eliminate.

Active Recall: What's the relationship between a Dockerfile, an image, and a container? tap to reveal
A Dockerfile is a text recipe of build instructions. Running that Dockerfile produces an image — a static snapshot/blueprint. Running that image produces a container — a live, active instance. Many containers can be spun up from the same single image.

Refactor Adapting the App for AWS — What Actually Changed
▸

Moving from Vercel's model to a single Docker container required real architectural changes, not just a redeploy:

  • next.config updated to static export — the Next.js front end is now pre-compiled into plain HTML/CSS/JS at build time, not served dynamically on demand the way Vercel handled it.
  • Front-end fetch calls updated from /api to /api/consultation — a more specific route since front end and back end now share one server.
  • New server.py replaces index.py — adds CORS middleware (restricts which origins can call the backend), a new /health endpoint (required by AWS App Runner's health checks), and logic so the FastAPI backend also serves the static front-end files directly at / — front end and back end now live in one process/container instead of Vercel's separate handling.
  • New .env additions: AWS default region and the 12-digit AWS account ID, alongside the existing Clerk/OpenAI secrets.

Architect's Lens

This is the real lesson hiding under the "just add two env vars" framing: moving between deployment platforms is rarely a pure ops change — it forced genuine application-level changes (static export, CORS, a merged front-end/back-end serving model, a new health endpoint). Worth internalizing as a general rule before quoting a "quick migration" timeline to stakeholders: cross-platform portability claims should always be verified against what the target platform actually expects structurally, not just where secrets and config live.

Question worth sitting with

  • If a squad told you "we can move this Vercel-hosted tool to AWS in an afternoon," would this walkthrough change how skeptically you'd probe that estimate?
Active Recall: Why does the FastAPI backend need a new "serve the static front end" route when deploying to AWS App Runner, when it didn't need this on Vercel? tap to reveal
Because on Vercel, the front end and back end were handled as separate concerns by the platform itself. On AWS, everything is packaged into one Docker container running one process — so the FastAPI backend now has to take on the extra job of serving the pre-built static front-end files (like index.html) whenever the root URL is requested, in addition to handling its API routes.
Docker The Multi-Stage Dockerfile — Building Front End and Back End Into One Image
▸ 
Stage 1 (temporary) — FROM node:22
  → npm run build     (compiles Next.js into a static site)

Stage 2 (final)      — FROM python:3.12-slim
  → pip install -r requirements.txt
  → COPY api/server.py .
  → COPY --from=stage1  (the static site built in Stage 1) → into this image
  → HEALTHCHECK        (periodically hits /health)
  → EXPOSE 8000
  → CMD uvicorn server:app --host 0.0.0.0 --port 8000

This is a multi-stage build — Stage 1 exists purely to compile the front end; only its output (the static files) gets copied into the final Python-based image, keeping the final image lean (no Node.js runtime bloat in production). A .dockerignore file (same concept as .gitignore) excludes unnecessary files from the build context.

Note, Not a Real Risk

Build-time warnings about the Clerk publishable key being present in the container are expected and safe to ignore — it's explicitly a publishable key, designed to be exposed client-side. Worth remembering as a category distinction: publishable/public keys are meant to be visible; secret keys are not — the warning tooling can't always tell the difference automatically.

Architect's Lens

Multi-stage builds are the standard answer to "my final image shouldn't need the entire build toolchain" — a pattern worth enforcing as a default across any Dockerized service at IDFC: build stage carries compilers/SDKs/dev dependencies, final stage carries only the runtime artifact. Smaller final images mean faster deploys, smaller attack surface, and lower registry storage costs at scale.

Active Recall: Why does this Dockerfile use two separate FROM stages instead of one? tap to reveal
Stage 1 (Node.js) exists only to compile the Next.js front end into static files — the Node.js runtime itself isn't needed to actually run the app. Stage 2 (Python) is the real final image; it copies only the compiled static output from Stage 1, keeping the final production image lean and free of unnecessary build tooling.
Deploy Build Locally, Test Locally, Then Ship to App Runner
▸

Sequence: run a script to load .env values as shell environment variables → docker build (creates the image, caching layers on repeat runs) → docker run (spins up a container locally, verified working — including Clerk login — entirely on localhost) → push the image to ECR → configure App Runner:

  • Port set to 8000 (matching the Dockerfile's EXPOSE/uvicorn port)
  • Auto-scaling config (ASC): concurrency limit (10 requests), min instances = 1, max instances = 1 for this exercise (kept intentionally non-scaling — real production would raise the max)
  • Health check: HTTP protocol, path /health, 5s timeout, 20s interval — App Runner uses this to decide if the container is actually healthy

Result: a live HTTPS App Runner URL, verified end-to-end with the same Clerk login → consultation form → OpenAI-generated summary flow that worked on Vercel — this time fully running on AWS.

Architect's Lens

The min=1/max=1 auto-scaling choice is a deliberate cost-safety decision for a learning exercise — it guarantees the container can never silently multiply and run up a bill, at the cost of having zero real scalability. Worth noting as the mirror image of the "no hard spend cap" risk from earlier in the day: here, the instructor manually built in his own cap by constraining max instances, since AWS itself won't do it for him.

Active Recall: Why does App Runner need a /health endpoint specifically, and what does it check? tap to reveal
App Runner needs a way to know whether the running container is actually healthy and ready to serve traffic. It periodically calls the /health endpoint (every 20s, with a 5s timeout in this config) and expects a simple JSON response confirming healthy status — repeated failures mark the instance unhealthy.
