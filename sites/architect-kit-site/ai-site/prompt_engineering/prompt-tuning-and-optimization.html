PART I

The loop — iterative prompt testing

−
1.1

What the loop actually is

−

Iterative prompt testing is guided trial and error: write a deliberately thin prompt, run it, name the specific gap between what came back and what you wanted, close that gap, run again. The lecture's framing is right — the goal is not a good output, it is a reliably good output.

That word reliably is doing enormous work, and the lecture never cashes it in. One good sample is not reliability. It is one sample from a distribution you have not measured.

ASCII The loop as taught vs. the loop as it must be run − 
  AS TAUGHT                          AS IT MUST BE RUN

  write prompt                       write prompt v1
       |                                  |
       v                             +----+----------------+
     run once                        |    v                |
       |                             |  run N times on M   |
       v                             |  fixed test inputs  |
   "looks better?"                   |    |                |
       |                             |    v                |
   yes -> ship                       |  score every output |
                                     |  against a rubric   |
  one sample. one input.             |    |                |
  no baseline. no record.            |    v                |
  improvement is a vibe.             |  compare to the     |
                                     |  previous version   |
                                     |    |                |
                                     |    +-- worse? -> revert
                                     |    |
                                     |  better on average AND
                                     |  no regression -> keep
                                     +---------------------+
                                          |
                                          v
                                     prompt v2, logged

The right-hand column is not enterprise ceremony. It is the minimum needed to know whether your edit helped, because the model's output varies run to run even with an unchanged prompt.

Recall

Why can a prompt edit look like an improvement when it changed nothing?

Because sampling is stochastic. At any temperature above 0 the same prompt produces different outputs on repeat runs. If the natural spread between runs is wider than the effect of your edit, you are reading noise as signal. The fix is more samples per version and a fixed set of test inputs, not a better eye.

1.2

The demo, replayed and dissected

−

The lecture runs three versions of a climate-change explainer. Laid out as a table, the progression is clean — and the flaw becomes visible.

Table Three prompt versions and what each edit actually supplies −
vPromptConstraint addedFailure it fixes
1Explain climate changenone—
2…to a 10-year-old, in simple languageaudience + registerToo technical
3…in three sentences, with a fun example at the endlength + structure + closing beatToo dense, shapeless

The useful generalisation: every edit supplied a constraint the model was otherwise free to guess. A vague prompt is not an under-specified request — it is a request where the model picks the defaults for you, and its defaults are trained on the average of the internet, which skews long, hedged and encyclopedic.

Note

Five axes cover most prompt failures: audience, register, length, structure, exclusions. The lecture exercises the first four. The fifth — saying what you do not want — is mentioned in passing and never demonstrated, and it is usually the highest-yield one, because it is the only way to kill a persistent unwanted habit like a preamble or a closing offer to help further.

1.3

Four method bugs in that demo

−

The prompts got better. The method for knowing they got better is broken in four separate ways, and all four are things you will do by accident at work.

Trap 1 · Context carryover

The instructor says "you can either create a new chat or continue this one — we want it to be iterative." Continuing the chat means v2 and v3 are evaluated with v1's full exchange still in context. The model has already seen its own technical answer and your implicit rejection of it. Some of the improvement belongs to the conversation history, not to the prompt. Paste v3 into a clean session and it may underperform. Always test prompt versions in a fresh context.

Trap 2 · Two variables at once

v3 changes length and adds a closing example. If the result had been worse, which edit caused it? Change one thing per version. It costs one extra run and buys you attribution.

Trap 3 · n = 1

One sample per version, one test input. A prompt that is excellent for climate change may be terrible for photosynthesis while looking identical on paper. Hold a small fixed input set — five to ten realistic cases including the awkward ones — and run every version against all of it.

Trap 4 · No scoring rubric

"Looks better" cannot be regressed against. Before you iterate, write down the three or four binary checks that define done — is it ≤3 sentences? is every word one a 10-year-old knows? is there a concrete example? is there no preamble? Now improvement is countable and a later edit that quietly breaks check 4 gets caught.

Architect

Your team ships a prompt that summarises loan applications. Six weeks later output quality "feels worse" although nobody changed the prompt. Where do you look, in order?

1 · The model, not the prompt. Hosted endpoints move under you. A pinned alias like gpt-4o resolves to new snapshots; providers deprecate and silently reroute. Check whether you pinned a dated snapshot. If you did not, that is the bug and the fix is pinning.

2 · The inputs. Prompt quality is a function of input distribution. If the business started accepting a new applicant category, your prompt is now being tested on cases it was never tuned for. Sample recent live inputs and diff them against your eval set.

3 · Context length. If the prompt is assembled with retrieved documents, the retrieved payload may have grown; instructions placed before a long context lose salience.

4 · The perception itself. Without a stored baseline of scored outputs you cannot distinguish degradation from a reviewer's rising standards. This is the real lesson: the eval set is not for the tuning phase, it is for the six-weeks-later phase. Build it on day one or you are permanently arguing about vibes.

1.4

Where prompt tuning stops paying

−

Not in the transcripts at all, and the single most valuable judgement in this space: knowing when to stop iterating and change technique.

Table Symptom → the technique that actually fixes it −
SymptomPrompting fixes it?Reach for
Wrong tone, length, formatYesConstraints in the prompt
Ignores an edge caseYes2–3 few-shot examples of that case
Invents facts about your domainNoRetrieval — put the facts in context
Output shape drifts across runsPartlyStructured output / JSON schema mode
Needs a house style over 1000s of callsExpensivelyFine-tune; amortises the prompt tokens
Needs current or private dataNeverTools / function calling
Multi-step task, fails midwayNoDecompose into chained calls with checks
Good

Rule of thumb: if three consecutive prompt edits produce no measurable movement on your rubric, the problem is not in the prompt. Prompting cannot install knowledge the model does not have, and it cannot make a stochastic process deterministic.

PART II

Behind the chat box — keys and clients

−
2.1

What the frontend hides

−

The lecture's motivation is exactly right: a consumer chat UI gives you one lever — the words you type. The API gives you two — the words and the decoding configuration. Everything in Part IV is invisible from a chat box.

ASCII Same model, two surfaces — what each one lets you set − 
   CHAT UI                          API CLIENT
   ┌──────────────┐                  ┌──────────────────────────┐
   │ your words   │                  │ your words               │
   └──────┬───────┘                  │ system / role separation │
          │                          │ temperature, top_p, top_k│
   ┌──────▼───────────────┐          │ max tokens, stop, seed   │
   │ vendor's fixed       │          │ repeat penalty           │
   │ system prompt,       │          │ response format / schema │

Warn

That last line is the practical one and the course never says it. A prompt perfected in ChatGPT will behave differently through the API, because the product's own system prompt (formatting habits, hedging, refusal posture) is gone. Tune where you will run.

2.2

API keys — the part the lecture gets dangerously wrong

−

The instructor says "never share your API key publicly," then pastes it into a notebook cell on camera, reasoning that only part of it is visible. Two things are wrong with that.

  • The notebook file keeps it. The key is now in .ipynb JSON, in your shell history if you echoed it, and in git the moment you commit. Partial screen visibility is irrelevant — the file is the leak.
  • Leaked keys are found in minutes. Bots scan public GitHub pushes continuously. A key committed and force-removed thirty seconds later is still compromised, because it lives in the pushed object history.
Python Legacy pattern from the lecture — and the current SDK equivalent − 
# ── WHAT THE LECTURE WRITES (openai<1.0 style, plus a hardcoded key) ──
import openai
openai.api_key = "sk-proj-....."          # in the file. in git. gone.
client = openai.OpenAI(api_key=openai.api_key)  # module global as a courier

# ── CURRENT (openai>=1.0) ─────────────────────────────────────────────
# Key lives in the environment. The constructor reads OPENAI_API_KEY
# by itself, so there is nothing to hardcode and nothing to forget.
from openai import OpenAI
client = OpenAI()                               # that is the whole setup

# Set it once, outside Python:
#   macOS/Linux : export OPENAI_API_KEY="sk-proj-....."
#   Windows PS  : $env:OPENAI_API_KEY = "sk-proj-....."
# Or use a .env file + python-dotenv, with .env in .gitignore:
from dotenv import load_dotenv
load_dotenv()                                   # now OpenAI() finds it
Good

Three habits that cost nothing: put a hard monthly spend cap on the project (the lecture is right that this matters, and it is the one control that turns a leak from ruinous into annoying); use a separate key per project so revocation is surgical; and rotate on any doubt — revoking and reissuing takes fifteen seconds and there is no partial credit for a key that was "probably" fine.

Recall

You pasted a key into a notebook, committed, then rewrote history and force-pushed. Are you safe?

No. The blob was on the remote and may have been fetched, cached by forks, or indexed by scanners before the rewrite. Rewriting history is cleanup, not remediation. The only remediation is revoking the key.

PART III

Image generation — a moving target

−
3.1

The lecture's code no longer runs

−

Before parameter theory, a hard fact. DALL·E 2 and DALL·E 3 were removed from the OpenAI API on 12 May 2026. The lecture's call — model="dall-e-3" with style="vivid" — now returns an error. The current line is the GPT Image family, with gpt-image-2 as flagship since April 2026, alongside gpt-image-1.5 and the cheaper gpt-image-1-mini.

Warn

This is not a footnote about one course being stale. It is the operating condition. Model IDs and parameter names in this space have a shelf life measured in months. Any tutorial you follow — including this page — should be checked against the provider's API reference before you build on it. Pin dated model snapshots in production so the ground does not move under a running service.

What survives from the lecture is the shape of the thing: a client object, a prompt, a handful of generation parameters, a response containing image data. That shape is stable. The specific field names are not.

3.2

The modern call, parameter by parameter

−
Python Generate and save an image — current SDK, no key in the file − 
import base64
from pathlib import Path
from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment

prompt = (
    "A single painted apple on a bare wooden table, "
    "oil-on-canvas texture, warm side light, muted background"
)

resp = client.images.generate(
    model="gpt-image-2",      # pin a dated snapshot in production
    prompt=prompt,
    size="1024x1024",        # cost and latency scale with pixels
    quality="low",           # low | medium | high — see the estimator below
    n=1,
)

# GPT Image models ALWAYS return base64. There is no url field to click.
Path("out").mkdir(exist_ok=True)
for i, img in enumerate(resp.data):
    Path(f"out/apple_{i}.png").write_bytes(base64.b64decode(img.b64_json))
    print(f"wrote out/apple_{i}.png")

Note what changed beyond the model name: the lecture prints image.url and tells you to click it. GPT Image models do not return URLs at all — the base64 field is the only channel. The response_format parameter that used to choose between them applied to DALL·E and is gone with it. Code written against the lecture fails at the print statement even after you fix the model ID.

Table Image parameters — what each one buys, and what it costs −
ParameterValuesEffect
prompttextThe only semantic control. Subject, medium, lighting, composition, background — in that order of leverage.
size1024x1024, 1024x1536, 1536x1024; gpt-image-2 also takes arbitrary W×H divisible by 16, aspect between 1:3 and 3:1Drives price and time. Do not request 2K for a 512px card.
qualitylow / medium / highThe dominant latency lever. On gpt-image-2, high runs a plan-and-review pass that can take 30–50× longer than low.
nintegerImages per call. Cheaper per image than n separate calls in wall-clock terms, but you pay per image regardless.
output_formatpng / webp / jpegTransport only. webp/jpeg with compression cuts bytes, not tokens.
backgroundtransparent / opaque / autoTransparent needs png or webp. Saves a downstream matting step.
3.3

Parameters the lecture invents

−

Three claims in that transcript are not true of the API being demonstrated. They are worth naming individually because each one teaches a different lesson about reading docs.

Trap · "you can add a seed number"

Said explicitly, twice, referencing the slides. The OpenAI images endpoint has never exposed a seed. Seeds are a Stable Diffusion / Flux concept, where you control the initial latent noise. This is a slide from a different vendor's world, presented as fact about this one. Consequence: you cannot reproduce an OpenAI image exactly. If bit-reproducibility matters, that requirement alone chooses your vendor.

Trap · "if you want a hundred, put 100 here"

DALL·E 3 accepted only n=1; the loop the instructor wrote "for the future" could never have fired on the model being used. More importantly the mental model is wrong — n is not a batch discount. You are billed per image. Ten images is ten images' worth of money whether it is one call or ten.

Trap · style="vivid" / "natural"

A real DALL·E 3 parameter, correctly used, now gone with the model. Its behaviour is worth remembering though: vivid quietly instructed the model to dramatise your prompt. The "surreal" look the instructor attributes to the word surreal in the prompt was partly this flag. Two variables changed at once, again — and the second one was invisible.

Note · the omission that explains the most

DALL·E 3 rewrote every prompt you sent it and returned the rewrite in a revised_prompt field. The lecture never mentions this and never reads that field. It is the single biggest reason image results feel unpredictable: you were not tuning the prompt the model saw. GPT Image models similarly interpret rather than transcribe. When output ignores your instruction, the question is what the model was actually handed.

3.4

Budget and latency before you build

−

The lecture's cost advice is "it's not very expensive, put a $10 limit." That is fine for a notebook and useless for a feature. Two numbers decide whether an image feature is viable: cost per thousand images, and p50 latency — because a 200-second call cannot sit inside a request/response cycle, which changes your architecture, not just your budget.

Estimate only. Unit prices are illustrative mid-2026 public figures and vary by exact size, prompt-token count and account tier — check the provider's pricing page before committing a budget. Latency bands come from reported production behaviour, not a benchmark.
Note

Two levers beat every pricing negotiation. Cache on a hash of (prompt, model, size, quality) — in most products the same image is requested many times. And generate previews at low quality, upgrading only the one the user keeps. A 20:1 preview-to-final ratio makes the flagship model affordable.

Architect

Product wants "generate a hero image" on a page that must respond in under two seconds. High quality takes ~200 seconds. What do you build?

You do not make the call synchronous. The request enqueues a job and returns an id immediately; a worker calls the API; the client polls or holds an SSE/websocket connection for the result. That is the whole answer, but the parts that get skipped are the ones that hurt:

  • Idempotency key on the job so a double-submit does not bill twice.
  • A timeout longer than you think. The SDK default is generous; people wrap it in an httpx client with a 60s timeout and get ReadTimeout on every high-quality call — then retry, and pay for images they abandoned.
  • Show a low-quality result first. Fire low and high in parallel; render low in a few seconds and swap. Perceived latency is the number the product actually cares about.
  • Bound the queue and degrade loudly. When the provider is slow, an unbounded queue converts a latency problem into an outage.
PART IV

Local text generation — where the real knobs are

−
4.1

Setup, and the PATH myth

−

Install Ollama, then ollama pull llama3.2. That is the whole setup. The lecture spends several minutes editing Windows environment variables to add the install directory to PATH, presenting it as a required step.

Trap

It is not required, for two reasons. The installer adds itself to PATH already. And more to the point — your Python code never invokes the CLI. It speaks HTTP to a local server on 127.0.0.1:11434. PATH governs whether your shell can find the ollama command. It has no bearing on whether requests.post can reach a socket. Debugging time spent on PATH when the API is unreachable is time not spent asking whether the server is running.

Shell Setup, and the two commands that actually diagnose problems − 
ollama pull llama3.2          # llama2 is legacy — don't start there in 2026
ollama list                   # what's on disk, and how big

# Is the server actually up? This, not PATH, is the first check.
curl http://localhost:11434/api/tags

# Is the model loaded in memory right now, and on GPU or CPU?
ollama ps
Warn · model choice

The lecture uses llama2, and then attributes its disappointing results to the model. Llama 2 shipped in 2023 and is two generations behind; a modern 3B model beats it on nearly every axis while being smaller. If you are reproducing these lessons, use llama3.2 or similar. The download is ~2 GB rather than the 900 MB installer plus a 7B model — and it will fit in RAM more comfortably.

4.2

The HTTP surface — three endpoints, pick deliberately

−

The lecture uses /api/generate without mentioning that alternatives exist. The choice matters more than it looks.

Table Ollama endpoints and when each is correct −

Good · the trick worth stealing

That third row deletes an entire category of work. Set OpenAI(base_url="http://localhost:11434/v1", api_key="ollama") and the same code runs against a local model or a hosted one, chosen by config. Your prompt harness becomes provider-agnostic — which is exactly what you want when the point of the exercise is comparing configurations.

4.3

The silent bug — where the parameters went

−

This is the heart of the section, and the course gets it backwards.

The lecture builds a payload dictionary with model, prompt, temperature, top_p, top_k and max_tokens all as siblings at the top level. Ollama's generate API accepts sampling settings only inside a nested options object. Top-level keys it does not recognise are silently ignored — no error, no warning, a perfectly normal-looking response.

ASCII Where each key lands in the server − 
  THE LECTURE'S PAYLOAD                    WHAT THE SERVER DOES

Trap · this invalidates the lecture's conclusion

The instructor runs temperature 0.9, then 0.1, sees two similar poems, and concludes: free models are weak, do not expect much from parameter changes, paid models would respond more. Both runs used the server default temperature. The only difference between them was ordinary sampling randomness. The experiment did not measure what it claimed to measure, and the lesson drawn from it — that these knobs do not matter much — is the opposite of true.

Note · the generalisable lesson

Permissive JSON APIs that ignore unknown fields will let you configure nothing all day without complaint. Whenever a parameter change produces no visible effect, first prove the parameter arrived — do not theorise about the model. The cheapest proof: set "seed": 42 and "temperature": 0, run twice, and check the outputs are byte-identical. If they are not, your options block is not landing.

4.4

Inside the sampler — what the knobs really do

−

The lecture's definitions — higher temperature is more creative, lower is more deterministic — are true and shallow. They do not tell you why setting temperature 0.9 and top_p 0.5 together, as the lecture does, is a self-cancelling configuration.

At each step the model emits one score (a logit) per token in its vocabulary. Everything you tune is post-processing on that list before one token is drawn.

ASCII Order of operations — filters cut candidates, temperature reshapes odds − 
  logits for all ~128k tokens
        │
        ▼
  ┌───────────────────┐   penalise tokens seen recently.
  │ repeat_penalty    │   Kills loops. Too high = word-salad,
  └────────┬──────────┘   because it punishes "the" and "," too.
           ▼
  ┌───────────────────┐   keep the k highest. A hard cap on
  │ top_k             │   candidates regardless of confidence.
  └────────┬──────────┘   Blunt: same k when the model is sure
           ▼               and when it is guessing.
  ┌───────────────────┐   keep the smallest set whose probability
  │ top_p (nucleus)   │   sums to p. Adaptive: narrow when the
  └────────┬──────────┘   model is confident, wide when it isn't.
           ▼
  ┌───────────────────┐   divide surviving logits by T, re-softmax.
  │ temperature       │   T<1 sharpens toward the leader.
  └────────┬──────────┘   T>1 flattens toward a coin toss.
           ▼
      draw one token  ──►  append, repeat

  THE INTERACTION THE LECTURE MISSES
  Filters run BEFORE temperature. top_p 0.5 may leave 2 candidates.
  Temperature 0.9 then redistributes odds among those 2 — it cannot
  reintroduce the ones already cut. You asked for creativity and then
  removed the material creativity is made of.

  Note: exact ordering varies by runtime. This is the llama.cpp /
  Ollama family's arrangement. vLLM and hosted APIs differ in details.

Good · presets that survive contact with production

Extraction, classification, JSON: temperature 0, top_p 1. You want the argmax; every other knob is a liability.
Summaries, explanation, chat: temperature 0.7, top_p 0.9, leave top_k off.
Ideation, copy variants: temperature 1.0–1.2 with top_p 0.95, plus min_p ~0.05 as a floor to keep genuine nonsense out.
Set one filter, not both. Reasoning about top_k and top_p simultaneously is harder than the benefit; top_p alone is the better default because it adapts to how confident the model is at each step.

Recall

Why does top_p adapt to model confidence while top_k does not?

top_k always keeps exactly k tokens. If the model is 99% sure of the next token, k=50 still admits 49 near-zero alternatives; if the model is genuinely torn between 200 plausible continuations, k=50 amputates most of them. top_p is defined on cumulative probability mass, so a confident step yields a nucleus of one or two tokens and an uncertain step yields dozens — the cut tracks the distribution's actual shape.

Architect

You set temperature 0 for a classifier. A reviewer says "now it's deterministic, we can cache and skip re-testing." Are they right?

No, and it is a useful thing to be right about in a design review.

Temperature 0 makes the sampling step deterministic — always take the highest-scoring token. It does not make the logits deterministic. Floating-point reductions on GPUs are not associative, so results depend on how work was scheduled and batched. On a hosted endpoint your request is batched with strangers' requests, and batch composition changes the arithmetic order. Mixture-of-experts routing adds another source of variation. The practical consequence: two near-tied classes can swap places between runs even at temperature 0.

What temperature 0 buys is a large reduction in variance, not a guarantee. Caching on (prompt, model, params) is still the right call — just because it saves money, not because the function is provably pure. And you still re-test on model upgrades, since determinism within a snapshot says nothing across snapshots.

4.5

Reading the response — streaming done properly

−

The lecture writes a loop over response.text.strip().split("\n"), parsing each line as JSON and concatenating the response field. The logic is correct and the explanation of it is good. The mechanics defeat the purpose.

Warn

Touching response.text blocks until the entire body has arrived and buffers it in memory. You have taken a streaming API and made it non-streaming, then written streaming-shaped parsing code over the corpse. If you are going to wait for the whole thing anyway, send "stream": false and parse one clean JSON object.

Python Both modes, correctly — plus the metrics field nobody reads − 
import json, requests

URL  = "http://localhost:11434/api/generate"
BASE = {"model": "llama3.2", "prompt": "Write a poem about the sunset."}
OPTS = {"temperature": 0.9, "top_p": 0.9, "num_predict": 120, "seed": 42}


def blocking():
    """One request, one JSON object. Simplest thing that works."""
    r = requests.post(URL, json={**BASE, "stream": False, "options": OPTS}, timeout=180)
    r.raise_for_status()          # the lecture never checks this
    data = r.json()
    print("tok/s:", data["eval_count"] / (data["eval_duration"] / 1e9))
    return data["response"]


def streaming():
    """Tokens land as they are produced. stream=True on the HTTP call
    is what makes iter_lines actually incremental."""
    with requests.post(URL, json={**BASE, "stream": True, "options": OPTS},
                       stream=True, timeout=180) as r:
        r.raise_for_status()
        parts = []
        for line in r.iter_lines(decode_unicode=True):
            if not line:
                continue              # keep-alive blank line
            chunk = json.loads(line)   # NDJSON: one object per line
            parts.append(chunk.get("response", ""))
            print(chunk.get("response", ""), end="", flush=True)
            if chunk.get("done"):    # the terminal object carries the timings
                print(f"\n[stop: {chunk.get('done_reason')}]")
        return "".join(parts)

Two things the lecture's version silently skips. There is no raise_for_status, so a 404 from a misspelled model name yields an empty string and looks like a model that had nothing to say. And the final chunk carries eval_count and eval_duration — your tokens-per-second, free, on every call. That number is how you decide whether a local model is viable at all, and it is sitting in a field nobody reads.

Note · done_reason

Worth checking every time. If it says length, your num_predict cut the output mid-sentence — a truncated answer that looks like a bad answer. The lecture's 100-token cap would do exactly this to a poem of any length, and the resulting stub would be blamed on the model.

Python sweep.py — prompt versions × parameter grid, scored. Needs only requests. − 
#!/usr/bin/env python3
"""
sweep.py - iterative prompt testing with the parameters actually applied.

    ollama pull llama3.2
    pip install requests
    python sweep.py

Runs every prompt version against every parameter setting N times,
scores each output against a rubric, prints a comparison table.
"""
from __future__ import annotations

import json
import re
import statistics
from dataclasses import dataclass, field

import requests

URL      = "http://localhost:11434/api/chat"   # chat, not generate
MODEL    = "llama3.2"
SAMPLES  = 3                                   # n=1 is how you fool yourself
TIMEOUT  = 180

# --- the fixed test inputs. Small, but never one. ------------------------
TOPICS = ["climate change", "how vaccines work", "why the sky is blue"]

# --- prompt versions. One variable changes per step. ---------------------
PROMPTS = {
    "v1_vague":     "Explain {topic}.",
    "v2_audience":  "Explain {topic} to a 10-year-old in simple language.",
    "v3_length":    "Explain {topic} to a 10-year-old in simple language. "
                     "Use exactly three sentences.",
    "v4_example":   "Explain {topic} to a 10-year-old in simple language. "
                     "Use exactly three sentences. End with one fun everyday "
                     "comparison. Do not add a preamble or a closing offer to help.",
}

# --- parameter grid. These land in options, where they are read. ---------
GRID = {
    "cold":    {"temperature": 0.1, "top_p": 1.0},
    "default": {"temperature": 0.8, "top_p": 0.9},
    "hot":     {"temperature": 1.3, "top_p": 0.95},
}


@dataclass
class Result:
    prompt_id: str
    setting:   str
    scores:    list[float] = field(default_factory=list)
    samples:   list[str]   = field(default_factory=list)

    @property
    def mean(self) -> float:
        return statistics.mean(self.scores) if self.scores else 0.0

    @property
    def spread(self) -> float:
        """Run-to-run variance. If this is large, a small mean gain is noise."""
        return statistics.pstdev(self.scores) if len(self.scores) > 1 else 0.0


def call(prompt: str, opts: dict, seed: int) -> str:
    """One completion. Note options nesting - the whole point of §4.3."""
    body = {
        "model":    MODEL,
        "messages": [{"role": "user", "content": prompt}],
        "stream":   False,
        "options":  {**opts, "num_predict": 300, "seed": seed},
    }
    r = requests.post(URL, json=body, timeout=TIMEOUT)
    r.raise_for_status()                     # fail loudly, not silently
    return r.json()["message"]["content"].strip()


def score(text: str) -> float:
    """Binary rubric checks. Crude on purpose: an imperfect rubric you
    actually run beats a perfect one you argue about. Replace the
    readability heuristic with a real metric when it starts to matter."""
    sentences = [s for s in re.split(r"[.!?]+", text) if s.strip()]
    words     = text.split()
    checks = [
        len(sentences) <= 3,                                # length held
        len(words) <= 90,                                   # density held
        sum(len(w) > 11 for w in words) <= 2,              # jargon proxy
        any(k in text.lower() for k in ("like", "imagine", "think of")),
        not text.lower().startswith(("sure", "certainly", "here", "of course")),
    ]
    return sum(checks) / len(checks)


def main() -> None:
    results: list[Result] = []
    for pid, template in PROMPTS.items():
        for sid, opts in GRID.items():
            res = Result(pid, sid)
            for topic in TOPICS:
                for i in range(SAMPLES):
                    # Varying the seed samples the distribution;
                    # fixing it per (topic, i) keeps the comparison paired,
                    # so every setting faces the same draws.
                    out = call(template.format(topic=topic), opts, seed=1000 + i)
                    res.scores.append(score(out))
                    res.samples.append(out)
            results.append(res)
            print(f"  ran {pid:14s} {sid:8s} -> {res.mean:.2f}")

    print("\n" + "PROMPT".ljust(16) + "SETTING".ljust(10) + "MEAN   SPREAD")
    print("-" * 44)
    for r in sorted(results, key=lambda r: -r.mean):
        print(f"{r.prompt_id:16s}{r.setting:10s}{r.mean:5.2f}  ±{r.spread:.2f}")

    best = max(results, key=lambda r: r.mean)
    print(f"\nbest: {best.prompt_id} @ {best.setting}\n")
    print(best.samples[0])

    # Keep the run. Next month's "it got worse" argument needs a baseline.
    with open("sweep_results.json", "w") as f:
        json.dump([{"prompt": r.prompt_id, "setting": r.setting,
                    "mean": r.mean, "spread": r.spread,
                    "samples": r.samples} for r in results], f, indent=2)


if __name__ == "__main__":
    main()

Reference

6.1

Glossary

−
API — Application Programming Interface
The programmatic surface of a service. Here, the thing that exposes parameters the chat UI hides.
b64_json
Response field carrying an image as base64 text rather than a link. The only image channel GPT Image models offer.
Eval set
A fixed collection of test inputs plus expected properties, run against every prompt version. The thing that converts "feels better" into a number.
Entropy
Uncertainty of a probability distribution, in bits. 0 bits means one certain token; 3 bits means roughly eight equally likely ones.
Logit
The raw score the model assigns each vocabulary token before it is turned into a probability. All sampling parameters operate on logits.
min_p
Drops any token whose probability is below a fraction of the top token's. A floor against nonsense that is gentler than top_k.
NDJSON — newline-delimited JSON
One complete JSON object per line. The wire format of Ollama's streaming responses.
num_predict
Ollama's maximum output tokens. The equivalent of max_tokens elsewhere.
Nucleus sampling
See top_p. Named for the "nucleus" of tokens holding the top p of probability mass.
Ollama
A local model runner that pulls quantised weights and serves them over HTTP on port 11434.
Quantisation
Storing weights at lower precision (8-bit, 4-bit) to fit larger models in less memory, at some quality cost. Why a 7B model downloads as ~4 GB.
repeat_penalty
Down-weights recently emitted tokens to break loops. Too aggressive and it starts punishing necessary function words.
revised_prompt
The rewritten prompt a model actually used to generate an image. Read it when output ignores your instructions.
Seed
An integer fixing the random draw so a run is reproducible. Present in Ollama; absent from OpenAI's image API.
Softmax
The function converting logits into probabilities summing to 1. Temperature is applied inside it.
Snapshot pinning
Requesting a dated model version rather than a moving alias, so a provider update cannot silently change your output.
Temperature
Divides logits before softmax. Below 1 sharpens toward the leading token; above 1 flattens toward uniform.
top_k
Keeps only the k highest-scoring tokens. A fixed-width cut that ignores how confident the model is.
top_p
Keeps the smallest set of tokens whose probabilities sum to p. An adaptive cut that widens when the model is unsure.
6.2

Closing recall — five questions

−
Recall · 1

Where do sampling parameters go in an Ollama request, and what happens if you put them elsewhere?

Inside a nested options object. Anywhere else they are silently dropped — no error — and the server uses its defaults, which is exactly how you end up concluding that temperature does not do much.

Recall · 2

Why is setting temperature 0.9 with top_p 0.5 usually incoherent?

Filters run before temperature. top_p 0.5 may leave only two candidates; temperature 0.9 then shuffles the odds between those two and cannot restore anything already cut. You asked for diversity and pre-emptively deleted its source. Set one or the other.

Recall · 3

Name two ways the course's iterative-testing demo could show improvement that would not survive a clean re-run.

(1) The versions were run in one continuing chat, so earlier turns were still in context and doing some of the work. (2) A single sample per version — the difference could be run-to-run sampling variance rather than a prompt effect.

Recall · 4

Your image call succeeds but image.url raises AttributeError. Why?

You are on a GPT Image model, which always returns base64 in b64_json and never a URL. The url/b64 choice belonged to DALL·E, which left the API in May 2026. Decode the base64 and write the bytes.

Architect · 5

Give the two-sentence case for running a prompt sweep harness rather than tuning in a chat window.

A chat window gives you one sample of one input with no baseline, so you cannot separate an improvement from noise, and you have nothing to compare against when quality drifts later. A harness makes the prompt a versioned artifact with a score attached — which is the only form in which it can be reviewed, regressed, or defended.
