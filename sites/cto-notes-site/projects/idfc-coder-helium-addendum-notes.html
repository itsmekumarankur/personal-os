💭 Deeper question:

Should Helium be eventually consistent or strongly consistent?
Reveal
EVENTUALLY CONSISTENT
        |
        +-- Index updated minutes after commit
        +-- Developers may get stale context
        +-- Simpler, less resource-intensive

STRONGLY CONSISTENT
        |
        +-- Index updated instantly
        +-- Developers always get current context
        +-- Complex, expensive

Architectural insight: The answer depends on:

         COST OF STALE CONTEXT
                |
      +---------+---------+
      |                   |
      v                   v
   HIGH RISK          LOW RISK
      |                   |
      +---------+---------+
                |
                v
      Appropriate consistency model

If stale context causes:

- Security issues
- Data corruption
- Production outages

Then strongly consistent is worth the cost.

If stale context causes:

- Minor bugs
- Developer rework
- Slight inefficiency

Then eventually consistent is acceptable.

    v

              KNOWLEDGE TYPES

🧠 FINAL ARCHITECTURE PRINCIPLE

If this entire document could be summarized in one principle:

               ARCHITECTURE PRINCIPLE

            SEPARATE KNOWLEDGE FROM
            REASONING

    Knowledge = Helium (dynamic, factual)
    Reasoning = LLM (static, generic)

            VALIDATE EVERYTHING

    Every generated claim should be
    verified against the knowledge layer

    doesn't know and ask for help

            LEARN FROM INTERACTIONS

    Not all knowledge should be
    available to all users
